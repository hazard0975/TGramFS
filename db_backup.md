# Архитектура и спецификация системы резервного копирования базы данных (db_backup.md)

Документ фиксирует согласованную архитектуру, механизмы снятия консистентных снимков SQLite в WAL-режиме, стратегию версионирования в отдельном канале Telegram и поддержку сценария «Дом — Работа» (мульти-устройство).

---

## 1. Контекст и бизнес-цель

### 1.1. Критичность `base.db`
В проекте виртуального диска Telegram файлы хранятся в Telegram как независимые медиа-сообщения. Вся логическая структура файловой системы хранится исключительно в локальной базе данных `base.db`:
* Иерархия каталогов (`parent_id`, связь папок и файлов, пустые каталоги).
* Версионирование файлов (`version = 1, 2...`).
* Состояния и виртуальная корзина (`in_trash = 1`).
* Локальные микрофайлы до 1 байта (`inline_data`).
* Персистентные очереди фоновых задач (`pending_deletions`, `pending_caption_updates`).

**Потеря `base.db` означает полную потерю дерева каталогов и превращение файлов в канале в разрозненный плоский массив.**

### 1.2. Отказ от реконструкции базы сканированием канала
Прямой парсинг всех сообщений канала при утере базы отклонен архитектурно:
* Лимиты Telegram API (`FLOOD_WAIT`) при обходе десятков и сотен тысяч сообщений.
* Невозможность восстановить пустые директории и структуру временных меток.
* Риск расхождения версий и порядка удалений.

## 2. Механика создания консистентных снимков SQLite (WAL Mode)

### 2.1. Особенность режима WAL (`base.db-wal`)
В сервисе включен режим `PRAGMA journal_mode=WAL;`. При активной записи данные находятся не только в `base.db`, но и в буферных файлах `base.db-wal` и `base.db-shm`. Прямое копирование файла `base.db` через `File.Copy` на лету недопустимо, так как копия будет поврежденной или неполной.

### 2.2. Двухэтапный алгоритм снятия снимка (Root Cause)
1. **Принудительный чекпоинт в основной файл:**
   ```sql
   PRAGMA wal_checkpoint(TRUNCATE);
   ```
   * Сбрасывает все подтвержденные транзакции из `base.db-wal` обратно в основной файл `base.db`.
   * Усекает файл `base.db-wal` до 0 байт.
   * Делает основной файл `base.db` на 100% консистентным на диске (включая безопасность для внешнего софта бэкапа).

2. **Создание изолированного монолитного снимка:**
   ```sql
   VACUUM INTO 'backups/base_snapshot.db';
   ```
   * Создает независимый, атомарный, дефрагментированный файл-слепок без блокировки читателей и писателей.
   * Целевой файл не требует WAL-файлов и сразу готов к передаче в Telegram.

## 3. Хранение бэкапов в отдельном Telegram-канале

### 3.1. Структура канала и единый источник правды (Single Source of Truth)
* Для бэкапов используется отдельный приватный канал Telegram (по умолчанию `Telegram Drive Backups`).
* **Хранение реквизитов канала:** ID канала (`channel_id`) и ключ доступа (`access_hash`) хранятся непосредственно в таблице `telegram_channels` базы `base.db` с признаком `channel_type = 'backup'`. В файле `settings.json` они не дублируются.
* **Мгновенное разрешение (0 мс):** При отправке бэкапа программа берет `channel_id` и `access_hash` прямо из SQLite без сетевого перебора диалогов (`Messages_GetAllChats`).
* **Бутстрап при первом запуске:** Если записи в базе нет, приватный канал создается автоматически через Telegram API и его реквизиты записываются в `telegram_channels`.
* В канале формируется хронологическая история всех ревизий базы данных.
* Пользователь может в любой момент открыть канал с телефона или любого ПК и скачать нужный снимок за любую дату.

### 3.2. Формат карточки сообщения в Telegram
Каждый файл базы выгружается как документ со стандартизированной подписью:
```text
💾 Резервная копия базы данных base.db
📅 Дата: 2026-10-11 18:45:10
💻 Устройство: WORK-LAPTOP
📁 Всего узлов: 14 250 (файлов: 12 800, папок: 1 450)
📦 Размер: 18.4 МБ
#db_backup
```

## 4. Сценарий «Дом — Работа» (Мульти-устройство и синхронизация)

### 4.1. Завершение работы на первом ПК (Рабочий ноутбук)
1. **Экстренный ручной бэкап из трея:**
   * В контекстном меню трея пункт: `Отправить бэкап базы в Telegram`.
   * Быстрое нажатие перед закрытием крышки ноутбука: выполняется чекпоинт, снимок и отправка в канал с уведомлением в трее.
2. **Автоматический бэкап при выходе:**
   * При выборе пункта `Выход` в трее сервис проверяет флаг наличия незафиксированных изменений структуры (`_hasUnsavedDbChanges`). Если были изменения — выполняется быстрая фоновая выгрузка в канал перед закрытием процесса.
3. **Фоновый отложенный таймер (Debounce):**
   * При непрерывной работе таймер срабатывает через 10–15 минут тишины после последней операции записи (`PUT`, `DELETE`, `MOVE`, `MKCOL`).

### 4.2. Запуск на втором ПК (Домашний компьютер)
1. **Проверка обновлений при старте:**
   * Сервис обращается к каналу бэкапов и читает последнее сообщение с хэштегом `#db_backup`.
   * Из подписи извлекаются дата снимка и имя устройства-источника.
2. **Диалоговое подтверждение:**
   * Если дата бэкапа в канале **свежее**, чем дата локальной `base.db`, пользователю выводится нативный диалог подтверждения:
     > *«В канале бэкапов обнаружена более свежая база данных от WORK-LAPTOP (11.10.2026 18:45:10).*  
     > *Локальная база датирована: 10.10.2026 21:10:00.*  
     > *Загрузить свежую базу и обновить структуру диска?»*  
     > `[ Обновить базу ]`  `[ Оставить локальную ]`
3. **Безопасная замена базы (Hot Swap):**
   * Перед заменой локальная база копируется в `backups/base_pre_sync_backup.db`.
   * Свежая база скачивается во временный файл, проверяется на целостность (`PRAGMA quick_check;`).
   * Очищается таблица `upload_progress` (чужие незавершенные загрузки с другого ПК не должны обрабатываться на домашнем).
   * Соединение с базой переинициализируется, виртуальный диск подхватывает обновленное дерево.

### 4.3. Изоляция сессий MTProto
* Файл авторизации `user.session` является локальным для каждого ПК.
* В схеме базы `telegram_accounts.session_path` указывает на локальный файл `'user.session'`.
* Подмена файла `base.db` **не сбрасывает** авторизацию на втором компьютере, если оба устройства были предварительно авторизованы со своими локальными файлами сессий.

## 5. Планируемые модули и интерфейс

### 5.1. Служба `DatabaseBackupService`
* `CreateLocalSnapshotAsync()` — чекпоинт WAL и `VACUUM INTO`.
* `UploadBackupToTelegramAsync(string channelIdOrTitle)` — отправка документа в канал с информационным сообщением.
* `CheckRemoteBackupStatusAsync()` — получение метаданных последнего бэкапа из канала.
* `RestoreFromRemoteBackupAsync(long messageId)` — скачивание, валидация и безопасная подмена `base.db`.

### 5.2. Пользовательский интерфейс (UI)
1. **Контекстное меню системного трея (`TrayContext`):**
   * Пункт: `Создать бэкап базы в Telegram`.
2. **Окно настроек (`AuthSettingsForm`):**
   * Секция настроек бэкапа:
     * Выбор целевого канала для бэкапов из списка доступных каналов Telegram.
     * Чекбокс: `[x] Проверять наличие свежей базы в Telegram при запуске`.
     * Чекбокс: `[x] Автоматический бэкап через 15 минут после изменений`.
     * Кнопка: `Создать бэкап сейчас`.
     * Кнопка: `Восстановить базу из Telegram...`.
