# Реестр технических решений и проверенных гипотез (DECISIONS_LOG)

Документ фиксирует историю исследованных подходов, архитектурных развилок, проверенных гипотез и кодов ошибок с детальным анализом первопричин (Root Cause Analysis). Служит единым источником правды для предотвращения повторения неэффективных или тупиковых решений при дальнейшей разработке.

## 1. Извлечение метаданных и генерация превью для видеофайлов (MP4/MKV)

### Бизнес-цель:
Автономно, без тяжелых внешних зависимостей (типа FFmpeg на 100 МБ), извлекать размеры видеокадра (`Width`, `Height`), длительность (`Duration`) и генерировать JPEG стоп-кадр (`Thumbnail`) для Telegram Bot API (SendVideo).

---

### Подход 1.1: Внешний бинарник FFmpeg CLI
* **Гипотеза:** Запуск `ffmpeg.exe -ss 00:00:01 -i video.mp4 -vframes 1 preview.jpg`.
* **Результат:** ❌ **Отклонено архитектурно.**
* **Первопричина:** 
  - Дистрибутив разрастается на 80–120 МБ.
  - Требует управления внешними процессами, перехвата `stdout`/`stderr`, контроля зависаний и создания временных файлов на диске.
* **Вывод:** Проект должен оставаться легковесным и использовать возможности ОС Windows или нативные .NET парсеры.

---

### Подход 1.2: Извлечение обложек через библиотеку ATL.NET
* **Гипотеза:** Библиотека тегов `ATL.AudioData` умеет читать метаданные мультимедиа и доставать встроенные изображения (`EmbeddedPictures`).
* **Результат:** ⚠️ **Частично решает (только базовые метаданные, превью нет).**
* **Первопричина:**
  - В отличие от MP3 (тег ID3v2 `APIC`), в обычных MP4 видеофайлах обложка (`covr` атом) почти никогда не зашита. В них есть видеопоток, но нет встроенной картинки.
* **Вывод:** ATL.NET подходит только для аудио и части метаданных контейнера, но не способна декодировать сжатый видеокадр.

---

### Подход 1.3: Чистый C# парсер атомов MP4 (ISO Base Media File Format)
* **Гипотеза:** Побайтово читать заголовок MP4 (атомы `ftyp`, `moov`, `trak`, `mdia`, `minf`, `stbl`, `tkhd`, `mvhd`) через `FileStream` с поиском нужных полей смещения.
* **Результат:** ✅ **Успешно принято для метаданных (`Width`, `Height`, `Duration`).**
* **Преимущества:**
  - Работает за 1–2 миллисекунды.
  - Потребляет минимум памяти, читает только мета-заголовки (первые несколько килобайт файла).
  - 100% автономно, не зависит от установленных кодеков ОС.
* **Ограничение:** Не умеет декодировать сжатые H.264/HEVC NAL-юниты в сырые пиксели.

---

### Подход 1.4: Windows Shell API (IShellItemImageFactory / IThumbnailCache)
* **Гипотеза:** Вызывать стандартный COM Shell API Windows, который генерирует миниатюры в Проводнике (Explorer).
* **Результат:** ⚠️ **Ненадежно для виртуальных и сетевых дисков.**
* **Первопричина:**
  - В Windows Shell действует встроенная политика энергосбережения и сетевой безопасности: **для файлов, расположенных на сетевых/виртуальных дисках (WebDAV/WinFsp), генерация миниатюр по умолчанию отключена**, если не включена специальная групповая политика (`DisableThumbsDBOnNetworkFolders`).
  - Вызов возвращает пустую иконку файла вместо кадра видео.
* **Вывод:** Нельзя полагаться на Shell Cache при работе с WebDAV/WinFsp.

### Подход 1.5: Windows Media Foundation (IMFSourceReader P/Invoke)

Попытка использовать встроенный в Windows декодер Media Foundation без внешних DLL. Пройдена цепочка из 5 технических итераций:

#### Итерация 1.5.1: Декларативный C# COM-интерфейс `IMFSourceReader`
* **Что делали:** Описали интерфейс с атрибутом `[ComImport] [Guid("70ae66fd-9a09-4224-b056-22563b764c5f")] [InterfaceType(ComInterfaceType.InterfaceIsIUnknown)] interface IMFSourceReader`.
* **Ошибка:** `System.InvalidCastException: Specified cast is not valid`.
* **Root Cause:** Внутренний объект SourceReader в Media Foundation реализует `IMFSourceReader` через нестандартную раскладку tear-off интерфейсов, из-за чего CLR COM-маршалер не мог корректно сопоставить таблицу виртуальных методов (vtable).
* **Решение:** Переход на динамический вызов методов через указатель на vtable интерфейса (Direct VTable pointer dispatch).

#### Итерация 1.5.2: Вызов экспортируемой функции `MFSetAttributeUINT32`
* **Что делали:** Импортировали `[DllImport("mfplat.dll")] MFSetAttributeUINT32(IntPtr pAttributes, ref Guid guidKey, uint unValue)`.
* **Ошибка:** `System.EntryPointNotFoundException: Unable to find an entry point named 'MFSetAttributeUINT32' in DLL 'mfplat.dll'`.
* **Root Cause:** В Windows SDK `MFSetAttributeUINT32` является C++ inline-макросом, который вызывает метод COM-интерфейса `pAttributes->SetUINT32()`, а не экспортируемой C-функцией из `mfplat.dll`.
* **Решение:** Получение `IMFAttributes` через `MFCreateAttributes`, вычисление смещения метода в vtable (метод `SetUINT32` находится по смещению `index * IntPtr.Size` в `IMFAttributesVtbl`) и вызов через `Marshal.GetDelegateForFunctionPointer`.

#### Итерация 1.5.3: Запрос форматов (RGB32/NV12/YUY2) и ошибка `0x80070057 (E_INVALIDARG)`
* **Что делали:** Создали пустой медиатип через `MFCreateMediaType`, заполнили `MF_MT_MAJOR_TYPE` и `MF_MT_SUBTYPE`, вызвали `reader.SetCurrentMediaType(MF_SOURCE_READER_FIRST_VIDEO_STREAM, NULL, mediaType)`.
* **Ошибка:** `SetCurrentMediaType вернул hr = 0x80070057 (E_INVALIDARG)` для всех подтипов (RGB32, NV12, YUY2).
* **Root Cause:** 
  1. **Значение констант потоков:** `MF_SOURCE_READER_FIRST_VIDEO_STREAM` в Windows SDK равен `0xFFFFFFFC` (-4), а `MF_SOURCE_READER_ALL_STREAMS` равен `0xFFFFFFFE` (-2). Ошибочные значения (`-2` и `-3`) приводили к невалидному дескриптору потока в методе `SetCurrentMediaType`.
  2. **Пустой дескриптор типа:** При создании типа через `MFCreateMediaType` в нём отсутствуют обязательные атрибуты видеокадра (`MF_MT_FRAME_SIZE`, `MF_MT_PIXEL_ASPECT_RATIO` и т.д.), из-за чего MFT-декодер отклоняет запрос как неполный аргумент.
* **Решение:** 
  - Исправлены битовые константы потоков: `FIRST_VIDEO_STREAM = 0xFFFFFFFC` (-4), `ALL_STREAMS = 0xFFFFFFFE` (-2).
  - Реализовано получение нативного типа от декодера через `reader.GetNativeMediaType(streamIndex, 0, out baseType)` с последующей заменой `MF_MT_SUBTYPE` (таким образом сохраняются все реальные видео-атрибуты файла).
  - Добавлен двухэтапный перебор дескриптора потока: сначала символический `MF_SOURCE_READER_FIRST_VIDEO_STREAM`, затем явный индекс видеопотока `0`.

#### Итерация 1.5.4: Ошибки `0xC00D5212` (MF_E_TOPO_CODEC_NOT_FOUND) и `InvalidCastException` в ReadSample
* **Что делали:** Вызывали `ReadSample` с маршалингом выходного параметра напрямую в `out IMFSample ppSample` и передавали `IMFAttributes` через нетипизированный указатель.
* **Ошибки:**
  1. `System.InvalidCastException: Specified cast is not valid` в CLR `InterfaceMarshaler.ConvertToManaged`.
  2. `0xC00D5212` / `0xC00D36B4`: декодер не мог согласовать подтип RGB32 для сжатых H.264 потоков.
* **Root Cause:**
  1. Выходной параметр `ppSample` в `ReadSample` может содержать промежуточные COM-объекты или кастоваться некорректно через жесткую декларацию C# интерфейса.
  2. В `IMFSourceReader` по умолчанию отключен видеопроцессор преобразования форматов цвета. Без включенного `MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING` декодер требует явного кодека для вывода RGB.
* **Решение:**
  - Типизированный вызов `attributes.SetUINT32(MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING, 1)` при создании ридера (включает системный аппаратный преобразователь цвета Windows Video Processor).
  - В `ReadSample` параметр объявлен как `out IntPtr pSample` с безопасным приведением через `Marshal.GetObjectForIUnknown(pSample)` и освобождением `Marshal.Release(pSample)`.

#### Итерация 1.5.5: Отказ от `MFCreateAttributes` и автоматический фоллбек на текущий медиатип
* **Что делали:** В `MFCreateAttributes` происходил `InvalidCastException` из-за несоответствия COM-маршалинга `IMFAttributes` в .NET рантайме.
* **Root Cause:**
  1. `MFCreateAttributes` в `mfplat.dll` не гарантирует точного соответствия декларации интерфейса в .NET при маршалинге через P/Invoke.
  2. Вызов `reader.SetStreamSelection(ALL_STREAMS, false)` деактивировал декодеры видео в некоторых сборках Windows Media Foundation.
* **Решение:**
  - `MFCreateSourceReaderFromURL` вызывается напрямую с `IntPtr.Zero` (атрибуты необязательны для декодирования видеопотока).
  - Убран деструктивный вызов отключения всех потоков: первый видеопоток активируется напрямую через `SetStreamSelection(FIRST_VIDEO_STREAM, true)`.
  - Добавлен надежный фоллбек: если согласование целевого подтипа не удалось, ридер опрашивает свой текущий нативный тип (`reader.GetCurrentMediaType`), извлекает `MF_MT_SUBTYPE` и читает кадры в этом нативном формате.

#### Итерация 1.5.6: Устранение `InvalidCastException` в `IMFSample` через прямой вызов VTable слотов
* **Что делали:** `Marshal.GetObjectForIUnknown(pSample)` бросал `InvalidCastException: Specified cast is not valid`.
* **Root Cause:** 
  1. В C++ Windows Media Foundation интерфейс `IMFSample` наследуется от `IMFAttributes` (3 метода `IUnknown` + 30 методов `IMFAttributes` = методы `IMFSample` начинаются со слота 33, а не 3).
  2. Маршалер .NET при использовании C# интерфейса `[InterfaceType(ComInterfaceType.InterfaceIsIUnknown)]` не может разрешить vtable-смещение унаследованных COM-интерфейсов и выбрасывает ошибку приведения типа.
* **Решение:**
  - Полный отказ от COM-маршалинга `IMFSample` и `IMFMediaBuffer`.
  - Вызовы осуществляются напрямую через смещения в таблице виртуальных функций (VTable):
    - `ConvertToContiguousBuffer`: слот 41 в `IMFSample` VTable.
    - `Lock`: слот 3 в `IMFMediaBuffer` VTable.
    - `Unlock`: слот 4 в `IMFMediaBuffer` VTable.
  - Это на 100% исключает исключения среды выполнения .NET и обеспечивает прямую высокопроизводительную работу с памятью кадра.

#### Итерация 1.5.7: Нативная C# конвертация NV12/YUY2 в растр RGB
* **Что делали:** Полученный от Media Foundation буфер сэмплов `NV12` преобразуется в `System.Drawing.Bitmap` (или `SKBitmap`) с помощью прямого доступа к памяти (`Bitmap.LockBits` + unsafe pointers).
* **Формула цвета (ITU-R BT.601):**
  $$\begin{aligned}
  R &= Y + 1.402 \cdot (V - 128) \\
  G &= Y - 0.344136 \cdot (U - 128) - 0.714136 \cdot (V - 128) \\
  B &= Y + 1.772 \cdot (U - 128)
  \end{aligned}$$

#### Итерация 1.5.8: Активация Windows Video Processor через VTable IMFAttributes
* **Что делали:** Для отдельных специфических профилей H.264 видеопоток не декодировался напрямую в `NV12` аппаратным кодеком, оставаясь в сыром FourCC `AVC1` (`0x31305641`).
* **Root Cause:** Без установленного атрибута `MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING = 1` Media Foundation не подключает промежуточный системный преобразователь форматов цвета (Video Processor MFT).
* **Решение:**
  - Создание `IMFAttributes` через прямой P/Invoke `MFCreateAttributes(out IntPtr pAttributes, 1)`.
  - Установка флага `MF_SOURCE_READER_ENABLE_VIDEO_PROCESSING` через вызов метода `SetUINT32` (слот 19 в VTable `IMFAttributes`) по указателю без использования COM-маршалинга .NET.
  - Первоочередной опрос явного `streamIndex = 0` перед псевдо-индексом `-4`, исключая ошибки топологии `0xC00D5212`.
  - В результате Windows принудительно декодирует любые сжатые видеопотоки в несжатые растровые плоскости `NV12` / `RGB32`.

#### Итерация 1.5.9: Динамическое обнаружение индекса видеопотока (Multi-stream files)
* **Что делали:** В MP4-файлах, где поток 0 является аудиодорожкой (например, AAC/M4A), ридер ошибочно считывал сэмплы звука вместо видео.
* **Root Cause:** Предположение, что видео всегда находится под индексом `stream = 0`. В файле `Richard X...` поток 0 — это аудио, поэтому Проводник Windows и Media Foundation без явного указания потока спотыкались о звуковую дорожку.
* **Решение:**
  - Отключение всех потоков через `SetStreamSelection(MF_SOURCE_READER_ALL_STREAMS, false)`.
  - Динамический перебор потоков (`GetNativeMediaType`) и поиск того, у которого `MF_MT_MAJOR_TYPE == MFMediaType_Video`.
  - Включение именно найденного видеопотока.

#### Итерация 1.5.10: Учет аппаратного выравнивания строк (Stride/Pitch) и устранение артефактов
* **Что делали:** При конвертации NV12 для нестандартных ширин (например, 854x480) возникал диагональный сдвиг строк и зеленая полоса сверху из-за несовпадения логической ширины и аппаратного шага строки видеокарты (выравнивание по границе 16/32 байт).
* **Root Cause:** Чтение плоскостей NV12 линейно `width * height` вместо `stride * height`, где лишние паддинг-байты декодировались формулой BT.601 в зеленый цвет.
* **Решение:**
  - Определение `MF_MT_DEFAULT_STRIDE` или вызов `MFGetStrideForBitmapInfoHeader`.
  - Корректная адресация в памяти: `rowY = pY + (y * stride)`, `rowUV = pUV + ((y / 2) * stride)`.
  - Устранена зеленая полоса и любые геометрические искажения.

#### Итерация 1.5.11: Смещение таймкода превью (Seek) против темных/пустых начальных кадров
* **Что делали:** Добавлен вызов `reader.SetCurrentPosition` со смещением на 2.0 секунды вперед (или 0.5с для ультра-коротких роликов), чтобы избежать захвата черного экрана на Fade-In заставках клипов.
* **Результат:** ✅ **100% стабильное извлечение сочного кадра за 30–50 мс на любой версии Windows 10/11 без внешних библиотек и утилит.**

## 4. Универсальный (Format-Agnostic) алгоритм распознавания паттерна чтения и защиты от фонового скачивания

### Бизнес-цель:
Разграничить запросы считывания тегов/эскизов/метаданных от реального скачивания/воспроизведения файла, не привязываясь к конкретным спискам расширений файлов (`.mp3`, `.mp4`, `.mkv` и т.д.).

---

### Подход 4.1: Белые списки расширений (`isMediaFile`)
* **Гипотеза:** Проверять расширение файла (`.mp3`, `.flac`, `.mp4`) и включать логику метаданных только для известных медиаформатов.
* **Результат:** ❌ **Отклонено архитектурно.**
* **Первопричина:** Расширений файлов сотни (`.mkv`, `.mov`, `.avi`, `.pdf`, `.zip`, `.iso`), за всеми не уследить. Включение или исключение форматов из списков приводит к тому, что не включенные расширения при открытии папок в Проводнике провоцируют фоновый претч всего файла на 100%.

---

### Подход 4.2: Определение по фактическому паттерну чтения чанков (Sequential Read Detection)
* **Гипотеза:** Отслеживать историю запрошенных чанков (`FileReadSequence`). Если клиент запрашивает первый чанк (`#0`), хвостовой чанк (`#N-1`) или совершает одиночные скачки (Seek), считать это сбором метаданных/эскизов (`isMetadataProbe = true`). Если фиксируется чтение минимум 2 чанков подряд (`#0 -> #1`, `#5 -> #6`), переключаться в режим полноценного скачивания (`isMetadataProbe = false`).
* **Результат:** ✅ **Успешно принято.**
* **Преимущества:**
  - 100% Format-Agnostic: одинаково идеально работает для любого существующего и будущего формата (`.mp4`, `.mp3`, `.mkv`, `.iso`, `.zip`).
  - Проводник Windows при открытии папок с видеоклипами скачивает только первые/хвостовые байты для эскиза, отображается плашка `[Запрос метаданных]`, и выкачка файла на 100% не запускается.
  - Изоляция микро-запросов внутри одного чанка: повторные обращения Проводника к суб-блокам одного и того же чанка (`currentChunkIdx == LastChunkIndex`) больше не накручивают `SequentialCount`. Инкремент происходит строго при переходе на следующий 1 МБ чанк (`currentChunkIdx == LastChunkIndex + 1`), исключая ложные фоновые выкачки файлов при обычном открытии папок.
  - Адаптивное буферизирование по типу медиаконтента (Adaptive Media Buffering):
    * Для музыкальных треков (`.mp3`, `.flac`, `.ogg`, `.m4a` и др.) используется отдельное окно упреждения `AudioPrefetchWindowMb` (по умолчанию 2 МБ, что дает 40–60 секунд запаса звучания без лишнего скачивания всего трека).
    * Для видео и крупных файлов (`.mp4`, `.mkv`, `.avi`, архивы) используется `StreamingPrefetchWindowMb` (по умолчанию 20 МБ, дающее быстрый старт тяжелого видеопотока).
  - При запуске проигрывания или копировании перетягиванием Drag&Drop/Copy-Paste со второго чанка подряд подхватывается фоновый конвейер MTProto, и выводится оверлей `[Download]`.

## 5. Отправка изображений и файлов произвольного формата в Telegram (Root Cause Analysis: почему закачанную картинку нельзя было скачать)

### Бизнес-цель:
Обеспечить надежное сохранение и последующее чтение/скачивание любых файлов (включая изображения `.jpg`, `.png`, `.webp`, `.bmp`, `.gif`) на виртуальном диске WebDAV/WinFsp без потерь качества и сбоев при скачивании.

---

### Симптом:
Пользователь загрузил картинку на диск, файл отобразился в проводнике, но при попытке скачать его или открыть выдавалась ошибка (в логах `FileNotFoundException: Не удалось найти медиа-документ для сообщения ID ... в Telegram`).

---

### Первопричина (Root Cause):
1. **Точка записи (`UploadFileAsync`):** Не-аудио и не-видео файлы отправлялись через `_client.SendMediaAsync(peer, effectiveCaption, inputFile)`.
2. Библиотека `WTelegramClient` внутри `SendMediaAsync` анализирует расширение файла. Увидев расширение изображения, она автоматически конвертирует его в `InputMediaUploadedPhoto` и отправляет в Telegram как сжатую фотографию (`TL.MessageMediaPhoto`), а не как бинарный документ.
3. Telegram пересжимает изображение и сохраняет его в сообщении с типом медиа `TL.MessageMediaPhoto` (с объектом `TL.Photo`).
4. **Точка чтения (`DownloadFileAsync` -> `GetDocumentFromMessageAsync`):** Потоковый ридер ожидал строго `TL.MessageMediaDocument` (`msg.media is TL.MessageMediaDocument mediaDoc && mediaDoc.document is TL.Document doc`). Так как `media` являлось `TL.MessageMediaPhoto`, метод возвращал `null`, приводя к `FileNotFoundException`.
5. Кроме того, отправка как Photo нарушает принцип облачного диска: файл сжимается с потерями, меняется его бинарный размер относительно сохраненного в базе SQLite `node.Size`, и ломается побайтовая целостность.

---

### Принятое решение (Принцип Root Cause First):
* **Отказ от `SendMediaAsync`:** Все файлы (не-аудио и не-видео) теперь отправляются строго как несжатые документы через `_client.SendMessageAsync(peer, effectiveCaption, mediaDoc)` с использованием `TL.InputMediaUploadedDocument` и атрибутом `TL.DocumentAttributeFilename`.
* Добавлен хелпер `GetDocumentMimeType` для явного указания MIME-типа файла.
* Telegram гарантированно сохраняет файлы 1-в-1 без сжатия в виде `TL.MessageMediaDocument`.
* Чтение и скачивание через MTProto (`Upload_GetFile`), параллельные воркеры и RAM-кэш работают штатно и прозрачно для всех форматов файлов.

## 7. Устранение повреждения изображений и файлов при чтении (Root Cause Analysis: дефект частичного первого чанка и докачка остатка в RAM)

### Бизнес-цель:
Обеспечить 100% целостность файлов (включая изображения и видео) при открытии в Проводнике Windows и просмотрщиках фотографий после предварительного зондирования метаданных (AIMP, EXIF probe) без артефактов и без повторного скачивания уже имеющихся в RAM байт.

---

### Симптом:
При открытии изображения в «Средстве просмотра фотографий Windows» верхняя часть картинки отображалась поврежденной (коричневая полоса/смещение строк), либо файл терял первые 768 КБ данных. При этом зондирование метаданных в AIMP работало штатно.

---

### Первопричина (Root Cause):
1. **Зонд метаданных (256 КБ):** При первом запросе файла со смещением 0 или при первичном чтении заголовков срабатывал режим зонда метаданных (`isMetadataProbe = true`), запрашивавший у MTProto первые 256 КБ вместо стандартного 1 МБ чанка. Эти 256 КБ сохранялись в `_chunkMemoryCache` со смещением `0`.
2. **Ложный пропуск сетевого запроса в `MtprotoDownloadWorkerPool`:** 
   Когда файл открывался полностью (просмотрщиком фото или потоковым скачиванием), пул параллельных воркеров при обработке чанка #0 опрашивал кэш через `existingChunkProvider(0)`. Воркер получал массив из 256 КБ и проверял условие `existing != null && existing.Length > 0`. Так как 256 КБ > 0, воркер ошибочно считал чанк #0 **полностью готовым**, отправлял его дальше и переходил к чанку #1 (смещение 1 048 576 байт). Байты с 262 144 по 1 048 576 (768 КБ) выпадали из потока данных.
3. **Преждевременный выход из прямого чтения:** В `TelegramService.DownloadFileAsync` точечное чтение из кэша возвращало данные сразу через `return`, даже если клиент запрашивал 1 МБ, а в кэше лежало только 256 КБ.
4. **Некорректный учет в `NetworkTransferAudit`:** Метод `MarkRangeReceived(0, 262144)` помечал чанк #0 как полностью завершенный, хотя была получена только четверть блока.

---

### Принятое решение (Принцип Root Cause First):
1. **Точечная докачка остатка чанка в `MtprotoDownloadWorkerPool`:**
   - Воркер сравнивает размер имеющихся в RAM байт с ожидаемым размером чанка: `expectedChunkSize = Math.Min(chunk.RequestLimit, totalSize - chunk.ChunkOffset)`.
   - Если `existingBytes.Length == expectedChunkSize`, чанк считается полным, и сетевой запрос пропускается.
   - Если `existingBytes.Length < expectedChunkSize`, воркер **не перекачивает чанк заново**, а выполняет запрос только на недостающий остаток:
     `reqOffset = chunk.ChunkOffset + partialExisting.Length;`
     `reqLimit = chunk.RequestLimit - partialExisting.Length;`
   - После получения ответа воркер бесшовно склеивает массив из RAM и свежеполученный остаток через `Buffer.BlockCopy`, сохраняя полный 1 МБ блок в кэш.
2. **Устранение обрыва чтения в `DownloadFileAsync`:** Ранний возврат из точечного чтения разрешен только если кэш полностью покрывает запрошенную клиентом длину (`bytesToSend == length`). В противном случае чтение продолжается в основном потоковом цикле.
3. **Строгая фиксация полноты в `NetworkTransferAudit`:** Чанк отмечается как завершенный в аудите только если переданный диапазон байт целиком покрывает данный 1 МБ блок (`offset <= chunkStart && endPos >= chunkEnd`).
4. **Сохранение скорости сканирования библиотеки AIMP:** Зонды метаданных по-прежнему читают ровно 256 КБ без избыточного трафика, а при последующем открытии картинки или видео недостающий остаток докачивается автоматически без дыр и артефактов.

---

## 8. Ликвидация конкурирующих пулов выкачки и переход к единому конвейеру поставщик-потребитель (Этап 1 рефакторинга скачивания)

### Бизнес-цель:
Устранить избыточный сетевой трафик (коэффициент 1.25x вместо 1.00x) и коллизии параллельных запросов одних и тех же чанков, возникавшие из-за одновременной работы фонового префетчера и прямого пула воркеров.

---

### Симптом:
В логах при скачивании файла наблюдалось одновременное создание двух пулов воркеров (до 6 воркеров суммарно) и параллельные запросы одних и тех же чанков (например, чанк #0 и чанк #1 запрашивались одновременно двумя разными воркерами из разных пулов), приводя к 25% перерасходу трафика.

---

### Первопричина (Root Cause):
В теле метода `DownloadFileAsync` одновременно вызывались:
1. `TriggerContinuousPrefetch` (создававший фоновый пул `MtprotoDownloadWorkerPool` из 3 воркеров);
2. Прямой вызов `new MtprotoDownloadWorkerPool` (создававший второй независимый пул из 3 воркеров на переднем плане).

Оба пула работали независимо и не согласовывали свои сетевые RPC-запросы.

---

### Принятое решение (Принцип Root Cause First):
1. **Единый конвейер поставщика (Single Producer Pipeline):**
   - Устранен второй экземпляр пула `workerPool` из метода `DownloadFileAsync`.
   - Фоновый `TriggerContinuousPrefetch` стал единственным поставщиком чанков для скачиваемого файла.
2. **WebDAV как чистый потребитель (Consumer):**
   - Потоковый цикл WebDAV в `DownloadFileAsync` ожидает готовности нужного чанка через `_inFlightChunkWaiters` (с поддержкой как 1 МБ блоков, так и 256 КБ зондов) и непрерывно транслирует готовые байты из RAM в сокет клиента.
   - Если префетч не требуется (зонды метаданных или мелкие файлы), данные запрашиваются напрямую под контролем `_downloadRpcSemaphore`.
3. **Синхронная регистрация `_inFlightChunkWaiters` ДО перехода в фон:**
   - Вычисление недостающих чанков и их регистрация в `_inFlightChunkWaiters` теперь выполняется синхронно внутри `TriggerContinuousPrefetch` до передачи задачи в `Task.Run`.
   - Это на 100% исключает гонку, при которой WebDAV-поток не находил зарегистрированный чанк и отправлял дублирующий прямой запрос к MTProto.
4. **Уточнение критериев зонда метаданных (`isMetadataProbe`)**:
   - Зондом считаются только короткие запросы ($\le 256$ КБ) при `SequentialCount < 2`. Чтение тела файла любого размера сразу получает статус нормального потока.
5. **Безусловный вывод итогового аудита (`NetworkTransferAudit`)**:
   - При получении 100% чанков файла (`audit.IsAllChunksReceived()`) отчет `LogCompletionOnce()` выводится в лог **всегда**, независимо от того, в какой зоне файла (голова, середина, хвост) завершилось последнее чтение.
6. **Результат:**
   - Строгая сетевая эффективность 1.00x без дублирования на чанках #1, #6, #11.
   - Гарантированный вывод строки аудита при каждом полном скачивании файла.

## 9. Изоляция точечных сэмплов и эскизов видео в середине файла (Вариант 3)

### Бизнес-цель:
Исключить паразитный сетевой трафик (запуск тяжелого 20 МБ префетча), когда внешнее приложение (генератор превью видео Windows, парсер индексов или единичный Seek) запрашивает малый фрагмент (например, 30 КБ) в середине крупного видеофайла.

---

### Первопричина:
Условие зонда (`isMetadataProbe`) ранее проверяло только начало файла (#0) и последние 2 МБ хвоста. Запрос в середине файла (например, чанк #6) приводил к `isMetadataProbe = false` и немедленному запуску фонового поезда воркеров на 20 МБ вперед, даже если клиенту нужен был всего один кадр (30 КБ) и файл сразу закрывался.

---

### Принятое решение:
1. **Универсальный критерий точечного сэмпла**:
   Любой запрос длиной $\le 256$ КБ при `SequentialCount < 2` классифицируется как точечный зонд / сэмпл (`isMetadataProbe = true`), независимо от его смещения в файле.
2. **Скачивание ровно 1 чанка (1 МБ) без фонового префетча (Вариант 3)**:
   - При точечном запросе в середине файла скачивается ровно 1 целевой чанк (1 МБ) и сохраняется в кэш ОЗУ.
   - Фоновый поезд воркеров на следующие 20 МБ не запускается.
3. **Бесшовный переход к потоковому воспроизведению**:
   - Если клиент продолжает читать данные (`SequentialCount >= 2` или `length > 256 КБ`), система автоматически активирует `TriggerContinuousPrefetch` и разгоняет воркеров для непрерывного стриминга.
4. **Результат**:
   - 0 лишнего трафика при создании эскизов видеокадров.
   - Мгновенный отклик при перемотке (Seek).
   - 100% стабильность и сохранение целостности 1 МБ структуры кэша.

---

## 10. Запуск префетча строго после готовности текущего чанка в ОЗУ (Root Cause Fix)

### Бизнес-цель:
Исключить дублирование скачивания остатка Чанка #0 (768 КБ) при одновременном запросе из WebDAV сокета и фонового пула воркеров MTProto.

---

### Первопричина:
`TriggerContinuousPrefetch` запускался в начале `DownloadFileAsync` до того, как текущий 768 КБ хвост Чанка #0 был скачан и сохранен в RAM. В результате основной поток `DownloadFileAsync` и Воркер #3 префетчера одновременно отправляли в Telegram запрос на один и тот же хвост чанка #0 (со смещения 262 144).

---

### Принятое решение:
1. **Склейка зонда и хвоста в цельный 1 МБ блок**:
   При получении хвоста чанка (со смещения 262 144) он автоматически склеивается в памяти с ранее полученным 256 КБ зондом головы в единый массив `1 048 576 байт` с ключом `{messageId}:0:1048576`.
2. **Перенос вызова `TriggerContinuousPrefetch`**:
   Префетч запускается **строго после** того, как текущий блок успешно скачан, склеен и отдан клиенту.
3. **Результат**:
   Когда префетчер начинает работу, Чанк #0 уже на 100% готов в RAM, поэтому очередь `missingChunks` формируется строго начиная с **Чанка #1** (`#1, #2, #3...`). Дублирование исключено на 100%.

---

## 11. Каноническое хранилище чанков в ОЗУ и склейка в точке записи (`StoreChunkInMemoryCache`)

### Бизнес-цель:
Гарантировать полное отсутствие фрагментации и старых огрызков в `_chunkMemoryCache`, чтобы любой метод (`TryGetFromMemoryCache`, префетчер, WebDAV сокет) всегда мгновенно и детерминированно получал единственный актуальный 1 МБ блок.

---

### Первопричина:
Ранее при склейке 1 МБ блока старый ключ зонда `{messageId}:0:262144` оставался в словаре `_chunkMemoryCache`. Поскольку `_chunkMemoryCache` перебирался в цикле `foreach`, метод `TryGetFromMemoryCache` натыкался на старый огрызок 256 КБ первым, возвращал его префетчеру, и префетчер считал, что Чанк #0 не скачан.

---

### Принятое решение (Принцип Root Cause at Write):
1. **Метод `StoreChunkInMemoryCache`**:
   - Любая запись в ОЗУ (и из `DownloadFileAsync`, и из `TriggerContinuousPrefetch`) теперь проходит через единую точку `StoreChunkInMemoryCache`.
2. **Склейка на лету с удалением старых ключей**:
   - При получении хвоста (768 КБ) старый зонд `{messageId}:0:262144` атомарно извлекается через `TryRemove`.
   - Зонд и хвост склеиваются в цельный `byte[1048576]`.
   - В ОЗУ сохраняется **только** `{messageId}:0:1048576`. Промежуточный ключ хвоста `{messageId}:262144:768432` не создается вообще.
   - Любые другие частичные ключи этого же мегабайта зачищаются.
3. **Результат**:
   - В словаре ОЗУ для каждого мегабайта существует **ровно один канонический блок**.
   - `TryGetFromMemoryCache` всегда возвращает полный 1 МБ блок.
   - Префетчер видит 100% готовность Чанка #0 и запускает воркеров строго с **Чанка #1**.

---

## 12. Устранение зацикливания при чтении превью видео и синхронизация кванта MTProto

### Проблема:
При открытии в Проводнике папки с видеофайлами без готового превью система впадала в бесконечный цикл запросов к Telegram MTProto (до 12 запросов в секунду), непрерывно перезапрашивая один и тот же чанк (например, Чанк #3 со смещением 3 145 728 и размером 512 КБ).

### Первопричина (Root Cause):
1. Windows Shell / Media Foundation при попытке сгенерировать миниатюру видео делает Seek в середину файла (например, на смещение 3.5 МБ = 3 670 016).
2. Логика `TelegramService.cs` классифицировала это как `isIsolatedMiddleProbe` и вычисляла `baseChunkSize = 512 КБ`.
3. Однако переменная `use256kQuantum` включалась только для головы и хвоста (`isHeadOrTailProbe`). Из-за этого `chunkAlignment` остался равным 1 МБ (1 048 576).
4. Смещение `chunkOffset` выровнялось на 3 145 728 (начало 1 МБ), а `requestLimit` составил 512 КБ.
5. Telegram вернул байты от 3.0 до 3.5 МБ (3 145 728 .. 3 670 015).
6. Внутри цикла `internalOffset` (3 670 016 - 3 145 728 = 524 288) оказался $\ge$ длине полученных данных `raw.Length` (524 288). Срабатывал `break;`, клиенту отдавалось 0 байт, и Проводник мгновенно повторял запрос на то же самое смещение.

### Принятое решение:
1. **Синхронизация кванта и выравнивания (`use256kQuantum = isSmallFile || isMetadataProbe`)**:
   Для любых метаданных и точечных зондов (`isMetadataProbe`) квант и выравнивание строго зафиксированы на **256 КБ (262 144 байта)**. При скачивании или последовательном воспроизведении (`SequentialCount >= 2`) — строго **1 МБ**.
2. **Удаление несогласованной эвристики `bytesToMegaEnd`**:
   Устранено искусственное урезание размера до 512 КБ без соответствующего сдвига `chunkOffset`.
3. **Корректная очистка в `StoreChunkInMemoryCache`**:
   Удаление фрагментов производится только при записи полного 1 МБ блока, предотвращая взаимное вытеснение непересекающихся 256 КБ кусочков.
4. **Предотвращение бесконечного цикла**:
   Добавлено предупреждающее логирование при аномальном `internalOffset >= raw.Length`.

---

## 13. Предотвращение ложного срабатывания префетча на стыках мегабайтных блоков (Вариант А)

### Проблема:
Если ключевой кадр видео для превью оказывается на границе 1 МБ блоков (например, в конце 5-го мегабайта на смещении `6 029 312` и продолжается в начале 6-го на `6 291 456`), переход `5 -> 6` увеличивал `SequentialCount` до 2. Это ложно расценивалось как воспроизведение файла: включался тяжелый фоновый префетч 3 воркерами на 5 МБ вперед, а повторные мелкие запросы отменяли `CancellationTokenSource`, вызывая спам ошибками `A task was canceled` и `The CancellationTokenSource has been disposed`.

### Первопричина (Root Cause):
1. Порог `SequentialCount >= 2` был слишком чувствительным: любой кадр или заголовок (100–300 КБ), лежащий на стыке двух мегабайт, давал один переход `N -> N+1`.
2. Метод `TriggerContinuousPrefetch` при каждом вызове безоговорочно отменял `oldCts.Cancel()` предыдущего активного конвейера, приводя к коллизиям и отменам задач в сокетах.

### Принятое решение (Вариант А):
1. **Повышение порога последовательности (`SequentialCount >= 3` или `AccumulatedSequentialBytes >= 1.5 МБ`)**:
   Одиночный шаг через стык мегабайтов при коротких чтениях (`length <= 256 КБ`) сохраняет статус `isMetadataProbe = true` и квант 256 КБ. Переключение на 1 МБ и запуск префетча происходят только при устойчивом длительном чтении.
2. **Исключение дергания префетчера**:
   В `TriggerContinuousPrefetch` добавлена проверка: если для файла уже работает активный конвейер (`!existingCts.IsCancellationRequested`), повторные вызовы не прерывают его работу, позволяя воркерам спокойно завершать скачивание.

## 14. Предотвращение ложного повторного показа оверлея «МЕТАДАННЫЕ ПОЛУЧЕНЫ»

### Проблема:
При воспроизведении видеофайла онлайн плеер считывает первые 1.5 МБ порциями по 64 КБ с паузами 1.5–1.6 сек (декодирование кадров). В этот период в правом нижнем углу экрана каждые 1.5 секунды повторно всплывало окно оверлея с плашкой «МЕТАДАННЫЕ ПОЛУЧЕНЫ».

### Первопричина (Root Cause):
1. В `TelegramService.cs` событие `OnMetadataCompleted` вызывалось строго один раз благодаря атомарному `audit.LogMetadataCompletedOnce()`.
2. Однако в `TrayProgressOverlay.cs` внутри таймера `HideCheckTimer_Tick` (проверка неактивности > 1.5 сек) при `_isMetadata == true` стоял вызов `CompleteMetadata(_currentFileName)`.
3. Каждое чтение плеера обновляло `UpdateMetadataProgress` (`_isTransferring = true; _isMetadata = true;`).
4. При паузе 1.5 сек таймер оверлея ошибочно расценивал это как «сбор метаданных завершился» и сам принудительно открывал оверлей через `CompleteMetadata()`, вызывая мерцание окна 4–5 раз подряд.

### Принятое решение:
1. **Удаление вызова `CompleteMetadata` из таймера неактивности**:
   При паузе более 1.5 сек оверлей тихо скрывается (`Hide()`), не генерируя фейковых событий завершения.
2. **Защитный барьер `_lastMetadataCompletedFile`**:
   Метод `CompleteMetadata(fileName)` игнорирует повторные вызовы для того же файла. Сброс флага происходит только при открытии нового файла (`_currentFileName != fileName`). Плашка «МЕТАДАННЫЕ ПОЛУЧЕНЫ» гарантированно всплывает строго 1 раз.

## 15. Устранение ложного всплывания оверлея «СКАЧИВАНИЕ ИЗ TELEGRAM» при воспроизведении из RAM

### Проблема:
После того как файл полностью скачан по сети в ОЗУ (100% чанков получено, Wi-Fi 0 кбит/с, оверлей сообщил о завершении и скрылся), во время дальнейшего воспроизведения плеером каждые несколько секунд повторно всплывало окно «СКАЧИВАНИЕ ИЗ TELEGRAM» со скоростью чтения плеера (например, 97,8 КБ/с).

2. **Проверка полноты загрузки `!audit.IsAllChunksReceived()`**:
   Сетевой прогресс отправляется только до тех пор, пока файл физически не получен на 100%.
3. **Защита в UI (`TrayProgressOverlay.cs`)**:
   Если для текущего файла передача уже перешла в статус `_isCompleted == true`, любые запоздалые сетевые обновления для него игнорируются, исключая повторное открытие окна.

## 16. Устранение повреждения фото-превью (битые пиксели в углу и сплошная заливка цветом)

### Проблема:
При отправке фотографий в Telegram через виртуальный диск генерируемое легковесное превью (`tg_preview_message_id`) отображалось как сплошная заливка цветом с несколькими битыми пикселями в левом верхнем углу при максимальном увеличении.

### Первопричина (Root Cause):
1. **Конфликт ленивого чтения GDI+ и перемещения потока (`Image.FromStream`)**:
   В `CreateOptimizedGalleryThumbnail` объект `System.Drawing.Image.FromStream(stream)` создавался напрямую из `uploadStream`, после чего сразу вызывался `stream.Seek(origin, SeekOrigin.Begin)` для перемотки потока назад. Поскольку GDI+ читает пиксели лениво при вызове `DrawImage`, сдвиг потока приводил к тому, что декодер JPEG читал с 0-го байта заголовки EXIF вместо сжатых данных картинки. Декодер считывал несколько мусорных байт (битые пиксели в левом верхнем углу), натыкался на ошибку и аварийно прекращал декодирование, оставляя 99.9% растра пустой фоновой заливкой.
2. **Искажение масштаба из-за DPI**:
   Вызов `g.DrawImage(originalBmp, 0, 0, newW, newH)` без явного указания `GraphicsUnit.Pixel` масштабировал изображение исходя из DPI (у фото с телефонов часто 300+ DPI против 96 DPI холста).
3. **Опечатка в получении энкодера**:
   `GetEncoder` опрашивал `ImageCodecInfo.GetImageDecoders()` вместо `GetImageEncoders()`.

### Принятое решение (Шаг 1):
1. **Изоляция потока**:
   Перед созданием `Image` данные потока копируются в полностью изолированный локальный `MemoryStream`, что исключает любое влияние внешних операций `Seek` на ленивый декодер GDI+.
2. **Пиксельная точность `DrawImage`**:
   Использована перегрузка `g.DrawImage(originalBmp, new Rectangle(0, 0, newW, newH), 0, 0, origW, origH, GraphicsUnit.Pixel)` с точными координатами в пикселях.
3. **Корректный опрос энкодеров**:
   `GetEncoder` переведён на `ImageCodecInfo.GetImageEncoders()`.

### Развитие решения (Шаг 2):
1. **Именование превью**:
   Вместо статичного `"photo.jpg"` при вызове `UploadFileAsync` формируется осмысленное имя с суффиксом `_preview.jpg`:
   `previewFileName = $"{Path.GetFileNameWithoutExtension(effectiveFileName)}_preview.jpg"`. При сохранении превью из клиента Telegram Desktop пользователю предлагается родное имя файла (например, `Море_2024_preview.jpg`).
2. **Встраивание миниатюры (`thumb`) в оригинальный документ при размере > 10 МБ**:
   Для файлов $\le 10$ МБ Telegram автоматически строит превью документа на сервере без дополнительных запросов. Для больших файлов ($> 10$ МБ), где серверный процессинг Telegram отключён, эскиз `galleryPhotoBytes` дополнительно загружается и прикрепляется к оригинальному документу (`mediaDoc.thumb = thumbFile; mediaDoc.flags |= has_thumb;`). Это гарантирует отображение обложки в Telegram-чате для файлов любого размера.

### Устранение ошибки закрытого потока (Шаг 3):
- **Проблема**: `WTelegramClient.UploadFileAsync(uploadStream, ...)` автоматически диспоузит переданный поток `uploadStream` после завершения выгрузки байтов. Последующее обращение `uploadStream.Length > 10 * 1024 * 1024` выбрасывало `ObjectDisposedException: Cannot access a closed file`, прерывая отправку документа-оригинала.
- **Исправление**: Длина `long fileLength = uploadStream.Length;` фиксируется до вызова `UploadFileAsync`, полностью предотвращая падение при проверке порога 10 МБ.

## 11. Сохранение оригинальных системных дат файлов (CreationTime / LastWriteTime) в драйвере WinFsp

### Бизнес-цель:
При копировании файлов с локального накопителя (например, `D:\Music\Track.mp3`) на виртуальный диск `Y:` через Проводник Windows должны сохраняться точные исторические даты создания и изменения исходного файла (например, 2023 год), а не подставляться текущая дата и время выгрузки в Telegram.

### Симптом:
У скопированного на виртуальный диск файла даты «Создан» и «Изменен» устанавливались на момент копирования и завершения загрузки в Telegram.

### Первопричина (Root Cause Analysis):
1. **Игнорирование `creationTime` в `SetBasicInfo`**: Метод `SetBasicInfo` в `WinFspServer.cs` считывал только `lastWriteTime`, пропуская `creationTime`.
2. **Отсутствие записи дат в SQLite**: В `SetBasicInfo` новые даты не передавались в базу данных через `_repository.UpdateNodeTimestamps(node.Id, ...)`.
3. **Затирание дат в `Cleanup`**: При финализации отправки файла в Telegram метод `Cleanup` вызывал `CreateOrUpdateFile` без передачи сохранённых таймстампов (SQLite выставлял `CURRENT_TIMESTAMP`), а затем строка `node.UpdatedAt = DateTime.UtcNow;` принудительно затирала дату изменения текущим моментом.

### Принятое решение:
1. В `SetBasicInfo` реализовано извлечение и валидация как `lastWriteTime`, так и `creationTime` с немедленным вызовом `_repository.UpdateNodeTimestamps(node.Id, newUpdatedAt, newCreatedAt)`.
2. В `Cleanup` перед запуском асинхронного таска выгрузки фиксируются `targetUpdatedAt = node.UpdatedAt` и `targetCreatedAt = node.CreatedAt`, которые передаются в `CreateOrUpdateFile` и сохраняются в `Node` без принудительной перезаписи на `DateTime.UtcNow`.
3. В `NodeRepository.CreateOrUpdateFile` добавлена поддержка обновления `created_at` наряду с `updated_at` при заполнении 0-байтовых плейсхолдеров от Проводника.

## 17. Гарантированная перманентная очистка файлов из Telegram (Transactional Deletion Queue / Outbox Pattern)

### Проблема:
При удалении папок и файлов из корзины `.Trash` через виртуальный диск WinFsp в Telegram ничего не удалялось (сообщения оставались в канале-хранилище, а в логах Telegram была тишина).

### Первопричина (Root Cause Analysis):
1. **Отсутствие перманентного удаления в драйвере WinFsp**:
   В методе `WinFspServer.Cleanup` при удалении вызывался исключительно `_repository.SoftDeleteNode(node.Id)`. В коде вообще отсутствовала проверка нахождения в корзине (`node.IsDeleted` или `IsNodeInTrash`), вызов `_telegramService.DeleteFilesFromTelegramAsync` и физическое удаление `_repository.PermanentDeleteNodes`.
2. **Паразитное удаление родительской папки без дочерних файлов**:
   Когда `SoftDeleteNode` вызывался для элемента, который уже лежал в `.Trash`, SQL-запрос `SELECT id FROM nodes WHERE parent_id = @parentId AND name = @name AND is_dir = 1 AND is_deleted = 1` находил саму эту папку. В итоге выполнялся `DELETE FROM nodes WHERE id = @nodeId` только для самой папки, оставляя все её вложенные файлы сиротами (`orphans`) в SQLite и нетронутыми в канале Telegram.
3. **Отсутствие защиты `.Trash` в WinFsp `CanDelete`**:
   Системная папка `.Trash` не проверялась на запрет удаления, что позволяло Проводнику попытаться удалить саму корзину.

### Архитектурное решение (Transactional Deletion Queue):
1. **Атомарная транзакция в SQLite (Outbox Pattern)**:
   - Создана таблица `pending_deletions (id, tg_message_id, created_at)`.
   - Метод `_repository.EnqueuePermanentDeletion(tgMessageIds, dbNodeIds)` в единой транзакции переносит все `tg_message_id` и `tg_preview_message_id` в очередь `pending_deletions` и физически удаляет записи из таблицы `nodes`.
   - Для Проводника Windows и файловой системы операция завершается мгновенно (1 мс) без блокировок интерфейса.
2. **Фоновый воркер `ProcessDeletionQueueAsync` в `TelegramService` (Event-Driven)**:
   - Полностью исключен холостой опрос базы данных SQLite: при пустой очереди воркер находится в глубоком сне (`_deletionSignal.WaitAsync(token)` без таймаута, 0% нагрузки на CPU и диск).
   - Просыпается только по событиям:
     - При помещении в очередь любого нового удаления (`TriggerDeletionQueueProcessing()`).
     - При запуске приложения и успешном подключении к Telegram (прогрев и подхват зависших задач прошлых сессий).
   - При сбое сети или `FLOOD_WAIT` воркер повторяет попытки только до тех пор, пока в таблице `pending_deletions` остаются не удаленные записи. Как только последний пакет отправлен — немедленно засыпает.
   - Пакетно удаляет сообщения из Telegram (до 100 за запрос с биссекцией).
   - После подтверждения удаления из Telegram очищает записи из таблицы `pending_deletions`.
   - Записи гарантированно сохраняются в SQLite при выключении ПК, гибернации или обрыве связи и автоматически дочищаются при следующем запуске или удалении.
3. **Рекурсивный сбор дерева (`GetSubtreeNodes`)**:
   - `NodeRepository.GetSubtreeNodes(rootId)` полностью обходит дерево каталога и собирает все вложенные файлы и папки, исключая появление потерянных записей.
4. **Защитные барьеры**:
   - `WinFspServer.CanDelete`: возврат `NT_STATUS_CANNOT_DELETE` при попытке удалить `.Trash`.
   - `NodeRepository.SoftDeleteNode`: guard clause `if (node.IsDeleted || IsNodeInTrash(node.Id)) return;` защищает дерево базы данных от повреждений.
   - Унифицирована логика для обоих протоколов доступа (WinFsp и WebDAV).

Предоставить пользователю возможность самостоятельного тонкого тюнинга баланса между скоростью выкачки (МБ/с) и чувствительностью к серверным лимитам Telegram MTProto (`FLOOD_WAIT`), а также исключить повторный спам запросами при смене треков.

## 19. Восстановление логов [RAM Streaming] префетча и отображение имени файла в запросах MTProto

### Проблема:
После перевода архитектуры на единый постоянный `Singleton MtprotoDownloadWorkerPool` (Этапы 7.27–7.28) из логов пропала привычная строка старта упреждающего конвейера (`[RAM Streaming] Скачивание 5,00 МБ...`), а в логах сетевых запросов чанков воркерами перестало отображаться имя файла, из-за чего было невозможно визуально отслеживать работу префетча и определять принадлежность чанков к конкретному файлу.

### Первопричина:
При слиянии независимых пулов в единый пул воркеров лог старта префетча в `TriggerContinuousPrefetch` был непреднамеренно опущен, а метод `ProcessChunkRequestAsync` в `MtprotoDownloadWorkerPool` логировал только `#request.ChunkIndex/{total}` без подстановки `request.FileName`.

### Принятое решение:
1. **Проверка `IsChunkInFlight` в `MtprotoDownloadWorkerPool`**:
   Метод `IsChunkInFlight(messageId, chunkOffset)` проверяет наличие чанка в активной очереди воркеров. Это предотвращает повторные вызовы лога для чанков, которые уже скачиваются в данный момент.
2. **Восстановление строки старта упреждения в `TriggerContinuousPrefetch`**:
   При постановке в очередь новых чанков вычисляется их точный диапазон (`#first..#last`), общий объем в МБ и выводится историческая запись:
   `[MtprotoWorkerPool] [RAM Streaming] Скачивание {mb:0.00} МБ ({rangeStr} из {totalChunks}) для '{fileName}' через {activeWorkers} воркеров MTProto...`
3. **Идентификация файлов в логах воркеров**:
   В `ProcessChunkRequestAsync` в логи запроса, получения чанков и исчерпания попыток добавлен тег `для '{request.FileName}'`.

## 20. Устранение ложного статуса `[Полный]` и точная калибровка тегов зондов/остатков в `MtprotoWorkerPool`

### Проблема:
При считывании метаданных и тегов (ID3v2 в начале файла и ID3v1 в хвосте файла) воркер логировал запрос как `[Докачка остатка/Зонд]`, а при получении 256 КБ выводил `[Полный]`. Пользователь справедливо обратил внимание, что Чанк #0 имеет размер 1 МБ и скачался только на 25%, поэтому статус `[Полный]` вводил в заблуждение.

### Первопричина:
В `MtprotoDownloadWorkerPool.cs` переменная `expectedChunkSize` инициализировалась значением `request.RequestLimit` (262 144 байт). При получении 262 144 байт условие `receivedLen == expectedChunkSize` выполнялось, из-за чего к строке лога безусловно прикреплялся тег `" [Полный]"`.

### Архитектурное решение (Root Cause Fix):
1. **Калибровка тега запроса (`requestTag`)**:
   - Если запрашивается порция $\le 256$ КБ: `[Зонд 256 КБ]`...
   - Если запрашивается полный мегабайт (1 048 576 байт): `[Полный чанк]`...
2. **Калибровка статуса полученного чанка (`chunkTag`)**:
   - `receivedLen >= 1048576` $\rightarrow$ `[Полный чанк]`.
   - Достигнут реальный конец файла (`ChunkOffset + receivedLen >= FileTotalSize`) $\rightarrow$ точный расчёт остатка до двух знаков: `[Остаток {kb:0.00} КБ]` (например, `[Остаток 59,76 КБ]`).
   - Получен зонд 256 КБ $\rightarrow$ `[Зонд 256 КБ]`.
3. **Человекопонятная 1-based нумерация чанков в логах (`displayChunkIdx = request.ChunkIndex + 1`)**:
   - Во всех логах сетевых запросов воркеров (`Запрос чанка`, `Получен чанк`, ошибки, ретраи), а также в логах префетча (`чанки #first..#last`) и чтения из ОЗУ (`Глобальный Чанк #X`) нумерация переведена на естественную 1-based шкалу (`#1/total .. #total/total`), устраняя психологический диссонанс `#0/total` и мнимое ощущение недокачки на `#N-1/total`.

## 22. Атомарная дедупликация задач воркеров (`Interlocked.CompareExchange`) и защита срочных чанков от отмены

### Проблема:
При переключении пула с 1 на 2 (или 3) активных воркера MTProto сетевой аудит регистрировал двойной трафик (`1.98x`, `1.94x`), а в логах было видно, что Воркер #1 и Воркер #2 одновременно в одну и ту же миллисекунду отправляли одинаковые сетевые запросы `Upload_GetFile` на один и тот же чанк (например, чанк #2/18). Кроме того, начальный чанк #1 иногда получал ошибку «Не удалось получить чанк смещением 0 из пула воркеров».

### Первопричина (Root Cause):
1. **Коллизия очередей при повышении приоритета**:
   Когда чанк предварительно ставился префетчем в `_normalPriorityQueue`, а затем при подходе головки чтения запрашивался со срочным приоритетом (`isHighPriority = true`), метод `EnqueueChunk` добавлял его в `_highPriorityQueue`, не извлекая из обычной очереди (`ConcurrentQueue` не поддерживает произвольное удаление).
   При 2 параллельных воркерах: Воркер #1 вычитывал объект из `_highPriorityQueue`, а Воркер #2 в ту же миллисекунду вычитывал его дубликат из `_normalPriorityQueue`. В итоге оба воркера параллельно шли в сеть и скачивали один и тот же мегабайт дважды!
2. **Ложная отмена срочных чанков**:
   Метод `CancelPendingChunksForFile` при смене смещения чтения перебирал `_normalPriorityQueue` и выставлял `req.IsCancelled = true` всем задачам файла без проверки `IsHighPriority` и факта, что чанк уже взят в работу воркером.

### Архитектурное решение (Чистая единая приоритетная очередь):
Вместо латания симптомов через флаги и условные проверки вокруг двух независимых очередей внедрена единая, математически строгая структура данных под легковесным `_queueLock`:
1. **Единый связный список задач (`LinkedList<ChunkDownloadRequest> _queue`)**:
   Каждая задача скачивания физически представлена в очереди **строго в единственном экземпляре**.
2. **Мгновенный O(1) поиск (`Dictionary<string, LinkedListNode<ChunkDownloadRequest>> _waitingRequests`) и учет активных (`Dictionary<string, ChunkDownloadRequest> _inProgressRequests`)**:
   - `IsChunkInFlight` проверяет наличие ключа в `_waitingRequests` или `_inProgressRequests`.
   - `EnqueueChunk`: если чанк уже качается или ждет в очереди — дублирующая задача не создается.
   - Повышение приоритета: если фоновый чанк понадобился плееру срочно, его нода мгновенно перемещается в группу срочных задач (`_queue.Remove` $\rightarrow$ `_queue.AddBefore(firstNormal, node)`).
3. **Физическое удаление отмененных задач (`CancelPendingChunksForFile`)**:
   При перемотке или смене трека неактуальные фоновые чанки **физически удаляются** из очереди `_queue` и словаря. Воркерам в руки вообще не попадает отмененный мусор.
4. **Чистейший воркерный конвейер без гонок**:
   Воркер просто извлекает первый элемент из головы списка под локом, переносит его в `_inProgressRequests` и идет скачивать в сеть. Полное отсутствие дублей, флагов состояния и гонок конкурентности.
5. **Корректная русская грамматика логов воркеров**:
   - «1 воркер MTProto готов», «2/3/4 воркера MTProto готовы», «5 воркеров MTProto готовы».
   - «через 1/2/3/4 воркера MTProto», «через 5 воркеров MTProto».

## 23. Строгое соблюдение порога активации префетча (`StreamingActivationThresholdMb`) и калибровка окна упреждения

### Проблема:
Настройка интерфейса «Старт упреждения после (МБ)» (по умолчанию 1 МБ) фактически игнорировалась: префетч активировался раньше времени (до завершения первого 1 МБ чанка), а в очередь префетча аудиофайлов ставилось 3 МБ вместо настроенных 2 МБ.

### Первопричина (Root Cause Analysis):
1. **Ложный обход `!isShortRead`**:
   В `TelegramService.cs` условие `!isShortRead` (`length > 256 КБ`) принудительно выставляло `isSequentialPlayback = true` на 0-м байте файла при любом запросе от WebDAV/плеера с крупным диапазоном (например `Range: bytes=0-`), обходя счетчик накопленных байт.
2. **Преждевременный вызов `TriggerContinuousPrefetch`**:
   Метод постановки упреждающих чанков вызывался до фактического получения чанка по сети (`await chunkTask`).
3. **Захват недокачанного текущего чанка в префетч**:
   В `TriggerContinuousPrefetch` сканирование начиналось с текущего чанка (`scanOffset = startChunkOffset`), из-за чего недособранный 1-й чанк попадал в очередь фонового префетча вместе со следующими.

### Архитектурное решение (Root Cause Fix):
1. **Строгая классификация зондов метаданных**:
   Зонд определяется как `isTailProbe || (length <= 262144 && readSeq.AccumulatedSequentialBytes < activationThresholdBytes)`.
2. **Внутренний барьер порога в `TriggerContinuousPrefetch`**:
   В начало метода добавлена проверка `if (seq.AccumulatedSequentialBytes < activationThresholdBytes) return;`. Префетч гарантированно не встает в очередь, пока клиент непрерывно не вычитал заданный объем $N$ МБ (из настройки «Старт упреждения после (МБ)»).
3. **Калибровка окна префетча со следующего чанка**:
   Сканирование начинается строго со следующего чанка (`scanOffset = startChunkOffset + 1048576`), а глубина сканирования строго ограничена `windowBytes`. Для аудио при настройке 2 МБ в очередь ставятся ровно следующие 2 чанка (`#2..#3`).
4. **Универсальная поддержка перемотки (Seek)**:
   При перемотке в середину файла счетчик непрерывных байт сбрасывается в 0, а старая фоновая очередь отменяется. Префетч от новой точки перемотки стартует строго после того, как в ней вычитано `N` МБ.

## 24. Безопасный перехват исходных файлов при Drag-and-Drop через файловые хэндлы ядра (NtQuerySystemInformation) без COM/UI

### Бизнес-цель:
Обеспечить 100% извлечение метаданных (длительность трека, обложки альбомов, стоп-кадры и разрешение видео) при копировании файлов и папок через перетаскивание мышью (Drag-and-Drop) на виртуальный диск WinFsp без создания временных файлов на системном диске C:.

---

### Симптом:
При перетаскивании файла или папки мышкой из Проводника Windows на виртуальный диск в логе появлялось предупреждение:
`[WARN ] [WinFsp] [Буфер обмена] OpenClipboard успешен, но формат CF_HDROP (файлы) отсутствует в буфере обмена (код Win32: 0).`
`[WARN ] [WinFsp] [Write] Исходный путь НЕ найден в буфере обмена Windows.`
В результате для аудиофайлов длительность выставлялась в `0 сек`, а для видеофайлов не извлекались превью и габариты.

---

### Первопричина (Root Cause Analysis):
1. **Разделение подсистем Clipboard и OLE Drag-and-Drop в Windows**:
   - Буфер обмена (`OpenClipboard` / `CF_HDROP`) задействуется исключительно при операциях `Ctrl+C` / `Ctrl+V` (Copy-Paste) или через контекстное меню.
   - При перетаскивании мышью (Drag-and-Drop) Проводник использует OLE-интерфейсы `IDataObject` и `IDropTarget` напрямую между процессами окон. Буфер обмена Windows при этом остаётся абсолютно пустым.
2. Метод `TryFindSourceFileFromClipboard` искал оригиналы только в буфере обмена, из-за чего для любых перетаскиваемых файлов путь `OriginalSourcePath` оказывался `null`.

---

### Принятое решение (Принцип Root Cause First):
1. **Инспекция открытых окон Windows Shell (`IShellWindows`)**:
   - Через системный COM-интерфейс `CLSID_ShellWindows` (`{9BA05972-F6A8-11CF-A442-00A0C90A8F39}`) опрашиваются все активные окна Проводника (`explorer.exe`).
   - Считываются выделенные пользователем файлы и папки (`SelectedItems`), которые при перетаскивании остаются в состоянии выделения в окне-источнике.
   - Также считывается путь самой папки окна (`Folder.Self.Path`).
2. **Поддержка Рабочего стола Windows**:
   - В пул источников добавлены системные пути Рабочего стола (`SpecialFolder.Desktop` и общесистемный Desktop).
3. **Честная пофайловая модель сессии (`CopySession`, Zero Timers)**:
   - Полный отказ от любых таймеров и эвристик времени.
   - Фиксируется точный состав файлов пачки (`PendingFiles`) и каталоги источников (`SourceRoots`).
   - По мере поступления файлов на виртуальный диск они вычеркиваются из сессии.
   - Когда все файлы обработаны (`PendingFiles.Count == 0`), сессия автоматически завершается.
   - При копировании файлов вне активной сессии (или из другой папки) мгновенно запрашивается и создается новая независимая сессия.
4. **Универсальный метод `TryFindSourceFile`**:
   - Объединяет опрос активных окон Проводника (`IShellWindows`), системный буфер обмена (`CF_HDROP`) и Рабочий стол с последующей верификацией через `CheckCandidate` и `VerifyReadable`.
5. **Результат**:
   - При перетаскивании файлов и папок через Drag-and-Drop оригинальные пути мгновенно обнаруживаются на диске-источнике.
   - ATL.NET и Media Foundation честно извлекают длительность, теги и обложки, гарантируя передачу в Telegram без временных файлов на диске C:.











## 25. Мгновенный выход при первом совпадении хэндла в CollectExplorerOpenFileHandles (Fast-Break)

### Проблема:
При перетаскивании пачки файлов опрос дескрипторов ядра успешно находил целевой файл-источник (`Addison Rae - Obsessed.m4a`), однако цикл `for` продолжал перебор оставшихся тысяч системных хэндлов Explorer (системные библиотеки, кэши иконок, именованные каналы). Один из системных дескрипторов Windows мог блокировать системный вызов `GetFinalPathNameByHandle`, из-за чего поток WinFsp зависал на отметке 0% копирования.

Как только целевой файл `targetFileName` обнаружен и проверен на существование, метод `CollectExplorerOpenFileHandles` мгновенно прерывает цикл (`return results`), не трогая посторонние дескрипторы операционной системы.

## 26. Фильтрация дескрипторов ядра по ObjectTypeIndex для предотвращения Kernel IRP Deadlock

### Первопричина зависания процесса (Root Cause):
Среди тысяч дескрипторов процесса `explorer.exe` присутствуют синхронные именованные каналы (Named Pipes), почтовые ящики (Mailslots) и RPC-сокеты. При вызове `DuplicateHandle` и последующем `GetFileType` или `GetFinalPathNameByHandle` для блокирующего канала Windows отправляет синхронный запрос в драйвер устройства (`IRP_MJ_QUERY_INFORMATION`). Если канал ждет данных, поток засыпает в ядре в состоянии `Kernel Executive Wait` намертво. В таком состоянии процесс невозможно снять даже через диспетчер задач («Отказано в доступе»).

### Решение (Root Cause Fix):
1. Метод `GetFileObjectTypeIndex()` один раз динамически определяет системный индекс типа `File` в ядре NT для текущей версии Windows.
2. В цикле перебора дескрипторов `SYSTEM_HANDLE_TABLE_ENTRY_INFO_EX` выполняется мгновенная проверка `objectTypeIndex == fileTypeIndex`.
3. Все дескрипторы не-файловых типов (пайпы, сокеты, порты ALPC, мьютексы) отсекаются в памяти до вызова `DuplicateHandle`. `DuplicateHandle` вызывается строго и исключительно для дисковых файлов.

## 27. Изоляция системного вызова GetFinalPathNameByHandle с таймаутом и Multi-Folder Session Caching

### Проблема:
При перетаскивании пачек файлов опрос дескрипторов ядра успешно находил файлы, но на некоторых дескрипторах вызов ядра `GetFinalPathNameByHandle` блокировался без возврата управления, вызывая зависание I/O потока. Кроме того, при копировании нескольких папок или файлов из разных мест сессия очищалась после первого же файла, вынуждая сканировать дескрипторы заново для каждого файла.

### Решение (Root Cause Fix):
1. **Изоляция с таймаутом (GetPathWithTimeout)**: Системный вызов `GetFinalPathNameByHandle` выполняется в выделенном потоке с жестким таймаутом 50 мс. Если ядро заблокировано на чужом дескрипторе, поток отбрасывается по таймауту, и основной поток драйвера WinFsp продолжает работу без зависания.
2. **Накопительный кэш корней (Multi-Folder Support)**: При нахождении нового источника его родительская папка регистрируется в списке `SourceRoots` активной сессии. Все последующие файлы из этой и других открытых папок мгновенно находятся за 0 мс через проверку прямого пути, не требуя повторного сканирования тысяч хэндлов ядра.

## 28. Синхронное завершение операций записи (Synchronous Cleanup) для нативного диалога копирования Windows

### Проблема:
При завершении передачи файла в методе `Cleanup` файлового драйвера WinFsp финализация и регистрация сообщения в Telegram выполнялись в фоновом потоке (`_ = Task.Run(...)`). Из-за этого драйвер мгновенно возвращал Windows статус `STATUS_SUCCESS` ещё до фактического завершения передачи, и Проводник Windows закрывал свою операцию за доли секунды, не успевая показать стандартное окно копирования Windows с графиком скорости, процентов и кнопкой «Отмена».

### Решение (Root Cause Fix):
1. **Синхронный `Cleanup`**: Завершение записи (`pipe.CompleteWriting()`) и ожидание ответа Telegram (`uploadResult = uploadTask.GetAwaiter().GetResult()`) выполняются непосредственно в контексте файловой операции драйвера WinFsp.
2. **Нативное окно Windows**: Проводник Windows держит стандартный диалог копирования с живым графиком скорости и прогресс-баром на протяжении всего времени передачи данных в Telegram.
3. **Стабильность оверлея в трее**: Таймаут неактивности оверлея увеличен до 4–12 секунд на этапе финализации RPC в Telegram, что исключает моргание и ложное скрытие интерфейса при сетевых задержках Telegram.
4. **Увеличение буфера кольцевой очереди**: Емкость чанков в `StreamingPipeStream` увеличена до 64 шт (~4–8 МБ) для сглаживания микрорывков скорости.

## 29. Точный 512 КБ лимит буфера памяти в StreamingPipeStream (Active Backpressure)

### Проблема:
При буфере емкостью 64 чанка (~8–16 МБ) файлы размером до 15 МБ целиком записывались Проводником Windows в память за 20 мс со скоростью 500 МБ/с. Затем Проводник несколько секунд ждал в `Cleanup` закрытия файла без вызовов `Write`, из-за чего встроенный график скорости Windows замирал, а прогресс-бар обновлялся рывками («прыжками») только при закрытии каждого файла.

### Решение (Root Cause Fix):
1. **Жесткий лимит 512 КБ**: Размер буфера в памяти ограничен ровно 512 КБ (размером одной части пакета Telegram MTProto).
2. **Плавный непрерывный график скорости**: Проводник Windows записывает порции данных синхронно со скоростью сетевой отдачи в Telegram. График скорости в окне копирования Windows непрерывно и плавно рисует реальную скорость интернет-канала.
3. **Минимальный расход ОЗУ**: В памяти никогда не накапливаются лишние мегабайты данных.

## 31. Перенос учетных записей и каналов Telegram из appsettings.json в базу данных SQLite (telegram_accounts / telegram_channels)

### Бизнес-цель и первопричина (Root Cause Analysis):
1. **Защита уникальных идентификаторов хранилища**: Файлы в таблице `nodes` жестко связаны с номерами сообщений Telegram (`tg_message_id`), которые уникальны строго внутри конкретного канала (`StorageChannelId`). Если `appsettings.json` будет случайно удален или сброшен к дефолтным значениям, связь с каналом будет утеряна без возможности восстановления.
2. **Изоляция настроек хоста и хранилища**: Системные настройки (буква диска, порт, размер RAM кэша, пути к логам) относятся к конфигурации локальной машины и хранятся в `appsettings.json`. Данные учетной записи (`api_id`, `api_hash`, `phone_number`, `session_path`) и каналов (`channel_id`, `access_hash`, `title`, `is_primary`) относятся к самому хранилищу и должны быть неотделимы от `base.db`.
3. **Задел на поддержку мульти-аккаунтов и мульти-каналов**: В будущем папки на диске (например, `Z:\Music`, `Z:\Photos`) смогут привязываться к отдельным каналам Telegram.

### Архитектурное решение:
1. **Созданы таблицы в `Schema.sql`**:
   - `telegram_accounts`: хранение параметров авторизации Telegram, телефона, пути к сессии и признака активности.
   - `telegram_channels`: хранение пула каналов (`channel_id`, `access_hash`, `title`, `is_primary`, `is_active`) с внешним ключом на аккаунт.
   - `nodes.tg_channel_id`: колонка для точной привязки файла/папки к конкретному каналу хранилища.
2. **Очистка `appsettings.json`**: Секция `Telegram` полностью удалена из `AppSettings.cs`. В конфигурационном файле остаются исключительно системные параметры `Server`, `Database`, `Logging`.
3. **Обновление `TelegramService` и `AuthSettingsForm`**: Все операции чтения и записи профиля Telegram и каналов выполняются напрямую через репозиторий SQLite (`NodeRepository`).

## 32. Расширенное диагностическое логирование поиска и удаления файлов в WinFsp и NodeRepository

### Проблема:
При удалении нескольких файлов из корзины `.Trash` часть файлов пропускалась Проводником Windows с ошибкой «*Не удалось найти этот элемент*». Для точной диагностики поведения Проводника Windows и базы SQLite потребовалось подробное логирование этапов поиска узлов, чтения прав, проверки удаления и очистки хэндлов.

### Решение:
1. **`NodeRepository.GetNodeByPath`**: Добавлено предупреждение `[GetNodeByPath NOT FOUND]` с указанием искомого пути, родительского `parentId` и флага `expectedInTrash`, если узел не найден в базе SQLite.
2. **`WinFspServer.GetSecurityByName` & `Open`**: Добавлено логирование `[GetSecurityByName NOT FOUND]` и `[Open NOT FOUND]`, фиксирующее точные пути, запрашиваемые Проводником Windows.
3. **`WinFspServer.CanDelete` & `SetDelete`**: Добавлено логирование сведений об узле (`ID`, `Name`, `InTrash`) при вызовах проверки прав на удаление и установке флага `DeleteOnClose`.
4. **`WinFspServer.Cleanup` & `ReadDirectoryEntry`**: Добавлено фиксирование флагов закрытия хэндла (`flags`, `DeleteOnClose`) и стартового количества элементов при чтении листинга директорий.

## 33. Детализированное протоколирование цепочки удаления, версионирования и пакетной очистки Telegram

### Бизнес-цель:
Обеспечить 100% прозрачный аудит всех этапов удаления, версионирования и поиска файлов (включая события драйвера WinFsp, сервера WebDAV, репозитория SQLite и сетевого API Telegram), чтобы точно фиксировать причины пропуска или отсутствия файлов без гипотез и фантазий.

### Принятое решение:
1. **Протоколирование ветки поддерева (`WinFspServer` & `WebDavMiddleware`)**:
   При перманентной очистке корзины или удалении директории протоколируется каждый элемент поддерева с выводом `ID`, `Name`, `IsDir`, `InTrash`, `ParentId`, `TgMessageId` и `TgPreviewMessageId`. Добавлено явное предупреждение `[WARN]`, если у файла отсутствует `TgMessageId` в базе данных.
2. **Аудит транзакции удаления в БД (`NodeRepository.EnqueuePermanentDeletion`)**:
   Фиксируется точный список удаляемых ID узлов из таблицы `nodes` и список Telegram Message ID, заносимых в персистентную очередь `pending_deletions`.
3. **Логирование версионирования и перезаписи (`NodeRepository.CreateOrUpdateFile`)**:
   При перезаписи существующего файла протоколируется отправка старой версии в корзину под инкрементированным именем (`_v1`, `_v2`), родительский ID в корзине и связанный `TgMessageId`.
4. **Аудит сетевых запросов удаления Telegram (`TelegramService.DeleteBatchWithBisectAsync`)**:
   Логируются точные массивы Message ID, передаваемые в вызовы Telegram API (`Channels_DeleteMessages` / `Messages_DeleteMessages`), а также результаты алгоритма бинарного деления (биссекции) при сбоях.

## 34. Синхронизация встроенной схемы базы данных (EmbeddedFallbackSchema) и авто-создание таблиц telegram_accounts / telegram_channels

### Проблема:
При первом запуске приложения с чистой базой данных возникала критическая ошибка:
`SQLite Error 1: 'no such table: telegram_accounts'` в методе `TelegramService.ConnectAsync()`.

### Первопричина (Root Cause Analysis):
1. **Рассинхронизация `EmbeddedFallbackSchema`**: В `DatabaseManager.cs` строковая константа `EmbeddedFallbackSchema` содержала устаревшую схему базы без таблиц `telegram_accounts`, `telegram_channels` и колонки `nodes.tg_channel_id`.
2. При запуске исполняемого файла (когда внешний файл `Schema.sql` отсутствовал рядом с бинарником) `DatabaseManager` применял встроенную резервную схему, из-за чего таблицы аккаунтов и каналов физически не создавались.
3. Кроме того, метод `InitializeDatabase()` вызывал `ApplySchema()` только если отсутствовала таблица `nodes`.

### Принятое решение (Root Cause Fix):
1. **Синхронизация `EmbeddedFallbackSchema`**: Таблицы `telegram_accounts`, `telegram_channels` и колонка `nodes.tg_channel_id` добавлены непосредственно в константу `EmbeddedFallbackSchema` в `DatabaseManager.cs`.
2. **Безусловное применение схемы при старте (`ApplySchema`)**: В `InitializeDatabase()` вызов `ApplySchema` выполняется всегда (все инструкции содержат `CREATE TABLE/INDEX IF NOT EXISTS`), гарантируя появление всех необходимых таблиц.
3. **Метод `EnsureSchemaColumns`**: Добавлена автоматическая проверка и создание колонки `tg_channel_id` в таблице `nodes` через `ALTER TABLE nodes ADD COLUMN tg_channel_id INTEGER;` для гарантированной целостности схемы.

## 35. Отказ от реляционного FOREIGN KEY для колонки original_node_id

### Бизнес-цель и первопричина:
В схеме базы данных колонка `original_node_id` содержала реляционное ограничение внешней связи:
`FOREIGN KEY (original_node_id) REFERENCES nodes(id) ON DELETE CASCADE`.
При поштучном удалении версий файла из корзины удаление записи `v1` вызывало автоматическое каскадное стирание версий `v2`, `v3`, `v4`... движком SQLite втайне от C#-кода. Из-за этого C# не успевал занести их `tg_message_id` в очередь `pending_deletions`, а Проводник Windows получал статус `NOT FOUND`.

### Принятое решение:
Из схемы `Schema.sql` и константы `EmbeddedFallbackSchema` в `DatabaseManager.cs` полностью удалена строчка ограничения `FOREIGN KEY (original_node_id)`.
Поле `original_node_id` стало обычным числовым полем (`INTEGER`), служащим простым указателем на ID оригинала. Управление удалением узлов полностью находится в руках C#-кода по их уникальному `id` (`DELETE FROM nodes WHERE id = @id;`), гарантируя 100% занесение всех сообщений Telegram в очередь очистки.

## 36. Полный отказ от автоматического каскада ON DELETE CASCADE в схеме БД и явный сбор версий в C#

### Бизнес-цель и первопричина:
В `Schema.sql` и `DatabaseManager.cs` для внешних ключей `parent_id` и `node_id` содержалось автоматическое правило `ON DELETE CASCADE`. При удалении родительского элемента движок SQLite стирал все дочерние файлы и подпапки каскадом прямо внутри SQL-запроса, из-за чего C#-код не успевал извлечь их `tg_message_id` и занести в `pending_deletions`. Файлы оставались в Telegram, а Проводник выдавал ошибку.

### Принятое решение:
1. **Удаление `ON DELETE CASCADE` из схемы**: Из `Schema.sql` и `EmbeddedFallbackSchema` убраны директивы `ON DELETE CASCADE` для `parent_id` и `node_id`. Теперь SQLite никогда не удаляет дочерние записи автоматически втайне от приложения.
2. **Явный сбор всех версий в C# (`CollectAssociatedVersions`)**: Метод `GetSubtreeNodes` в `NodeRepository.cs` расширен для рекурсивного сбора не только дочерних папок, но и всех связанных версий файлов (`original_node_id`). Все их `tg_message_id` гарантированно вносятся в `pending_deletions` до выполнения `DELETE FROM nodes`.

## 37. Ограничение сбора ассоциированных версий (`CollectAssociatedVersions`) только вызовами удаления директорий

### Бизнес-цель и первопричина:
При удалении одной конкретной версии файла из Корзины метод `GetSubtreeNodes` вызывал `CollectAssociatedVersions` без проверки типа узла. Из-за этого при удалении версии 5 метод собирал и удалял также версии 1, 2, 3, 4.

### Принятое решение:
Вызов `CollectAssociatedVersions` перенесен строго внутрь блока `if (rootNode.IsDir)`. При перманентном удалении конкретного файла (`is_dir == 0`) стирается строго только этот запрашиваемый файл/версия. Посторонние версии не затрагиваются. При удалении всей папки (`is_dir == 1`) папка вычищается целиком со всеми вложенными файлами и их версиями.

## 38. Архитектурная очистка: полная ликвидация суррогатного обхода версий (CollectAssociatedVersions) и разделение иерархии папок и версий

### Бизнес-цель и первопричина:
Метод `CollectAssociatedVersions` смешивал две разные концепции: иерархию владения файловой системы (`parent_id`) и временную историю изменений (`original_node_id`). Попытка связывать удаление папок с версиями создавала риск утечки удаления на живые файлы основного диска (`id = @origId`).

### Принятое решение:
1. **Полное удаление `CollectAssociatedVersions`**: Метод целиком удален из `NodeRepository.cs`. Метод `GetSubtreeNodes` возвращает строго физическое поддерево папки (или один узел для файла) без блуждания по истории версий.
2. **Гарантия порядка «Сначала файлы, потом папки»**: В `WinFspServer.cs` и `WebDavMiddleware.cs` при перманентном удалении поддерева узлы явно сортируются (`OrderBy(n => n.IsDir ? 1 : 0)`), благодаря чему из базы сначала удаляются все файлы, а освободившиеся пустые папки стираются последними.
3. **Изоляция удаления версий**: Удаление архивного файла в Корзине затрагивает исключительно этот файл и его `tg_message_id`, не влияя ни на рабочий файл на основном диске, ни на другие версии.





## 39. Опция автоматического VACUUM при очистке Корзины и стабилизация фоновой очереди подписей (FloodWait)

### Бизнес-цель и первопричина:
1. При интенсивном удалении файлов или тестировании очистки Корзины фиксированный вызов _repository.ScheduleVacuum(3000) вызывал пересборку базы SQLite каждые 3 секунды. Для пользователей с большими базами данных частый VACUUM может вызывать кратковременные микрофризы дискового ввода-вывода.
2. В TelegramService.UpdateMessageCaptionAsync блок catch (Exception ex) логировал предупреждение и глушил исключение без проброса. В результате воркер фоновой очереди ProcessCaptionQueueAsync не получал TL.RpcException с кодом 420 (FLOOD_WAIT), глобальный таймер _globalFloodWaitUntil не взводился, а при возникновении неустранимой ошибки (например, MESSAGE_ID_INVALID) элемент вызывал сбои.

### Принятое решение:
1. **Настройка AutoVacuumOnTrashDelete**:
   - В AppSettings.DatabaseSettings добавлено свойство AutoVacuumOnTrashDelete (по умолчанию true).
   - В AuthSettingsForm.cs добавлен чекбокс «Автоматически сжимать базу (VACUUM) при очистке корзины» в блоке базы данных вкладки «Общие».
   - В WinFspServer.cs и WebDavMiddleware.cs вызов ScheduleVacuum(3000) теперь выполняется только если опция включена в настройках.
2. **Прозрачная обработка FLOOD_WAIT и ошибок в очереди подписей**:
   - В TelegramService.UpdateMessageCaptionAsync добавлен перехват TL.RpcException (Code == 420) с вызовом TriggerGlobalFloodWait(rpcEx.X) и последующим throw, чтобы воркер ProcessCaptionQueueAsync корректно уходил в паузу на запрошенное Telegram время.
   - Неустранимые ошибки (код 400: MESSAGE_ID_INVALID, CHAT_ADMIN_REQUIRED) логируются, а в ProcessCaptionQueueAsync перехватываются с удалением проблемной записи из pending_caption_updates, предотвращая зависание очереди.

## 40. Расширение глобального пейсинга (PacingDelayMs) на фоновые сервисные операции Telegram

### Бизнес-цель и первопричина:
Пользовательская настройка «Задержка между запросами (мс)» (`PacingDelayMs`, по умолчанию 180 мс) ранее применялась исключительно в пуле воркеров скачивания файлов (`MtprotoDownloadWorkerPool`). При этом фоновые операции обновления подписей сообщений использовали захардкоженную паузу 120 мс, а операции пакетного удаления сообщений при очистке корзины вызывались без соблюдения пейсинга между пачками.

### Принятое решение:
1. **Фоновая очередь обновления подписей (`ProcessCaptionQueueAsync`)**:
   Заменен фиксированный `Task.Delay(120)` на вызов глобального темпового регулятора `await EnsurePacingDelayAsync(token)`. Теперь темп переименования/обновления файлов в Telegram синхронизирован с настроенной задержкой и автоматически адаптируется при любых сигналах о флуде.
2. **Фоновое удаление сообщений (`DeleteBatchWithBisectAsync`)**:
   Перед отправкой каждого RPC-запроса на удаление пакета (пачки по 100 сообщений или деления по биссекции) добавлен вызов `await EnsurePacingDelayAsync()`. Это исключает спайковую нагрузку на Telegram API при массовой очистке корзины.
3. Потоковая загрузка файлов (Upload) оставлена без искусственных пауз, чтобы не резать пропускную способность сокета TCP на передаче бинарных чанков.

## 41. Очистка избыточного и отладочного логирования при операциях удаления и навигации

### Бизнес-цель и первопричина:
После всесторонней стабилизации перманентного и мягкого удаления файлов, транзакций SQLite и отказоустойчивой очереди `pending_deletions`, в журнале оставалось большое количество отладочных логов уровня `INFO` и ложных предупреждений `WARN`.
1. Проводник Windows при закрытии удаляемых файлов и проверке несуществующих ресурсов (а также скрытых файлов `desktop.ini`) порождал десятки вызовов `GetNodeByPath` и `GetSecurityByName`, которые логировались как `[WARN] NOT FOUND`, захламляя журнал ложными тревогами.
2. При перманентном удалении директорий в цикле поддерева для каждого отдельного элемента выводился `[INFO]` лог (`[CleanupDelete Subtree]` и `[HandleDeleteAsync Subtree]`), что при удалении сотен файлов создавало чрезмерную нагрузку на дисковый логгер.
3. В методы `EnqueuePermanentDeletion` и `DeleteBatchWithBisectAsync` передавались дампы полных массивов идентификаторов узлов и сообщений через запятую в `[INFO]`.
4. Рутинный листинг директорий (`ReadDirectoryEntry START`) выводился в `[INFO]` на каждое открытие или обновление каталога в Проводнике.

### Принятое решение:
1. **Перевод логов штатного отсутствия файлов в `DEBUG`**:
   - `GetNodeByPath NOT FOUND` в `NodeRepository.cs` переведен из `Warn` в `Debug`.
   - `GetSecurityByName NOT FOUND` в `WinFspServer.cs` переведен из `Warn` в `Debug`.
2. **Очистка поэлементных дампов поддерева**:
   - Поэлементный перебор в `WinFspServer.cs` и `WebDavMiddleware.cs` переведен в `Debug`. Полезный `Warn` сохранен только для критических аномалий (если файл не имеет `TgMessageId`).
   - Итоговые сводки об общем количестве удаленных узлов и сообщений сохранены в `INFO`.
3. **Сокращение дампов списков ID**:
   - Дампы массивов Telegram Message ID и Node ID в `EnqueuePermanentDeletion` переведены в `Debug`.
   - В `TelegramService.DeleteBatchWithBisectAsync` лог `Пакет из {ids.Length} сообщений успешно удален из Telegram.` оставлен лаконичным в `INFO`, а массив ID пишется в `Debug`.
4. **Снижение шума при навигации**:
   - `ReadDirectoryEntry START`, `SetDelete` и `CleanupDelete` переведены в `Debug`.
5. При штатной конфигурации (`EnableInfo = true`, `EnableDebug = false`) журнал стал чистым, легкочитаемым и информативным.

## 43. Персистентная фоновая очередь миграции каналов (pending_channel_migrations) и перенос файлов при MOVE

### Бизнес-цель и первопричина:
1. При перетаскивании файлов или папок через `MOVE` между директориями, привязанными к разным Telegram-каналам, метаданные узла менялись в SQLite, но сообщения в Telegram оставались в канале источника.
2. При привязке крупных папок (1000+ файлов) или перемещении файлов между каналами синхронная пересылка вызывала риск зависания UI, обрыва миграции при перезапуске программы или сбоев из-за лимитов Telegram `FLOOD_WAIT`.

### Принятое решение:
1. **Персистентная таблица `pending_channel_migrations`**:
   - В `Schema.sql` и `EmbeddedFallbackSchema` добавлена таблица `pending_channel_migrations` (`node_id`, `source_channel_id`, `target_channel_id`, `status`).
2. **Фоновый воркер миграции `ProcessChannelMigrationsAsync`**:
   - В `TelegramService` запущен асинхронный воркер, который выборками по 10 файлов берет элементы из очереди, пересылает сообщение и превью галереи с флагом `drop_author = true`, ставит старые Message ID в `pending_deletions`, обновляет `nodes` и ставит новый путь подписи в `pending_caption_updates`.
   - Добавлена прозрачная обработка `FLOOD_WAIT` (автоматическая задержка и возобновление работы с места остановки).
   - Миграция устойчива к закрытию или перезапуску сервиса (все неперенесенные файлы сохраняются в БД и подхватываются при следующем старте).
3. **Автоматический перенос при `MOVE` в `WinFspServer` и `WebDavMiddleware`**:
   - При перемещении файла или пачки файлов между папками с разным `GetEffectiveChannelId` файлы автоматически ставятся в очередь `pending_channel_migrations` и немедленно передаются воркеру на обработку.

### Бизнес-цель и первопричина:
Пользователь запрашивал возможность структурированного хранения файлов на разных каналах Telegram (например, отдельный канал для `Музыка`, `Фото`, `Рок` и т.д.), с сохранением иерархического просмотра через виртуальный диск WebDAV/WinFsp и официальный клиент Telegram, а также с возможностью привязки произвольных папок любого уровня вложенности к отдельным каналам.

### Принятое решение:
1. **Управление каналами в БД (`telegram_channels`) и `TelegramService`**:
   - Реализованы методы создания приватных каналов (`Channels_CreateChannel`), переименования (`Channels_EditTitle`) и удаления (`Channels_DeleteChannel`).
   - Добавлена таблица `telegram_channels` и интеграция с `nodes.tg_channel_id`.
2. **Рекурсивное вычисление унаследованного канала (`GetEffectiveChannelId`)**:
   - При создании новых файлов и подпапок метод `GetEffectiveChannelId(parentId)` поднимается вверх по дереву каталогов к корню и возвращает `tg_channel_id` ближайшего привязанного предка.
3. **Бесшовный механизм миграции и форвардинга (`MigrateSubtreeToChannelAsync`)**:
   - При связывании существующей папки с файлами с новым каналом сообщения (и галерейные фото-превью) пересылаются через RPC `Messages_ForwardMessages` с флагом `Flags.drop_author`.
   - Записи `nodes` обновляются в базе с новыми `tg_message_id`, `tg_preview_message_id` и `tg_channel_id`.
   - Старые Message ID помещаются в очередь `pending_deletions` для асинхронного удаления из прежнего канала, а текстовые подписи путей обновляются через очередь `pending_caption_updates`.
4. **Интеграция с Проводником Windows**:
   - В контекстное меню папок Windows зарегистрирован пункт «Привязать папку к отдельному каналу Telegram» (`--bind-channel "%1"`).
   - В `Program.cs` перехватывается `--bind-channel`, выполняется привязка/миграция поддерева и выводится нативное уведомление.
5. **Автоматическая синхронизация названий и Garbage Collection каналов**:
   - При переименовании привязанной папки отправляется RPC `Channels_EditTitle`.
   - При окончательном удалении папки из корзины выполняется каскадная проверка `HasActiveNodesForChannel`: если в базе не осталось активных узлов с этим `tg_channel_id`, канал автоматически удаляется из Telegram.

## 44. Хронологический порядок миграции по tg_message_id ASC и приоритетная пересылка фото-превью

### Бизнес-цель и первопричина:
1. Алфавитный порядок обхода файловой системы при миграции папок приводил к тому, что отредактированные файлы (новые версии, созданные позже) оказывались разбросанными по середине истории Telegram, а не в конце, нарушая хронологию создания данных.
2. Для фотоснимков с миниатюрой галереи (`tg_preview_message_id`) пересылка документа перед превью приводила к тому, что в новом канале полноразмерный документ публиковался раньше превью, нарушая наглядный вид ленты и фотоальбома.

### Принятое решение:
1. **Сортировка очереди по `tg_message_id ASC`**:
   - В `TelegramService.MigrateSubtreeToChannelAsync`, `WinFspServer.Rename` и `WebDavMiddleware.HandleMoveAsync` все наборы файлов сортируются строго через `OrderBy(n => n.TgMessageId!.Value)`.
   - Это гарантирует перенос файлов в точном соответствии с историческим порядком их загрузки в Telegram.
2. **Приоритет превью над документом**:
   - В воркере `ProcessChannelMigrationsAsync` пересылка `oldPreviewId` выполняется строго ДО вызова пересылки `oldMessageId`.
   - В целевом Telegram-канале превью всегда оказывается первым сообщением, а оригинальный документ — следующим за ним.

## 45. Межпроцессное взаимодействие (IPC) через Named Pipe для команд контекстного меню Explorer

### Бизнес-цель и первопричина:
При вызове пункта контекстного меню Проводника Windows «Привязать папку к отдельному каналу Telegram» Explorer запускал новый отдельный процесс `TelegramWebDAV.exe --bind-channel "%1"`. 
Этот второй процесс пытался самостоятельно инициализировать `TelegramService` и подключиться к файлу сессии `user.session`. Поскольку основной процесс службы уже удерживал монопольную блокировку на `user.session`, второй процесс завершался ошибкой:
`The process cannot access the file 'D:\Temp\TG webDAV\user.session' because it is being used by another process.`

### Принятое решение:
1. **Архитектура Local IPC на базе `NamedPipeServerStream` / `NamedPipeClientStream`**:
   - Создан сервис `IpcService` (`IpcServer` и `IpcClient`), работающий через локальный пайп `TelegramWebDAV_IPC_Pipe`.
   - Основной процесс службы при старте запускает асинхронный слушатель `IpcServer`.
2. **Делегирование исполнения в основной процесс**:
   - При запуске `TelegramWebDAV.exe --bind-channel "%1"` вторичный процесс не трогает сессию Telegram и базу данных напрямую, а через `IpcClient.SendCommandAsync` отправляет команду `"bind-channel"` основному процессу.
   - Основной процесс выполняет `ExecuteBindChannelAsync`, используя свой уже авторизованный `TelegramService` и соединение с SQLite, создавая канал и запуская миграцию.
   - Результат возвращается во вторичный CLI-процесс через пайп, и пользователю выводится стандартное нативное уведомление Windows `MessageBox.Show`. Вторичный процесс моментально завершается.
   - Механизм не требует открытия сетевых TCP-портов и не вызывает предупреждений брандмауэра Windows.

## 46. Сквозная маршрутизация целевого Telegram-канала при прямой загрузке новых файлов (Root Cause Fix)

### Симптом:
При копировании нового файла в привязанную папку (например, `track1.mp3` в `Z:\Музыка`) файл физически отправлялся в основной (Primary) канал Telegram, хотя в базе данных в поле `nodes.tg_channel_id` сохранялся корректный ID нового канала «Музыка».

### Первопричина (Root Cause):
1. **Точка вызова загрузки (`WinFspServer.Write`, `WinFspServer.CleanupAsync`, `WebDavMiddleware.HandlePutAsync`):**
   - Вызывался метод `_telegramService.UploadFileAsync(...)` без указания целевого канала (`targetChannelId`).
2. **Точка отправки сообщения (`TelegramService.UploadFileAsync`):**
   - Метод вызывал `GetStoragePeerAsync()` без параметров, который всегда возвращал закэшированный `_storagePeer` основного канала по умолчанию.
   - В результате бинарные данные и сообщение Telegram уходили в общий основной канал.
3. **Точка фиксации метаданных в БД (`NodeRepository.CreateOrUpdateFile`):**
   - Метод `CreateOrUpdateFile` честно вычислял `GetEffectiveChannelId(parentId)` и прописывал в таблицу `nodes` ID канала `Музыка`.
   - Возникало рассинхронизированное состояние: база данных считала, что файл в канале «Музыка», а физическое сообщение лежало в основном канале. При последующем чтении поиск сообщения по ID в канале «Музыка» мог вызывать сбои.

### Принятое решение (Принцип Root Cause First):
1. **Сквозной параметр `targetChannelId`**:
   - В сигнатуры `UploadFileAsync` и `UploadFileChunkAsync` добавлен параметр `long? targetChannelId = null`.
   - `TelegramService` получает целевой `InputPeer` через `await GetStoragePeerAsync(targetChannelId)`. В случае ошибки `CHANNEL_INVALID` повторный запрос также выполняется с правильным `targetChannelId`.
2. **Вычисление эффективного канала на стороне вызывающих серверов**:
   - В `WinFspServer.cs` (как для прямого стриминга на лету в `Write`, так и для сохранения из памяти в `CleanupAsync`) перед вызовом загрузки определяется `targetChannelId = _nodeRepository.GetEffectiveChannelId(node.ParentId)`.
   - В `WebDavMiddleware.cs` (как для одиночного `PUT`, так и для чанковых докачек) определяется `targetChannelId = repository.GetEffectiveChannelId(parentNode.Id)`.
3. **Отказоустойчивость при чтении и удалении**:
   - В `NodeRepository.cs` добавлен метод `GetChannelIdByTgMessageId(int messageId)` и создан индекс `idx_nodes_tg_message_id`.
   - `GetDocumentFromMessageAsync`, `DownloadFileAsync` и `DeleteFilesFromTelegramAsync` используют явный `channelId` с автоматическим фолбэком на поиск канала по `messageId` в БД, если канал не был передан.
   - Пакетное удаление `DeleteFilesFromTelegramAsync` автоматически группирует удаляемые ID по их каналам.

## 47. Изоляция сборщика мусора каналов (Garbage Collection) в WinFspServer (Root Cause Fix)

### Симптом:
Пользователь удалил все файлы из привязанной папки и очистил корзину. Сама привязанная папка осталась на диске пустой, однако в Telegram связанный с ней канал неожиданно исчез.

### Первопричина (Root Cause):
1. **Преждевременное удаление канала в сборщике мусора (`WinFspServer.Cleanup`):**
   - При перманентном удалении файлов из корзины сборщик каналов перебирал `uniqueChannelIds = sortedSubtree.Where(n => n.IsDir && n.TgChannelId.HasValue).Select(n => n.TgChannelId!.Value)`.
   - В результате канал в Telegram удалялся, даже если сама привязанная папка продолжала жить на виртуальном диске.

### Принятое решение (Принцип Root Cause First):
- **Канал удаляется ТОЛЬКО при перманентном удалении самой привязанной папки (`WinFspServer.cs`):**
  - Условие сбора мусора строго ограничено: канал удаляется только если перманентно удаляемый в корзине узел является самой привязанной папкой (`n.Id == node.Id && n.IsDir`). Очистка содержимого папки больше никогда не затрагивает её канал в Telegram.

## 48. Отказ от скрытого автосоздания каналов в GetStoragePeerAsync (Root Cause First / Чистый отказ вместо скрытых заплаток)

### Проблема попытки компенсирующего решения:
Ранее в `GetStoragePeerAsync` была добавлена логика автоматического создания нового канала и подмены `tg_channel_id` в базе данных на лету в случае, если запрашиваемый канал не найден в диалогах Telegram.

### Почему решение было признано костылем и отменено:
1. **Нарушение ответственности метода чтения:** `GetStoragePeerAsync` — метод получения дескриптора пира. Он не должен совершать деструктивных или созидательных побочных эффектов в Telegram и базе данных (создавать каналы-дубликаты и перезаписывать связи узлов).
2. **Игнорирование воли пользователя:** Если канал был намеренно удален пользователем в Telegram Desktop, приложение не имеет права самовольно плодить новые каналы в аккаунте.
3. **Прямой диагноз:** Если целевой канал недоступен или удален, метод обязан выбрасывать честное исключение `InvalidOperationException($"Целевой канал Telegram ID {specificChannelId.Value} не найден или недоступен.")`, а не маскировать проблему созданием несанкционированных дубликатов.
4. Метод `UpdateNodesChannelId` удален из репозитория как ненужный.

## 49. Очистка шумящих логов и дедупликация навигации по папкам в WinFsp (ReadDirectoryEntry)

### Проблема и симптом:
1. При навигации в Проводнике Windows консоль засорялась повторяющимися сообщениями `[GetNodeByPath NOT FOUND]` и `[GetSecurityByName NOT FOUND]` для системных файлов Windows (`desktop.ini`), что не несет диагностической пользы.
2. При открытии папки Windows Explorer открывает сразу несколько параллельных дескрипторов (UI-дерево, подсчет колонок/метаданных, кэш эскизов), из-за чего строка `ReadDirectoryEntry START` выводилась по 3–5 раз за доли секунды.

### Принятое решение:
1. Шумящие логи поиска отсутствующих системных файлов (`desktop.ini`) полностью устранены из файловой системы и репозитория.
2. В `TelegramWinFspFileSystem.ReadDirectoryEntry` реализовано дедуплицированное логирование навигации уровня INFO (позволяет пользователю видеть смену каталогов и количество элементов в стандартном режиме работы службы), срабатывающее строго при реальной смене папки (`dirNode.Id != _lastListedDirId`) с защитным тайм-окном (500 мс) от дребезга параллельных дескрипторов Explorer:
   `[ReadDirectoryEntry] Навигация в папку '{displayName}' (ID {dirNode.Id}), элементов: {children.Count}`.
3. Повторные параллельные вызовы перечисления для той же папки не спамят консоль.

## 50. Изоляция привязки Telegram-канала к корневой папке и устранение ложного переименования канала при создании подпапок (Root Cause Fix)

### Симптом:
При создании новой подпапки внутри привязанной папки (например, `/муз тест/Новая папка`) и последующем её переименовании в Проводнике (например, в `/муз тест/рок`) служба неожиданно меняла название самого Telegram-канала папки `/муз тест` на `'рок'`.

### Первопричина (Root Cause):
1. **Избыточная запись `tg_channel_id` вложенным каталогам:**
   - В `NodeRepository.CreateFolder`, `EnsureDirectoryPathExists` и `TelegramService.MigrateSubtreeToChannelAsync` всем дочерним подпапкам принудительно записывался `tg_channel_id` родительской привязанной папки.
   - Механизм наследования целевого канала (`GetEffectiveChannelId`) изначально был спроектирован динамическим (поднимается по дереву родителей к корню). Статическое дублирование `tg_channel_id` в строках подпапок стёрло различие между корневой привязанной папкой и её внутренними подпапками.
2. **Ложное срабатывание в `WinFspServer.Rename` и `WebDavMiddleware.HandleMoveAsync`:**
   - Обработчики переименования проверяли лишь `node.TgChannelId.HasValue && node.TgChannelId.Value != primaryId`. Поскольку любая подпапка содержала этот ID, переименование любой подпапки ошибочно вызывало `EditChannelTitleAsync` для канала родительской папки.

### Принятое решение (Принцип Root Cause First):
1. **Исправление в точке создания и привязки каталогов (`NodeRepository.cs`, `TelegramService.cs`):**
   - В `CreateFolder` параметр `tgChannelId` больше не подменяется на `GetEffectiveChannelId(parentId)` — подпапки создаются с `tg_channel_id = NULL`.
   - В `EnsureDirectoryPathExists` создаваемые директории всегда создаются с `tg_channel_id = NULL`.
   - В `MigrateSubtreeToChannelAsync` `SetFolderChannelId` вызывается строго для самой привязываемой папки. Подпапкам в поддереве `tg_channel_id` сбрасывается в `NULL`.
   - Наследование целевого канала файлами и подпапками происходит динамически через `GetEffectiveChannelId`.
2. **Защита в обработчиках переименования (`WinFspServer.cs`, `WebDavMiddleware.cs`):**
   - Добавлена проверка `node.TgChannelId.Value != parentEffectiveChannelId`. Даже при наличии старых записей переименование подпапки никогда не триггерит переименование Telegram-канала, так как родитель уже относится к этому каналу. Переименование канала срабатывает только при переименовании корневой привязанной папки.
3. **Корректировка инициализации схемы (`DatabaseManager.cs`):**
   - Метод `EnsureSchemaColumns` проверяет и дополняет только структуру таблиц (`ALTER TABLE ADD COLUMN`), без автоматической модификации пользовательских данных.
4. **Синхронизация проверки GC в WebDAV (`WebDavMiddleware.cs`):**
   - В `HandleDeleteAsync` добавлено условие `n.Id == node.Id` (аналогично `WinFspServer.Cleanup` из решения 47), гарантирующее, что удаление файлов или подпапок внутри привязанной папки никогда не удалит сам канал Telegram.

## 51. Отказ от скрытых фоновых очисток и миграций данных БД при старте приложения (Root Cause & Пользовательский контроль)

### Проблема и архитектурный принцип:
Автоматическое выполнение SQL-запросов очистки данных (data cleanup/migrations) при каждом старте службы без явного ведома и согласия пользователя скрывает имеющиеся аномалии в БД, создает неучтенные задержки при запуске и нарушает принцип прозрачности работы с пользовательскими данными.

### Принятое решение:
1. **Удаление фоновой автоочистки из `DatabaseManager.cs`:**
   - Из метода `EnsureSchemaColumns` полностью удален цикл сброса унаследованных `tg_channel_id` у подпапок.
2. **Принцип управления данными:**
   - Инициализатор БД выполняет строго DDL-операции проверки и создания структур (таблицы, колонки, индексы).
   - Любое исправление или очистка существующих пользовательских данных в БД не должна зашиваться в скрытый код запуска, а предлагается пользователю в виде отдельного SQL-скрипта или точечной команды.

## 52. Игнорирование путей виртуального диска в TryFindSourceFile и устранение дедлоков при копировании/перемещении внутри диска Telegram (Root Cause Fix)

### Симптом:
При операциях внутри смонтированного виртуального диска (например, копирование или перемещение файлов/папок из одной подпапки диска `Y:\` в другую подпапку диска `Y:\`) процесс либо зависал, либо принудительно размонтировался при закрытии программы. В логах фиксировался сканер хэндлов `[Handles DragDrop] Сканирование хэндлов для... процессов explorer`, пытавшийся опрашивать открытые дескрипторы самого диска `Y:\`.

### Первопричина (Root Cause):
1. Метод `TryFindSourceFile` спроектирован для поиска физических файлов-источников на локальных дисках ПК (например, `C:\`, `D:\`) при загрузке или перетаскивании их в Telegram.
2. При операциях внутри виртуального диска `Y:\` (Telegram -> Telegram) буфер обмена (`CF_HDROP`) и открытые дескрипторы `explorer.exe` содержали пути с самого смонтированного диска `Y:\`.
3. Запрос сведений об открытом дескрипторе диска `Y:\` через `GetFinalPathNameByHandle` во время исполнения запроса файловой системы WinFsp вызывал взаимную блокировку (дедлок) потоков WinFsp.

### Принятое решение (Принцип Root Cause First):
1. **Отслеживание точки монтирования (`WinFspServer.ActiveMountPoint`)**:
   - В класс `WinFspServer` добавлено публичное статическое свойство `ActiveMountPoint`, фиксирующее текущую букву смонтированного диска (например, `Y:`).
2. **Мгновенный фильтр кандидата (`IsCandidateOnMountedDrive`)**:
   - Реализован детерминированный фильтр `IsCandidateOnMountedDrive(path)`. Если кандидатский путь начинается с буквы текущего монтированного диска (например, `Y:\`, `\\?\Y:\`), он распознается как внутренний путь виртуального диска.
3. **Фильтрация во всех точках сборки источников**:
   - В `CollectClipboardCandidates` (Ctrl+C / Ctrl+V) пути с `Y:\` отфильтровываются.
   - В `CollectExplorerOpenFileHandles` (Drag-and-Drop) хэндлы диска `Y:\` сразу пропускаются без вызова функций чтения путей.
   - В `CheckCandidate` пути с `Y:\` мгновенно возвращают `null`.
4. **Результат**:
   - Поиск источника при операциях внутри диска `Y:\` завершается за 0 миллисекунд.
   - Отсутствуют вызовы ядра по собственным дескрипторам WinFsp, полностью исключены дедлоки и блокировки Проводника.

## 53. Защита от дедлоков при сканировании хэндлов ядра Windows (NT Device filtering & 100ms total scan budget)

### Симптом / Риск:
При сканировании тысяч открытых файловых дескрипторов в процессах `explorer.exe` во время Drag-and-Drop или вставки из буфера обмена задержка опроса дескрипторов могла расти, если в Проводнике было открыто множество внешних или сетевых файлов. Кроме того, обращения к дескрипторам драйвера WinFsp могли вызывать задержки при поиске путей.

### Первопричина (Root Cause):
1. Отсутствие общего ограничения по времени (time budget cap) на весь цикл опроса дескрипторов `CollectExplorerOpenFileHandles`.
2. Опрос ядерных путей дескрипторов WinFsp в файловой системе NT мог использовать системные вызовы Windows API, если путь в ядре начинался с NT-устройства WinFsp (`\Device\WinFsp.Disk...`).

### Принятое решение:
1. **Фильтрация ядерных путей WinFsp (`IsCandidateOnMountedDrive`)**:
   - В `IsCandidateOnMountedDrive` добавлена проверка путей ядра NT: если путь начинается с `\DEVICE\WINFSP` или содержит `\WINFSP.`, он мгновенно распознается как дескриптор WinFsp и отбрасывается за 0 мс без каких-либо обращений к файловой системе.
2. **Общий жесткий бюджет времени сканирования (100 мс)**:
   - В цикл сканирования дескрипторов `CollectExplorerOpenFileHandles` добавлен `Stopwatch scanSw`.
   - Если общее время сканирования хэндлов превышает 100 мс, цикл сканирования мгновенно прерывается, гарантируя, что ни при каких условиях опрос хэндлов не задержит операцию копирования.
3. **Результат**:
   - Гарантированное завершение сканирования дескрипторов за <= 100 мс.
   - Полное исключение вызовов I/O Win32 API для дескрипторов WinFsp в ядре NT.

## 54. Консолидация отслеживания точки монтирования WinFsp и устранение дублирования переменных (Root Cause Cleanup)

### Первопричина (Root Cause):
1. В `WinFspServer.cs` одновременно хранились и обновлялись две переменные точки монтирования (`_currentMountPoint` экземпляра сервиса и статическая `_activeMountPoint`).
2. Из-за параллельного существования двух переменных существовал риск рассинхронизации состояния монтирования и создавалось избыточное дублирование кода.

### Принятое решение:
1. Поле `_currentMountPoint` полностью удалено из `WinFspServer.cs`.
2. Статическое поле `_activeMountPoint` и свойство `ActiveMountPoint` сделаны единственным источником правды для состояния монтирования.
3. Свойство экземпляра `MountPoint` перенаправлено на `_activeMountPoint` (`public string? MountPoint => _activeMountPoint;`).
4. Управление состоянием монтирования в методах `Start()` и `Stop()` консолидировано в `_activeMountPoint`.

## 55. Серверное копирование файлов и папок через Telegram ForwardMessages (WebDAV COPY + WinFsp Zero-Traffic Virtual Copy)

### Бизнес-цель:
Обеспечить мгновенное копирование файлов и папок в пределах одного Telegram-канала или между разными каналами (например, `Z:\Музыка\Рок\track2.mp3` в `Z:\Музыка\новое`) без физического повторного выкачивания и перезагрузки байтов файла в Telegram (0 байт сетевого трафика на повторную загрузку).

### Проблема и Первопричина (Root Cause):
1. **В WebDAV**: метод HTTP `COPY` отсутствовал в роутере `WebDavServer.cs` и заголовке `Allow`. Любой клиент (Cyberduck, Total Commander, проводник) получал `405 Method Not Allowed` и откатывался к полному скачиванию (`GET`) и повторной загрузке (`PUT`).
2. **В WinFsp**: Проводник Windows при операции копирования не имеет системного вызова `CopyFile` на уровне ФС, а открывает файл-источник на чтение (`Open` -> `Read`) и создает целевой файл (`Create` -> `Write`).
3. Механизм поиска источников `TryFindSourceFile` в `WinFspServer.cs` в `CheckCandidate` прямо отсекал пути со смонтированного диска (`if (IsCandidateOnMountedDrive(path)) return null;`). В итоге целевой файл считался новым внешним файлом, открывался `StreamingPipeStream`, и файл заново целиком заливался в Telegram по сети.
4. В `TelegramService` форвардинг (`Messages_ForwardMessages`) использовался исключительно при миграции между разными каналами при `MOVE`, но не был доступен для операций создания копий.

### Принятое решение (Принцип Root Cause First):
1. **Ядро TelegramService (`ForwardFileAsync`)**:
   - Реализован универсальный метод `ForwardFileAsync(sourceMessageId, sourcePreviewMessageId, sourceChannelId, targetChannelId, newCaption)`.
   - Использует нативный RPC `Messages_ForwardMessages` с флагом `Flags.drop_author`.
   - Позволяет дублировать медиа-объект на серверах Telegram мгновенно за ~100–300 мс как в рамках одного канала (`from_peer = to_peer`), так и между разными каналами.
   - Telegram присваивает копии новый уникальный `MessageId` (нет коллизий при удалении оригинала), сохраняя ссылки на исходный документ в облаке.
   - Автоматически пересылает галерейное фото-превью (если есть) и планирует актуализацию подписи через `pending_caption_updates`.
2. **WebDAV сервер (`WebDavMiddleware.HandleCopyAsync`)**:
   - В `WebDavServer.cs` метод `COPY` добавлен в заголовок `Allow` и роутинг.
   - Реализован обработчик `HandleCopyAsync` согласно RFC 4918 (с поддержкой заголовков `Destination`, `Overwrite`, `Depth`).
   - Для файлов: мгновенный форвардинг через `ForwardFileAsync` и регистрация в SQLite со статусом `201 Created` (или `204 NoContent`).
   - Для папок: рекурсивное создание структуры каталогов и форвардинг всех дочерних файлов поддерева.
3. **WinFsp драйвер (`Zero-Traffic Virtual Copy`)**:
   - В `WinFspServer.cs` добавлены методы `GetVirtualPathFromMountedPath` и `TryFindVirtualSourceNode`, распознающие копирование файлов и папок с виртуального диска (через буфер обмена `CF_HDROP` и дескрипторы `explorer.exe`).
   - В `Create` и `Overwrite`: при обнаружении виртуального источника создается контекст `ctx.VirtualSourceNode = virtualSource`, и параллельно в фоне запускается `ForwardFileAsync`.
   - В `Write`: вызовы записи байтов от Проводника подтверждаются мгновенно за 0 мс без создания `StreamingPipeStream` и без трафика в Telegram.
   - В `Cleanup`: по завершении копирования фиксируются новые `TgMessageId` и `TgPreviewMessageId` в базе SQLite.
4. **Результат**:
   - Копирование гигабайтных файлов в Проводнике Windows и WebDAV происходит за доли секунды без расхода интернет-трафика на повторную загрузку.

## 56. Архитектурная изоляция привязки каналов и целевой сбор файлов для миграции (Root Cause First)

### Проблема:
При привязке папки к новому каналу Telegram через контекстное меню (например, `Y:\привязанная`) канал создавался успешно, но файлы, помещаемые в эту папку или её подпапки (например, `Y:\привязанная\big\file.mp3`), уходили в основной канал по умолчанию, а в базе SQLite у корневой привязанной папки `tg_channel_id` оставался `NULL`.

### Первопричина (Root Cause Analysis):
1. В методе `TelegramService.MigrateSubtreeToChannelAsync(int folderNodeId, long targetChannelId)` производилась привязка `_repository.SetFolderChannelId(folderNodeId, targetChannelId)`.
2. Затем запускался цикл очистки `_repository.GetSubtreeNodes(folderNodeId)` для сброса `tg_channel_id` у дочерних папок.
3. Поскольку `GetSubtreeNodes(rootNodeId)` по своей структуре возвращает и саму корневую папку (`result.Add(rootNode)`), цикл `foreach (var dir in subtree.Where(n => n.IsDir))` обходил целевую папку и вызывал `_repository.SetFolderChannelId(dir.Id, null)`. Это мгновенно стирало только что привязанный канал у самой папки.
4. Кроме того, старый сбор файлов через `GetSubtreeNodes` без разбора собирал все файлы поддерева, включая файлы из возможных вложенных привязанных папок.

### Принятое решение:
1. **Прямое назначение канала без деструктивных циклов**:
   - Метод `MigrateSubtreeToChannelAsync` назначает `targetChannelId` строго целевой привязываемой папке (`_repository.SetFolderChannelId(folderNodeId, targetChannelId)`).
   - Любые циклы обнуления дочерних папок полностью удалены. Обычные подпапки наследуют канал динамически через `GetEffectiveChannelId`, а вложенные папки с собственными каналами сохраняют свою изоляцию.
2. **Целевой рекурсивный сбор файлов с пропуском привязанных подпапок (`GetFilesForChannelMigration`)**:
   - В `NodeRepository.cs` добавлен метод `GetFilesForChannelMigration(int rootFolderId)`.
   - При рекурсивном обходе, если дочерняя папка имеет собственный `tg_channel_id` (`child.TgChannelId.HasValue && child.TgChannelId.Value != 0`), её поддерево полностью **пропускается** (`continue;`).
   - Файлы из вложенных привязанных папок не затрагиваются и гарантированно остаются в своих независимых каналах.
3. **Фиксация исходного канала до смены привязки**:
   - `oldEffectiveChannelId` считывается до назначения нового канала, обеспечивая безошибочную группировку файлов в очередь `EnqueueChannelMigrations`.
4. **Синхронизация логирования в `WinFspServer.cs`**:
   - В методе `Create` устранено избыточное логирование `Открыт каталог` при каждом обращении Проводника: оставлен чистый `if (!existed) { AppLogger.Info("WinFsp", $"Создан новый каталог..."); }`.

## 58. Поддержка кастомных каналов в фоновой очереди обновления подписей сообщений (Root Cause First)

### Проблема:
При перемещении файлов привязанной папки в корзину (`.Trash`), а также при их переименовании или версионировании, фоновый воркер `ProcessCaptionQueueAsync` падал с ошибкой Telegram:
`RpcError 400 MESSAGE_ID_INVALID`
и подписи сообщений не обновлялись (записи исключались из очереди).

### Первопричина (Root Cause Analysis):
1. Метод `UpdateMessageCaptionAsync(messageId, newCaption, channelId = null)` при `channelId == null` направляет запрос `Messages_EditMessage` в **основной канал** по умолчанию (`primaryChannel`).
2. В воркере `ProcessCaptionQueueAsync` вызов `UpdateMessageCaptionAsync(currentItem.TgMessageId, currentItem.NewCaption)` выполнялся без указания `channelId`.
3. Сообщения файлов, расположенных в кастомных привязанных каналах, искались в основном канале, где они физически отсутствуют, вызывая `MESSAGE_ID_INVALID`.

### Принятое решение:
1. В модель `PendingCaptionItem` добавлено свойство `ChannelId`.
2. Метод `GetNextPendingCaptionUpdate` в `NodeRepository.cs` модифицирован для извлечения `n.tg_channel_id` через `LEFT JOIN nodes n ON p.node_id = n.id`.
3. В `ProcessCaptionQueueAsync` в вызов `UpdateMessageCaptionAsync` передаётся точный `targetChannelId` с фоллбэком на `_repository.GetChannelIdByTgMessageId(currentItem.TgMessageId)`.
4. Теперь обновление подписей (при удалении в корзину, переименовании, версионировании) корректно адресуется именно в тот Telegram-канал, где лежит файл.

## 59. Оптимизация перманентного удаления привязанных папок и устранение гонки при удалении каналов (Root Cause First)

### Проблема:
При перманентном удалении привязанной папки (очистка корзины или Shift+Delete) все её файлы сначала помещались в очередь `pending_deletions`, запуская поштучное удаление сообщений пачками по 100 штук, а параллельно запускался вызов `DeleteChannelAsync(chId)`. 
Это приводило к race condition:
1. Если канал удалялся быстрее, воркер очереди натыкался на несуществующий канал и спамил ошибки или зависал.
2. В Telegram удаление канала через `Channels_DeleteChannel` атомарно уничтожает весь канал со всеми его сообщениями на сервере. Поштучное удаление сообщений перед удалением канала было абсолютно избыточным, тратило сетевые запросы и несло риск `FLOOD_WAIT`.

### Принятое решение:
1. **Предварительное определение уничтожаемых каналов**:
   - В `NodeRepository.cs` добавлен метод `GetNodeCountForChannel(channelId)`.
   - В `WinFspServer.cs` и `WebDavMiddleware.cs` перед формированием очереди перманентного удаления проверяется, уничтожается ли кастомный привязанный канал целиком (`totalNodesInDbForChannel == nodesInSubtreeForChannel`).
2. **Исключение из очереди `pending_deletions` сообщений удаляемых каналов**:
   - Сообщения файлов, чей канал подлежит полному уничтожению, больше не ставятся в очередь поштучного удаления `pending_deletions`. Они атомарно уничтожаются на сервере Telegram вместе с каналом в одной операции `Channels_DeleteChannel`.
   - В очередь `pending_deletions` ставятся только файлы, чьи каналы остаются на диске (например, основной канал).
3. **Отказоустойчивость в `DeleteFilesFromTelegramAsync`**:
   - В `TelegramService.cs` при обращении к каналам добавлена обработка ситуаций, когда канал уже удален/недоступен: сообщения автоматически признаются успешно очищенными без зависания очереди.

## 60. Интеллектуальный TopMost для оверлея прогресса с подавлением в полноэкранном режиме (Root Cause First)

### Проблема:
После перевода оверлея прогресса (`TrayProgressOverlay`) в обычный z-слой (`TopMost = false`) окна Проводника, расположенные в правом нижнем углу экрана (например, корзина `.Trash` или открытая папка программы), перекрывали плашку прогресса. Пользователю приходилось сворачивать окна, чтобы увидеть ход передачи. При этом прямой безусловный `TopMost` мешал при просмотре фильмов или в полноэкранных приложениях.

### Принятое решение:
1. **Возврат TopMost без перехвата фокуса**:
   - Восстановлены флаги `TopMost = true` и расширенный стиль `WS_EX_TOPMOST`.
   - Сохранены стили `WS_EX_NOACTIVATE | WS_EX_TOOLWINDOW` и свойство `ShowWithoutActivation => true`.
   - Плашка гарантированно отображается над окнами Проводника в углу экрана, не отбирая фокус мыши и клавиатуры.
2. **Двухуровневый детектор полноэкранного режима (`IsFullScreenAppRunning`)**:
   - Интегрирован вызов Windows Shell API `SHQueryUserNotificationState`: распознает полноэкранные игры, плееры Direct3D/DirectShow (`QUNS_RUNNING_D3D_FULL_SCREEN`), режим презентаций (`QUNS_PRESENTATION_MODE`) и занятость пользователя (`QUNS_BUSY`).
   - Добавлена геометрическая проверка `GetForegroundWindow` + `GetWindowRect` на соответствие габаритам экрана монитора (`screen.Bounds`), распознающая безрамочные полноэкранные плееры (VLC, MPC-HC, PotPlayer) и браузеры (F11 / полноэкранный YouTube). Исключены системные окна Рабочего стола (`Progman`/`WorkerW`) и Панели задач (`Shell_TrayWnd`).
3. **Тихий режим при просмотре видео / играх**:
   - При активном полноэкранном режиме оверлей автоматически подавляется и не всплывает (`TryShowOverlay()`).
   - Если полноэкранный режим активирован прямо во время текущей передачи, таймер `HideCheckTimer` мгновенно скрывает оверлей.

## 61. Поддержка сторонних программ (бэкаперов, файловых менеджеров) и ускорение сканирования дескрипторов ядра (Root Cause First)

### Проблема:
1. При копировании файлов через Проводник Windows в системах с большим числом дескрипторов (85 000+) тайм-аут 100 мс иногда прерывал сканирование буквально за несколько процентов до конца таблицы (например, обработано 82 308 из 84 748 дескрипторов). В результате путь к исходному файлу на диске не обнаруживался, а потоковый резервный парсер тегов не мог вычислить точную длительность VBR MP3 аудио без Xing-заголовка, выставляя `0 сек`.
2. При копировании файлов сторонними программами (программы бэкапов типа FreeFileSync, Cobian, FastCopy, файловые менеджеры Total Commander, Far Manager, консольные утилиты robocopy и скрипты) пути к оригинальным файлам не определялись никогда, так как сканер искал дескрипторы исключительно в процессах `explorer.exe`, а буфер обмена `CF_HDROP` бэкаперами не используется.

### Первопричина (Root Cause Analysis):
1. **Жесткая фильтрация только по Explorer**: Метод поиска дескрипторов опрашивал только `Process.GetProcessesByName("explorer")`. Любой иной процесс, вызывающий запись на виртуальный диск, полностью игнорировался.
2. **Оверхед таймера в цикле ядра**: Проверка `scanSw.ElapsedMilliseconds > 100` вызывалась на каждой из 85 000 итераций, создавая лишние накладные расходы системного таймера (`QueryPerformanceCounter`) до 15-20 мс, а порог 100 мс был излишне мал для первого файла сессии копирования.

### Принятое решение:
1. **Интеграция PID вызывающего процесса из WinFsp**:
   - Через нативный вызов WinFsp `FileSystemBase.GetOperationProcessId()` (обертка над `Api.FspFileSystemOperationProcessId()`) определяется точный `callerPid` процесса, выполняющего операцию `Create` / `Write`.
   - Если вызывающий процесс не является системным или собственным процессом, его PID автоматически включается в набор целевых процессов (`targetPids`).
   - Для программ бэкапов и альтернативных файловых менеджеров поиск дескриптора открытого исходного файла теперь выполняется мгновенно (в их собственном процессе, где всего сотни дескрипторов).
   - За счет механизма сессий (`ActiveCopySession`) корень исходной папки (`SourceRoots`) фиксируется при первом же файле, и все последующие файлы бэкапа из этой папки сопоставляются за 0 мс.
2. **Оптимизация цикла ядра и увеличение бюджета**:
   - Бюджет сканирования дескрипторов для первого файла увеличен со 100 мс до 350 мс.
   - Опрос системного таймера оптимизирован: время проверяется раз в 1024 итерации (`(i & 0x3FF) == 0`), что устранило накладные расходы и ускорило прогон по 85 000 дескрипторам ядра в 2–3 раза.
   - Сохранен моментальный выход (`Fast-Break`) при первом совпадении с целевым именем файла.

## 62. Единое разрешение источников файлов и скользящий тайм-аут сессии бэкапов (Root Cause First)

### Проблема:
При запуске бэкапа файлов через программы резервного копирования (например, SyncBackFree) на первых файлах папок (`Addison Rae`, `dj day`, `KOMODO`) пути к оригинальным файлам определялись как не найденные, хотя за мгновение до этого в логе фиксировалось:
`[INFO ] [WinFsp] [Handles DragDrop] Обнаружен открытый файл в процессе PID 8300: 'D:\TGtest\...'`.
При этом в Total Commander все файлы (включая самые первые) находились стабильно.

### Первопричина (Root Cause Analysis):
1. **Двойное несогласованное сканирование дескрипторов ядра в `Create` и `Overwrite`**:
   - Метод `Create` сначала вызывал `TryFindVirtualSourceNode` (поиск виртуальной копии внутри диска `Y:\`).
   - Сканер дескрипторов `CollectOpenFileHandles` опрашивал 88 000 хэндлов и **успешно находил** открытый файл на диске `D:\` в процессе бэкапера (`SyncBackFree`).
   - Однако метод `TryFindVirtualSourceNode`, увидев, что путь лежит не на смонтированном диске `Y:\`, считал его «чужим» и **выбрасывал найденный путь**, возвращая `null`.
   - Затем, через 40–50 мс, метод `Create` доходил до `TryFindSourceFile` и запускал тяжелое сканирование дескрипторов ядра **второй раз подряд**.
2. **Разница в паттернах работы с файлами (Total Commander vs SyncBackFree)**:
   - Total Commander держит исходный файл на чтение открытым непрерывно на всём протяжении создания целевого файла, поэтому второй скан также успевал застать дескриптор.
   - Программы бэкапов (SyncBackFree) открывают исходный файл кратковременно для чтения заголовка/хэша/атрибутов, сразу закрывают его дескриптор, вызывают `CreateFileW` на приёмнике `Y:\`, и лишь затем заново открывают файл для передачи данных. В паузе между этими действиями второй скан дескрипторов опаздывал и находил 0 открытых файлов.
3. **Потеря `callerPid` в операции `Write`**:
   - При первой записи блока в `Write` метод `FileSystemBase.GetOperationProcessId()` в контексте системного потока записи Windows возвращал `0`. В результате при повторной попытке определения источника процесс бэкапера вообще выпадал из списка целевых процессов, и опрашивался только Explorer (2 процесса вместо 3).
4. **Преждевременное уничтожение `CopySession`**:
   - При пофайловом копировании бэкапером `PendingFiles.Count` изначально равен 1. После сопоставления первого файла код немедленно обнулял `_activeSession = null`, лишая последующие файлы мгновенного сопоставления за 0.01 мс по запомненной папке `SourceRoots`.

### Принятое решение:
1. **Единый метод `ResolveFileSource`**:
   - В методах `Create` и `Overwrite` устранено двойное сканирование дескрипторов. Теперь опрос дескрипторов и буфера обмена выполняется **строго один раз** с параметром `includeMountedDrive: true`.
   - Единая классификация результата:
     - Если найденный кандидат лежит на диске `Y:\` — он передается в механизм виртуального копирования (`VirtualCopy`) для мгновенного форвардинга сообщений в Telegram.
     - Если найденный кандидат лежит на локальном физическом диске (`D:\`, `C:\` и др.) — он **никогда не выбрасывается**, а сразу привязывается как `OriginalSourcePath` и регистрируется в сессии копирования.
2. **Сохранение `CreatorProcessId` в контексте `FspNodeContext`**:
   - PID создателя файла фиксируется при `Create` и `Overwrite`. Если при записи `Write` потребуется повторное определение источника, сканер дескрипторов гарантированно опрашивает именно процесс бэкапера, даже если `GetOperationProcessId()` в системном потоке возвращает `0`.
3. **Скользящий тайм-аут активности сессии (`LastActivityUtc` и `IsExpired(20 сек)`)**:
   - Сессия `CopySession` больше не уничтожается сразу при обнулении очереди `PendingFiles.Count == 0`, если у неё есть запомненные папки `SourceRoots`.
   - Сессия сохраняет активность в течение 20 секунд с момента последнего совпадения. Пока бэкапер закидывает файлы один за другим, все файлы из той же папки сопоставляются за 0.01 мс через прямой `File.Exists` вообще без обращения к дескрипторам ядра.
   - По истечении 20 секунд неактивности сессия автоматически и безопасно освобождается.

## 63. Запуск воркера миграции каналов и отказоустойчивая пересылка сообщений (Root Cause First)

### Проблема:
При привязке папки к новому приватному каналу Telegram (`MigrateSubtreeToChannelAsync`) канал успешно создавался в Telegram и привязывался к папке в SQLite, файлы корректно помещались в таблицу `pending_channel_migrations` со статусом `pending`, но дальнейшая фоновая миграция файлов не происходила, и сообщения оставались в исходном канале.

### Первопричина (Root Cause Analysis):
1. **Отсутствие запуска воркера миграции при старте приложения:**
   - Метод `StartChannelMigrationQueueWorker()` вызывался исключительно внутри `SetRepository(NodeRepository repository)`.
   - Метод `SetRepository` не вызывался ни в одном месте кодовой базы, так как экземпляр `TelegramService` создавался через конструктор `new TelegramService(configManager, repository)`.
   - В конструкторе `TelegramService` запускались только `StartCaptionQueueWorker()` и `StartDeletionQueueWorker()`. Воркер миграции каналов `ProcessChannelMigrationsAsync` никогда не стартовал, а отправленный сигнал `_migrationSignal.Release()` уходил в пустоту.
2. **Необработанные исключения вызовов `GetStoragePeerAsync`:**
   - Вызовы получения дескрипторов исходного и целевого каналов находились снаружи блока `try/catch`. При любой сетевой ошибке или отсутствии сохраненного `access_hash` исключение аварийно завершало весь фоновый Task воркера без возможности восстановления.
3. **Неполная обработка ответа пересылки MTProto:**
   - Ответ `Messages_ForwardMessages` проверялся строго через `if (fwdUpdates is TL.Updates)`, тогда как Telegram для каналов часто возвращает `TL.UpdatesCombined`. В результате `newMsgId` оставался `0`.
4. **Контекст удаления старых сообщений из исходного канала:**
   - Старые сообщения помещались в очередь `pending_deletions`, которая не хранит ID канала, а определяет его через `GetChannelIdByTgMessageId`. Но к моменту удаления `nodes.tg_message_id` уже обновлялся на `newMsgId`, приводя к попытке удаления из первичного канала по умолчанию.

### Принятое решение:
1. **Гарантированный запуск воркера в конструкторе и триггер при авторизации:**
   - Вызов `StartChannelMigrationQueueWorker()` добавлен непосредственно в конструктор `TelegramService`.
   - В методы авторизации (`HandleWTelegramResult` / прогрев) добавлен вызов `TriggerChannelMigrationProcessing()`, гарантирующий автоматическое подхватывание очереди миграции после старта или реконнекта.
2. **Защита цикла и надежное получение пиров:**
   - Получение `targetPeer` и `sourcePeer` через `GetStoragePeerAsync` перенесено внутрь защищенного блока `try/catch` с логированием и паузой повтора при ошибке, предотвращая аварийное падение воркера.
3. **Универсальный парсинг `ExtractMessageIdFromUpdates`:**
   - Для ответов `Messages_ForwardMessages` задействован универсальный хелпер `ExtractMessageIdFromUpdates`, корректно извлекающий Message ID как из `TL.Updates`, так и из `TL.UpdatesCombined`.
4. **Прямое удаление старых сообщений из исходного канала:**
   - Старые сообщения удаляются асинхронно напрямую с явным указанием `item.SourceChannelId`: `DeleteFilesFromTelegramAsync(oldIdsToDelete, item.SourceChannelId)`.

## 60. Устранение холостого скачивания при копировании файлов внутри диска (Zero-Download Virtual Copy Read Bypass) и предотвращение ложного версионирования заготовок

### Проблема:
1. При копировании файлов или папок между каталогами виртуального диска Telegram (`Y:\`) через Проводник Windows (`explorer.exe`), механизм виртуального копирования (`VirtualCopy`) успешно определял источник и выполнял мгновенный серверный форвардинг (`ForwardFileAsync`) за 88 мс, но после этого запускалось полное скачивание файла из интернета через MTProto воркеры (`_telegramService.DownloadFileAsync`), с выводом оверлея `[Download]` в трее и расходом сетевого трафика.
2. После завершения копирования файл ложно версионировался в базе данных (`Database.CreateOrUpdateFile`): предыдущая заготовка отправлялась в корзину `.Trash` с `TgMessageId=NULL`, а новому файлу присваивался суффикс `_v2`.

### Первопричина (Root Cause Analysis):
1. **Проводник Windows не осведомлен о серверном клонировании**:
   - Стандартный алгоритм копирования `CopyFileEx` в `explorer.exe` выполняет цикл `ReadFile(hSource)` -> `WriteFile(hDestination)`.
   - Метод `Write(...)` для целевого виртуального файла отбрасывал входящие байты (`ctx.VirtualSourceNode != null -> return STATUS_SUCCESS`), так как данные уже сдублированы в Telegram.
   - Однако метод `Read(...)` для узла-источника не имел контекста того, что данный файл в текущую секунду читается Проводником исключительно ради передачи байтов в отбрасывающий их `Write(...)`. Метод `Read(...)` честно вызывал `DownloadFileAsync`, приводя к 100% скачиванию всего файла из сети Telegram.
2. **Ложное версионирование заготовок узлов**:
   - В методе `Create` узел создавался с ожидаемым размером `virtualSource.Size` и `tg_message_id = null`.
   - В `CreateOrUpdateFile` проверка на обновление существующего узла-заготовки содержала жесткое условие `existingNode.Size <= 1 && existingNode.TgMessageId == null`.
   - Поскольку размер заготовки уже составлял несколько мегабайт, база ошибочно считала узел полноценным существующим файлом, отправляла его в `.Trash` как «v1» и создавала новую запись «v2».

### Принятое решение:
1. **Регистрация активных операций виртуального копирования (`ActiveVirtualCopyInfo`)**:
   - В `TelegramWinFspFileSystem` внедрена потокобезопасная коллекция `_activeVirtualCopies` с отслеживанием `TargetNodeId`, `SourceNodeId`, `CreatorPid` и времени создания.
   - Регистрация выполняется в `Create` и `Overwrite` при связывании `VirtualSourceNode`.
   - Автоматическое снятие регистрации происходит в `Cleanup` и `FspNodeContext.Dispose()`.
2. **Мгновенный байпас чтения из ОЗУ (`Zero-Download Read Bypass`)**:
   - В методе `Read(...)` проверяется статус `IsVirtualCopySourceActive(node.Id, callerPid)`.
   - Если файл читается процессом Проводника, выполняющим виртуальное копирование (или системным потоком ядра), чтение из сети Telegram полностью исключается: буфер ядра мгновенно очищается нулями в оперативной памяти (`new Span<byte>(buffer, toRead).Clear()`) и возвращается `bytesTransferred = toRead; STATUS_SUCCESS;`.
   - Проводник мгновенно передает эти байты в `Write(...)`, где они отбрасываются. Скорость копирования составляет десятки ГБ/с (0 мс ожидания сети), трафик Download и Upload равен строго 0 байт.
   - Для сторонних процессов (плееры, другие приложения) или копирования с диска `Y:\` на физический диск `C:\` штатное скачивание из Telegram полностью сохранено без изменений.
3. **Исправление распознавания заготовок в `NodeRepository`**:
   - В `CreateOrUpdateFile` условие обновления заготовки изменено на `if (existingNode.TgMessageId == null && existingNode.InlineData == null)`. Любой узел без содержимого обновляется напрямую без ложного версионирования и без засорения корзины.

## 61. Каноническая стандартизация подписей Telegram при форвардинге и корректный расчет первой версии файлов (Root Cause First)

### Проблема:
1. При копировании файлов на виртуальном диске WinFsp в Telegram отправлялось пересыланное сообщение (`Messages_ForwardMessages`), но при последующей актуализации подписи через очередь `pending_caption_updates` исчезали системная иконка статуса `🟢`, строка идентификатора `ID: ...` и хэштег `#latest`. Подпись заменялась на голый путь к файлу.
2. Новые файлы при копировании получали ошибочный суффикс версии `_v2` вместо `_v1`, даже если файл копировался в новую пустую папку, где файлов с таким именем ранее не существовало.

### Первопричина (Root Cause Analysis):
1. **Пропуск форматирования подписи в `ForwardFileAsync`**:
   - Во всех остальных операциях системы (`UploadFileChunkAsync`, переименование, версионирование, миграция каналов) текст подписи формируется через канонический метод `NodeRepository.FormatTelegramCaption(...)`.
   - В `TelegramService.ForwardFileAsync` в очередь `pending_caption_updates` ставилась переданная из `WinFspServer` строка пути как есть (`_repository?.EnqueueCaptionUpdate(targetNodeId, newMsgId, newCaption)`), стирая всю системную разметку при обработке очереди.
2. **Некорректная проверка заготовок в `GetNextVersionForFile`**:
   - В `NodeRepository.GetNextVersionForFile` стояло условие `if (size <= 1 && !hasTg) return Math.Max(1, currentVersion);`.
   - Поскольку в `WinFspServer.Create` для виртуальной копии в SQLite создается запись заготовки с размером оригинала (`size > 1`), условие не срабатывало, и метод ошибочно считал заготовку уже существующей в Telegram версией файла, возвращая `currentVersion + 1 = 2`.

### Принятое решение:
1. **Каноническое форматирование подписи в `ForwardFileAsync`**:
   - В `TelegramService.ForwardFileAsync` перед постановкой в очередь обновления подписи добавлено автоматическое форматирование:
     `string effectiveCaption = newCaption.StartsWith("🟢") || newCaption.StartsWith("🗑️") ? newCaption : NodeRepository.FormatTelegramCaption(newCaption, newMsgId, isLatest: true);`
   - Для связанных превью-сообщений (`newPreviewId`) также формируется стандартизированная подпись с актуальным Message ID превью.
   - В `WinFspServer.cs` в методах `Create` и `Overwrite` в вызов `ForwardFileAsync` теперь явно передается `targetNodeId` (`vNode.Id` / `node.Id`), гарантируя привязку подписи к правильному узлу в SQLite.
2. **Исправление вычисления версии в `GetNextVersionForFile`**:
   - В `NodeRepository.cs` условие исправлено на `if (!hasTg && !hasInline) return Math.Max(1, currentVersion);`. Если у узла в базе еще нет привязанных данных в Telegram (`tg_message_id == null`) и нет локального `inline_data`, узел является заготовкой в процессе создания (первая версия `_v1`), а не перезаписью.
3. **Результат**:
   - При копировании файлов в Telegram подпись сообщения сохраняет полную каноническую разметку:
     `🟢 /путь/файл_v1.ext`
     `ID: 236`
     `#latest`
   - Имя файла сохраняет оригинальную версию `_v1` без ложных инкрементов.

## 64. Надежное удаление сообщений из привязанных каналов при удалении файлов (Root Cause First)

### Проблема:
При перманентном удалении отдельных файлов из привязанных папок (пользовательских каналов) файлы удалялись из базы SQLite, но сообщения оставались на сервере Telegram в исходных каналах.

### Первопричина (Root Cause Analysis):
1. Таблица персистентной очереди `pending_deletions` хранила только `tg_message_id`, теряя привязку к конкретному Telegram-каналу (`channel_id`).
2. При удалении файла узел сначала удалялся из таблицы `nodes` в базе данных. Когда фоновый воркер `DeletionQueueWorker` забирал ID из `pending_deletions` и вызывал `_repository.GetChannelIdByTgMessageId(id)`, узел в базе уже отсутствовал, поэтому метод возвращал `0` (основной канал).
3. В результате запрос на удаление сообщений отправлялся в основной канал вместо персонального канала привязанной папки, и Telegram возвращал ошибку либо не находил сообщение.

### Принятое решение:
1. **Сохранение `channel_id` в таблице `pending_deletions`**:
   - В схему базы данных (`Schema.sql`, `DatabaseManager.cs`) добавлена колонка `channel_id INTEGER NOT NULL DEFAULT 0` (с автоматическим применением `ALTER TABLE` для существующих баз).
   - В методах `EnqueuePermanentDeletion` (`WinFspServer.cs`, `WebDavMiddleware.cs`) в очередь записывается пара `(tg_message_id, channel_id)`.
2. **Группировка и удаление по каналам в `DeletionQueueWorker`**:
   - В `TelegramService.cs` воркер извлекает пары `(MessageId, ChannelId)`, группирует их по `ChannelId` и отправляет запросы на удаление `Channels_DeleteMessages` точно в тот канал, в котором находились сообщения.

## 26. Архитектура резервного копирования базы данных SQLite в отдельный канал Telegram (Часть 1: Снимки WAL, выгрузка и UI)

### Бизнес-цель:
Обеспечить 100% сохранность структуры виртуального диска (дерева каталогов, версий `v1/v2`, пустых папок, статусов корзины `.Trash` и локальных микрофайлов `inline_data`), предотвратив катастрофическую потерю иерархии файлов при случайном удалении `base.db`, повреждении диска или сбое ОС.

### Отклоненные решения:
* ❌ **Парсинг сообщений канала Telegram для восстановления базы:** Отклонено архитектурно из-за жестких лимитов `FLOOD_WAIT` при обходе десятков тысяч сообщений, невозможности восстановить пустые директории, порядок удалений и временные метки.
* ❌ **Прямое копирование `File.Copy("base.db", ...)` на лету:** В режиме WAL (`base.db-wal`) такое копирование создает неконсистентные или битые копии базы данных.

### Первопричина и принятое архитектурное решение (Root Cause First):
1. **Двухэтапное снятие снимков SQLite:**
   - Чекпоинт: `PRAGMA wal_checkpoint(TRUNCATE);` сбрасывает все завершенные транзакции из буфера `base.db-wal` в монолитный файл `base.db` и усекает файл `-wal` до 0 байт.
   - Снимок: `VACUUM INTO 'backups/base_snapshot.db'` создает монолитный, атомарный, дефрагментированный файл-слепок без остановки и блокировки читателей и писателей.
2. **Выгрузка в отдельный приватный канал Telegram:**
   - База данных выгружается в отдельный приватный broadcast-канал (по умолчанию «Telegram Drive Backups») с хронологической историей всех ревизий.
   - Карточка сообщения содержит имя компьютера `Environment.MachineName`, дату, количество узлов, размер и хэштег `#db_backup`.
3. **Политика создания копий и UI:**
   - Debounce-таймер тишины (по умолчанию 15 минут) после любых операций изменения структуры.
   - Автоматический бэкап при штатном закрытии процесса через системный трей (`HandleApplicationExit`).
   - Ручной пункт в меню трея Windows: «Отправить бэкап базы в Telegram».
   - Новая вкладка «Бэкап базы» в окне настроек `AuthSettingsForm.cs`.

## 65. Привязка канала резервных копий к таблице `telegram_channels` базы данных (Single Source of Truth)

### Бизнес-цель:
Устранить избыточное дублирование `BackupChannelId` в локальном конфигурационном файле `settings.json`, сделать базу данных `base.db` единым и самодостаточным источником правды для всех подключенных устройств (сценарий «Дом — Работа»), а также ускорить отправку бэкапов до 0 мс за счет прямого использования `(channel_id, access_hash)` без поиска по всем диалогам Telegram.

### Проблема и недостатки хранения в JSON:
1. Если ID канала хранится в `settings.json`, то при переносе базы на новый ПК (или ноутбук) конфигурацию приходилось дублировать вручную, иначе программа не знала о существовании канала бэкапов и создавала дубликат канала.
2. При отсутствии ID в конфиге происходило тяжелое сетевое сканирование всех чатов пользователя (`Messages_GetAllChats`) по текстовому названию, что приводило к лишним сетевым задержкам и риску лимитов FloodWait.

### Принятое решение (Root Cause First — Вариант 1):
1. **Расширение схемы `telegram_channels`**:
   - В таблицу `telegram_channels` добавлена колонка `channel_type TEXT NOT NULL DEFAULT 'storage'` (с автоматической бесшовной миграцией `ALTER TABLE` в `DatabaseManager.ApplySchema`).
   - Для каналов диска используется роль `'storage'`, а для выделенного канала резервных копий базы данных — `'backup'`.
2. **Методы репозитория `NodeRepository`**:
   - Добавлены методы `GetBackupChannel(accountId)` и `SaveOrUpdateBackupChannel(accountId, channelId, accessHash, title)`.
   - Основной метод поиска хранилища `GetPrimaryChannel` фильтрует каналы условием `channel_type != 'backup'`, исключая случайную запись файлов диска в канал резервных копий.
3. **Прямое разрешение peer в `TelegramService`**:
   - Метод `GetBackupStoragePeerAsync` проверяет наличие канала в базе данных: если запись есть, возвращается готовый `InputPeerChannel(channel_id, access_hash)` мгновенно без сетевых обращений.
   - Если канала в базе нет (самый первый запуск проекта с нуля), создается приватный канал `"Telegram Drive Backups"`, и его реквизиты сразу сохраняются в `base.db`.
   - Полностью исключен избыточный перебор всех диалогов через `Messages_GetAllChats`.
4. **Очистка `settings.json` и обновление UI**:
   - Поле `BackupChannelId` удалено из конфигурации `settings.json` (`AppSettings.cs`).
   - В интерфейсе настроек `AuthSettingsForm.cs` поле ID канала сделано информационным (Read-Only) с пояснением, что канал привязан непосредственно в `base.db`.

   - Валидация длины строки (до 128 символов по ограничениям MTProto `Channels_EditTitle`).
   - Автоматическая замена пустого значения или пробелов на дефолтное название `Telegram Drive Backups` во избежание ошибки `CHAT_TITLE_EMPTY`.
3. **Синхронизация при выполнении бэкапа (`TelegramService.GetBackupStoragePeerAsync`)**:
   - Перед возвращением peer-дескриптора бэкап-канала проверяется, совпадает ли текущий заголовок в базе данных с желаемым (`specificTitle`). Если они отличаются (например, настройки были изменены офлайн или при старте на другом ПК), заголовок обновляется в Telegram и локальной базе данных.

## 68. Устранение дедлока при автоматическом бэкапе при выходе из программы (Root Cause First)

### Проблема и симптомы:
При нажатии на пункт меню системного трея «Выход» процесс зависал: меню трея переставало откликаться, окно настроек не открывалось, диск продолжал функционировать в памяти, а в логах процесс останавливался на строке:
`[INFO ] [TelegramService] Загрузка резервной копии 'base_*.db' в Telegram (канал ID: ...)...`

### Анализ первопричины (Root Cause):
1. **Блокировка UI-потока WinForms**:
   Пункт меню «Выход» в `TrayContext.cs` синхронно вызывал `_backupService?.HandleApplicationExit()`.
2. Внутри `HandleApplicationExit()` выполнялся вызов `PerformBackupAsync(...).GetAwaiter().GetResult()`.
3. Внутри метода `PerformBackupAsync()` и вызываемого им `_telegramService.UploadBackupDocumentAsync()` выполнялись асинхронные вызовы (`await _client.UploadFileAsync`, `await _client.SendMessageAsync`).
4. Без передачи свободного управления циклу обработки сообщений Windows (`WindowsFormsSynchronizationContext`) поток UI блокировался в ожидании результата задачи, в то время как продолжение асинхронных вызовов требовало диспетчеризации контекста или цикла событий, приводя к классическому взаимному дедлоку UI-потока.

### Реализованное решение (Вариант 1):
1. **Асинхронный выход в `TrayContext.cs`**:
   - Метод закрытия переведен на полноценный асинхронный поток `private async Task ExitApplicationAsync()`.
   - Клик по пункту «Выход» вызывает асинхронный метод `async (s, e) => await ExitApplicationAsync()`.
   - Пользователю выводится информационное уведомление в трее: `«Сохранение резервной копии базы данных перед выходом...»`.
   - Гарантированный сброс ресурсов и завершение процесса (`Application.Exit()`) выполняется в блоке `finally`.
2. **Асинхронный метод `HandleApplicationExitAsync` в `DatabaseBackupService.cs`**:
   - Добавлен метод `public async Task HandleApplicationExitAsync()` с использованием `ConfigureAwait(false)`.
   - Для синхронного вызова оставлен безопасный метод `HandleApplicationExit()`, использующий `Task.Run` с таймаутом в пуле потоков без блокировки UI-контекста.

## 40. Автоматическое восстановление базы данных из канала Telegram (Root Cause & Safety First)

### Бизнес-цель:
Обеспечить автономное восстановление структуры файлов и базы данных `base.db` на новом компьютере или после повреждения локального файла напрямую из закрытого канала резервных копий Telegram без риска повреждения или потери текущих локальных данных.

### Архитектурные риски и первопричины (Root Cause Analysis):
1. **Блокировка файлов в WAL-режиме**:
   В SQLite при открытых соединениях и пуле соединений (`Connection Pooling`) файлы `base.db`, `base.db-wal` и `base.db-shm` заблокированы процессом Windows, что при попытке прямой перезаписи через `File.Copy` приводит к исключению `IOException: The process cannot access the file because it is being used by another process`.
2. **Риск потери свежих локальных данных**:
   Если пользователь случайно нажмет кнопку восстановления, когда в облаке лежит более старая база, без создания аварийного снимка текущие данные будут безвозвратно утрачены.

### Реализованное решение:
1. **`DatabaseManager.RestoreFromSnapshot`**:
   - Явный вызов `SqliteConnection.ClearAllPools()` перед заменой файла для полного освобождения файловых дескрипторов.
   - Автоматическое создание локального аварийного снимка текущей базы в `backups/base_pre_restore_TIMESTAMP.db` с возможностью мгновенного отката при возникновении сбоя.
   - Атомарная замена `base.db` и принудительное удаление остаточных временных файлов `-wal` и `-shm`.
   - Повторная инициализация схемы (`InitializeDatabase`) и проверка целостности базы через `PRAGMA integrity_check`.
2. **`TelegramService.GetLatestBackupDocumentAsync` & `DownloadBackupDocumentAsync`**:
   - Поиск последнего сообщения с файлом `base_*.db` или хэштегом `#db_backup` через API `Messages_GetHistory`.
   - Потоковое скачивание документа с передачей процентов прогресса в UI без избыточного расхода оперативной памяти.
3. **`DatabaseBackupService.RestoreFromTelegramAsync`**:
   - Оркестрация процесса с защитой через `_backupLock` от конкурентных фоновых автобэкапов.
   - Оповещение `_repository.NotifyNodeChanged()` для немедленного обновления файлового дерева виртуального диска.
4. **Интерфейс `AuthSettingsForm.cs`**:
   - Добавлена кнопка «📥 Восстановить базу из Telegram».
   - Выводится подробное диалоговое окно подтверждения с указанием имени файла, даты, размера снимка и предупреждения.
   - Индикация статуса выполнения непосредственно на форме.

## 41. Фоновая авто-проверка свежей базы в Telegram и тихая синхронизация между ПК (сценарий Дом/Работа)

### Бизнес-цель:
Обеспечить бесшовную работу пользователя на двух или более компьютерах (например, десктоп на работе и ноутбук дома): свежие изменения структуры диска автоматически подтягиваются без навязчивых модальных окон при выходе ноутбука из сна/гибернации или по периодическому таймеру.

### Архитектурные риски и первопричины (Root Cause Analysis):
1. **Проблема спящего режима (Sleep / Hibernation)**:
   При открытии крышки ноутбука процесс Windows Forms не перезапускается, следовательно, проверка «при старте приложения» не сработала бы.
   *Решение:* Подписка на системные события Windows `Microsoft.Win32.SystemEvents.PowerModeChanged` (режим `PowerModes.Resume`) с паузой в 8 секунд для переподключения сети.
2. **Проблема рассинхронизации системных часов**:
   Сравнение даты изменения локальной базы и даты сообщения из Telegram уязвимо к несовпадению системных часов между двумя материнскими платами или часовыми поясами.
   *Решение:* Фиксация строго монотонно возрастающего целочисленного `Message ID` сообщения в Telegram. В настройки добавлено свойство `LastSyncedBackupMessageId`.
3. **Устранение «усталости от подтверждений»**:
   Если бэкап пришел от другого компьютера (`caption.Contains(MachineName) == false`) и на локальном компьютере отсутствуют несохраненные изменения (`HasUnsavedChanges == false`), база данных накатывается полностью автоматически, а пользователю выводится лишь ненавязчивая подсказка в трее. Предупреждение генерируется только при наличии реального конфликта (когда на локальном ПК есть незалитые файлы).

### Реализованное решение:
1. `AppSettings.cs`: добавлены параметры `RemoteCheckIntervalMinutes` (по умолчанию 5 мин) и `LastSyncedBackupMessageId`.
2. `DatabaseBackupService.cs`:
   - Добавлен метод `CheckAndSyncFromTelegramAsync`.
   - Запущен периодический таймер `_cloudSyncTimer`.
   - Добавлен обработчик `PowerModeChanged` для мгновенной реакции на пробуждение ОС.
   - Внедрены события `OnCloudSyncApplied` и `OnCloudSyncConflict`.
3. `TrayContext.cs`: подписка на события с выводом информационных BalloonTip-подсказок в системном трее Windows.
4. `AuthSettingsForm.cs`: обновлен чекбокс и добавлено поле интервала проверки в минутах (активно только при включенном чекбоксе).

## 42. Блокировка выгрузки бэкапа при неразрешенном конфликте версий и трей-уведомления (Root Cause First)

### Бизнес-цель:
Предотвратить потерю данных и неконтролируемую перезапись облачной резервной копии базы данных `base.db` в Telegram, когда на локальном компьютере возник конфликт версий (например: удаленная база не смогла примениться из-за сбоя сети/файла, либо пользователь внес локальные изменения при наличии более свежей копии от другого ПК в облаке).

### Архитектурные риски и первопричины (Root Cause Analysis):
1. **Риск перезаписи облака устаревшими/разошедшимися данными**:
   Если локальный ПК обнаружил более свежий бэкап от другого ПК в Telegram, но не смог его применить (или пропустил из-за `HasUnsavedChanges == true`), последующая выгрузка локального бэкапа переписала бы актуальную цепочку в канале, перезаписав изменения с другого компьютера.
   *Решение:* Жесткая блокировка в точке записи (`DatabaseBackupService.PerformBackupAsync`). Если `HasConflict == true` или перед отправкой обнаруживается `MessageId > LastSyncedBackupMessageId` от другого ПК, выгрузка безусловно прерывается с возвратом `false`.
2. **Осведомленность пользователя без блокировки рабочего процесса**:
   Пользователь должен немедленно узнать о конфликте через системный трей, не теряя возможность продолжить работу.
   *Решение:* Генерация события `OnCloudSyncConflict` и показ предупреждающего BalloonTip в системном трее Windows.
3. **Возможность осознанного разрешения конфликта**:
   Если пользователь сознательно решает оставить свою локальную копию главенствующей, в окно настроек добавлен интерактивный диалог подтверждения принудительной выгрузки (`force: true`), снимающий блокировку и обновляющий `LastSyncedBackupMessageId`.

### Реализованное решение:
1. `DatabaseBackupService.cs`:
   - Добавлены свойства `HasConflict` и `ConflictDetails`.
   - Внедрена блокировка в `PerformBackupAsync`: выгрузка останавливается при наличии конфликта или при обнаружении несинхронизированного сообщения от другого ПК.
   - Добавлен параметр `force` для явного снятия блокировки при подтверждении пользователем.
   - Метод `ExtractMachineName` вынесен в переиспользуемый статический хелпер.
   - При сбое в `RestoreFromTelegramAsync` и `CheckAndSyncFromTelegramAsync` автоматически выставляется состояние конфликта с блокировкой последующей отправки.
2. `TrayContext.cs`:
   - При неудачной попытке отправки бэкапа из трея проверяется `HasConflict` с показом акцентной подсказки: «Выгрузка бэкапа заблокирована: в Telegram есть более свежая копия от другого ПК! Откройте настройки для проверки.».
3. `AuthSettingsForm.cs`:
   - При клике «Отправить бэкап в Telegram сейчас» в состоянии конфликта выводится диалог с подробным описанием и запросом на принудительную перезапись.
   - При ручном восстановлении базы теперь передается `MessageId` бэкапа, корректно актуализируя `LastSyncedBackupMessageId`.

## 43. Настройка интервала проверки при старте (5 сек) и детальное сквозное логирование бэкапов и синхронизации

### Бизнес-цель:
1. Обеспечить оперативную синхронизацию базы данных SQLite при холодном старте приложения (первичный опрос Telegram-канала уже через 5 секунд после запуска вместо 15 сек).
2. Предоставить полную прозрачность процессов резервного копирования и синхронизации в `logs/app.log`, чтобы пользователь и разработчик видели каждый шаг: факт отправки запроса в Telegram, количество прочитанных сообщений, найденный Message ID, сравнение с локальным `LastSyncedBackupMessageId` и причину принятого решения (пропуск, обновление указателя, обнаружение конфликта или накатывание базы).

### Архитектурные риски и первопричины (Root Cause Analysis):
1. **Непрозрачность фоновых операций («тихая» работа)**:
   Ранее методы `GetLatestBackupDocumentAsync` и `CheckAndSyncFromTelegramAsync` при штатных проверках, когда база не требовала обновления или когда бэкапов не было, возвращали `false` без подробных логов. В результате в журнале логов не было видно, сработал ли таймер и опрашивался ли Telegram.
   *Решение:* Внедрено подробное структурированное логирование на уровнях `Info` и `Debug` на всех этапах проверки и сопоставления.
2. **Задержка первого опроса при старте**:
   При запуске таймера `Timer(..., TimeSpan.FromSeconds(15), ...)` проверка откладывалась на 15 секунд. Для сценария быстрого открытия диска пользователем этот интервал сокращен до 5 секунд, с передачей признака первого старта (`isResumeOrStartup: true`).

### Реализованное решение:
1. `TelegramWebDAV/Services/DatabaseBackupService.cs`:
   - В `StartCloudSyncTimer()` начальная задержка первого срабатывания таймера установлена в 5 секунд (`TimeSpan.FromSeconds(5)`).
   - Введен флаг `_isFirstSyncRun`, благодаря которому первое срабатывание после старта корректно помечается как запуск при старте.
   - В `HandlePowerModeChanged` время ожидания стабилизации сети после выхода из сна также скорректировано до 5 секунд.
   - В `CheckAndSyncFromTelegramAsync` добавлено детальное логирование: причина вызова (при старте/пробуждении или по фоновому таймеру), текущие значения `LastSyncedBackupMessageId` и облачного `MessageId`, сообщение о совпадении имени устройства или о том, что база уже актуальна.
2. `TelegramWebDAV/Services/TelegramService.cs`:
   - В `GetLatestBackupDocumentAsync` добавлено логирование отправки запроса в Telegram, получения сообщений из канала (с указанием ID канала и количества сообщений), параметров найденного файла бэкапа (`MessageId`, имя файла, дата, размер в КБ) или явная фиксация отсутствия подходящих файлов.
3. - *Статус:* Пересмотрено в пользу Варианта А (решение 44) — проверка при старте перенесена непосредственно в точку входа перед монтированием диска, без использования задержек таймера.

## 44. Немедленная синхронизация базы данных из Telegram ДО монтирования виртуального диска (Вариант А)

### Бизнес-цель:
Устранить любую задержку актуализации структуры диска при старте приложения: если пользователь работал на ноутбуке/втором ПК и запустил приложение на домашнем компьютере, свежая база данных из Telegram накатывается **до** запуска WebDAV-сервера и монтирования диска WinFsp. В результате Проводник Windows и пользователь при открытии диска сразу видят 100% актуальное дерево файлов без необходимости обновления дерева «на лету».

### Архитектурные риски и первопричины (Root Cause Analysis):
1. **Гонка между открытием диска пользователем и фоновым таймером**:
   Если проверка базы отложена на таймер (даже на 5 секунд), пользователь после запуска приложения успевает открыть диск в Проводнике, увидит старое состояние файловой системы, а затем внезапно база подменяется в памяти, что требовало инвалидации кэшей и могло запутать пользователя.
   *Решение:* Перенос проверки в `Program.cs` сразу после `telegramService.ConnectAsync()`, до запуска WebDAV и монтирования WinFsp.
2. **Сохранение и показ уведомлений в трее**:
   Поскольку синхронизация завершается до создания `TrayContext` и иконки `_notifyIcon`, события `OnCloudSyncApplied` или `OnCloudSyncConflict` не имели активного подписчика в интерфейсе на момент старта.
   *Решение:* Добавлены свойства `PendingSyncNotification` и `PendingConflictNotification` в `DatabaseBackupService`. При создании `TrayContext` отложенные уведомления считываются и немедленно выводятся через BalloonTip в системном трее Windows.
3. **Разделение задач таймера и точки старта**:
   Фоновый таймер `_cloudSyncTimer` освобожден от ответственности за старт и работает исключительно на периодические проверки (раз в `intervalMinutes` минут, по умолчанию 5 мин).

### Реализованное решение:
1. `TelegramWebDAV/Program.cs`:
   - Сервис `DatabaseBackupService` инициализируется сразу после подключения к Telegram.
   - Вызывается `await backupService.CheckAndSyncFromTelegramAsync(isResumeOrStartup: true)` строго до вызовов `webDavServer.Start()` и монтирования WinFsp диска.
2. `TelegramWebDAV/Services/DatabaseBackupService.cs`:
   - Внедрены поля `_pendingSyncNotification` и `_pendingConflictNotification`, метод `ClearPendingNotifications()`.
   - При успешном накатывании базы или фиксации конфликта при старте сохраняется отложенное уведомление.
   - Таймер `StartCloudSyncTimer()` переведен на чистый периодический режим: `TimeSpan.FromMinutes(intervalMinutes)` как для начальной задержки, так и для интервала.
3. `TelegramWebDAV/UI/TrayContext.cs`:
   - В конструкторе добавлена проверка наличия `PendingSyncNotification` и `PendingConflictNotification` с моментальным показом информационного или предупреждающего всплывающего сообщения.

## 45. Удаление рудиментарной таблицы `upload_progress` и связанных методов

### Бизнес-цель и первопричина (Root Cause Analysis):
1. **Отсутствие чтения (0 SELECT-запросов):**

2. **Несоответствие архитектуре передачи файлов:**

Запись же промежуточных позиций в `upload_progress` и преждевременное обновление `nodes` с `tg_message_id = null` лишь засоряли базу незавершенными записями при сбоях передачи.
3. **Статус фичи: "Не сработало / Признано рудиментом":**
   Механизм докачки через отдельную таблицу базы данных не функционировал как полноценная докачка, усложнял схему БД и создавал ложную иллюзию отказоустойчивости при паузе в Проводнике Windows.

### Реализованное решение:
1. `TelegramWebDAV/Database/Schema.sql` и `TelegramWebDAV/Database/DatabaseManager.cs`:
   - Удалены `CREATE TABLE IF NOT EXISTS upload_progress` и индекс `idx_upload_progress_node_id`.
2. `TelegramWebDAV/Database/NodeRepository.cs`:
   - Удалены методы `UpdateUploadProgress` и `ClearUploadProgress`.
   - Из метода `CreateOrUpdateFile` удален неиспользуемый блок очистки `DELETE FROM upload_progress WHERE node_id = @nodeId`.
3. `TelegramWebDAV/Server/WebDavMiddleware.cs`:
   - В блоке обработки чанков `isResumableChunk` вызов `UpdateUploadProgress` заменен на прямую регистрацию файла через `CreateOrUpdateFile` при успешной сборке последнего куска (`uploadResult != null`). Промежуточные чанки подтверждаются статусом `202 Accepted` без паразитной модификации таблицы `nodes`.
4. `TelegramWebDAV/Models/UploadProgress.cs`:
   - Неиспользуемый класс-модель `UploadProgress` удален.
5. `db_backup.md` и `ROADMAP.md`:
   - Актуализированы спецификации, зафиксирован статус упразднения таблицы `upload_progress`.

## 46. Полное удаление устаревшего метода сборки чанков `UploadFileChunkAsync` и временных файлов `.part` на выгрузку (Zero-Temp Architecture Cleanup)

### Контекст:
В рамках перехода на архитектуру прямого потокового вещания (Zero-Temp Streaming) при выгрузке файлов с ПК в Telegram, был проведен аудит метода `UploadFileChunkAsync` и механизма сборки `.part` файлов в папке `%TEMP%/TelegramWebDAV_Uploads`.

### Первопричина и анализ (Root Cause Analysis):
1. **Атавизм старой двухэтапной архитектуры:**
   - В ранних версиях проекта выгрузка файлов осуществлялась с промежуточной буферизацией на локальный диск перед отправкой в Telegram.
   - Метод `UploadFileChunkAsync` собирал частичные фрагменты HTTP `Content-Range` во временный файл `{fileName}.part`, а затем целиком отправлял его в Telegram по завершении последнего чанка.
2. **Несоответствие целевой архитектуре Zero-Temp:**
   - Как в режиме виртуального диска WinFsp, так и в стандартном WebDAV выгрузка уже переведена на прямую потоковую передачу данных из сетевого сокета в Telegram через TCP Flow Control без создания промежуточных файлов на диске.
   - Проводник Windows и стандартные файловые менеджеры никогда не используют заголовок `Content-Range` при выгрузке (`PUT`).
3. **Критические риски и дефекты механизма `.part`:**
   - *Коллизии имен:* Имя временного файла строилось без учета пути или уникального идентификатора сессии (`{fileName}.part`), что приводило к повреждению данных при параллельной выгрузке файлов с одинаковыми именами.
   - *Утечка дискового пространства:* При сбое или отмене выгрузки на промежуточном чанке недособранный `.part` файл оставался в `%TEMP%/TelegramWebDAV_Uploads` навсегда без механизмов очистки по TTL.
   - *Отсутствие усечения:* Использование `FileMode.OpenOrCreate` без явного `SetLength` создавало риск склеивания с остаточными байтами старых файлов при повторной выгрузке с нулевого смещения.

### Реализованное решение:
1. **Удаление `UploadFileChunkAsync` (`TelegramWebDAV/Services/TelegramService.cs`):**
   - Полностью удален метод `UploadFileChunkAsync` вместе с логикой создания директории `TelegramWebDAV_Uploads` и работы с файлами `.part`.
2. **Упрощение `HandlePutAsync` (`TelegramWebDAV/Server/WebDavMiddleware.cs`):**
   - Удален разбор заголовка `Content-Range` и флаг `isResumableChunk`.
   - Все входящие `PUT` запросы унифицированы: поток данных сразу передается в `UploadFileAsync` с прямой отправкой в Telegram без промежуточных файлов на жестком диске.

## 47. Синхронизация базы данных по событию подключения к Telegram и аппаратный сторож сна (Time-Leap Watcher)

### Контекст и симптом:
При выходе компьютера из спящего режима или гибернации проверка обновлений базы данных из облака Telegram не срабатывала. В логах отсутствовала запись о фиксации пробуждения, а проверка выполнялась лишь спустя длительное время обычным фоновым таймером.

### Анализ первопричины (Root Cause Analysis):
1. **Непригодность `Microsoft.Win32.SystemEvents.PowerModeChanged` в Windows 10/11:**
   - *Статус предыдущего подхода:* **Не сработало / Отклонено.**
   - *Первопричина:* В современных ОС Windows (Windows 10, Windows 11) на большинстве устройств используется режим сна **Modern Standby (S0 Low Power Idle)** вместо классического ACPI S3. При входе и выходе из Modern Standby Windows не рассылает широковещательные оконные сообщения `WM_POWERBROADCAST` с кодами `PBT_APMSUSPEND` и `PBT_APMRESUME...`. Для их получения требуется нативная регистрация `RegisterSuspendResumeNotification`. Стандартный класс .NET `SystemEvents` не регистрирует этот обработчик и полностью игнорирует события Modern Standby, из-за чего событие `PowerModeChanged` никогда не наступало при пробуждении.
2. **Разрыв сокета WTelegram и сетевая гонка:**
   - За время сна сетевой адаптер отключался, а открытое TCP-соединение с серверами Telegram сбрасывалось маршрутизатором (`SocketException 10054: Удаленный хост принудительно разорвал существующее подключение`).
   - Внутренний реактор `WTelegramClient` выявляет разрыв и переподключается к DC спустя 6–10 секунд после первой сетевой активности. Любой слепой запуск по таймеру `Task.Delay(5000)` попадал бы в момент мертвого сокета и завершался сетевой ошибкой.

### Принятое архитектурное решение (Root Cause First):
1. **Событие `OnConnectionRestored` по факту готовности сокета Telegram:**
   - В `AppLogger` добавлено событие `OnWTelegramLog`, перехватывающее внутренние логи `WTelegramClient`.
   - В `TelegramService` реализовано событие `OnConnectionRestored`, которое вызывается при получении лога `Connected to DC` от сокетного реактора, а также при успешной авторизации.
   - Это гарантирует, что проверка базы запускается строго тогда, когда дата-центр Telegram физически доступен и хэндшейк завершен.
2. **Мгновенная реакция в `DatabaseBackupService`:**
   - Служба резервного копирования подписана на `_telegramService.OnConnectionRestored`.
   - При восстановлении связи сразу запускается `CheckAndSyncFromTelegramAsync(isResumeOrStartup: true)`.
   - Внедрен защитный интервал (Cooldown 30 сек) для предотвращения дублирующих запросов при нестабильном интернете.
3. **Аппаратный сторож сна (Time-Leap Watcher):**
   - Легкий таймер тикает каждые 10 секунд и замеряет разницу реального времени `DateTime.UtcNow`.
   - Если дельта между тиками превысила 30 секунд (компьютер спал или был в гибернации), сторож фиксирует факт сна и вызывает `_telegramService.PingOrReconnectAsync()`.
   - Пинг заставляет реактор Telegram немедленно выявить сброшенный сокет и выполнить переподключение, после чего событие `Connected to DC` сразу триггерит синхронизацию свежей базы.
4. **Удаление рудиментов:**
   - Полностью удалена неработающая подписка на `Microsoft.Win32.SystemEvents.PowerModeChanged`.

В окне настроек на вкладке «Бэкап базы» в группе «Действия с резервными копиями» строка статуса содержала длинный текст:

3. Текст гарантированно умещается в одну строку на любой ширине формы без разрывов и сдвигов элементов управления.

4. **Интерактивное обновление статистики при восстановлении**:

## 50. Поддержка файлов произвольного размера свыше 2 ГБ / 4 ГБ (Raw Binary Chunking & node_parts)

### Бизнес-цель:
Обеспечить возможность загрузки, надежного хранения, воспроизведения (стриминга) и произвольного позиционирования (Seek) для крупногабаритных файлов любого объема (4K видео 20–50 ГБ, ISO-образы систем, архивы, базы данных), многократно превышающих системные лимиты протокола Telegram MTProto (2 ГБ для обычных пользователей и 4 ГБ для Telegram Premium).

### Проблема и лимиты Telegram:
1. Серверы Telegram MTProto отклоняют документы размером свыше 2 000 МБ (~1.95 ГБ) для обычных пользователей и свыше 4 000 МБ (~3.90 ГБ) для Telegram Premium, возвращая ошибку `FILE_PARTS_TOO_MUCH` или блокируя вызов `upload.saveBigFilePart`.
2. Попытка нарезать файлы на тысячи мелких частей разрушает производительность базы данных и создает хаос в каналах Telegram.
3. Попытка хранить сегменты в общей таблице `nodes` потребовала бы добавления фильтрации во все 15+ существующих методов файловой системы (выборка каталогов, поиск, подсчет емкости) с риском появления дубликатов в Проводнике Windows.

### Архитектурное решение:

1. **Выделенная таблица `node_parts` с каскадным внешним ключом:**
   - Таблица `nodes` хранит только одну строку для файла с его реальным полным размером (например, 25 ГБ) и ID заглавного сообщения. Вся существующая логика файловой системы (`GetChildNodes`, `GetNodeByPath`, `SearchNodes`, расчет размера папок, WinFsp) остается абсолютно чистой и работает без изменений.
   - Сегменты хранятся в изолированной таблице:
     ```sql
     CREATE TABLE IF NOT EXISTS node_parts (
         id INTEGER PRIMARY KEY AUTOINCREMENT,
         node_id INTEGER NOT NULL,
         part_index INTEGER NOT NULL,
         part_size INTEGER NOT NULL,
         tg_message_id INTEGER NOT NULL,
         tg_channel_id INTEGER NOT NULL,
         created_at DATETIME DEFAULT CURRENT_TIMESTAMP,
         FOREIGN KEY (node_id) REFERENCES nodes(id) ON DELETE CASCADE,
         UNIQUE(node_id, part_index)
     );
     CREATE INDEX IF NOT EXISTS idx_node_parts_node ON node_parts(node_id);
     ```

2. **Потоковый адаптер `BoundedStream` (Zero-Temp Upload):**
   - Реализован потоковый адаптер `BoundedStream`, который читает из входящего сетевого сокета WebDAV или пайпа WinFsp ровно заданный квант части (`maxPartSize`), возвращая EOF (0 байт) для WTelegramClient без закрытия нижележащего потока.
   - Позволяет последовательно выгружать все части файла напрямую из входящего сокета без создания многогигабайтных временных файлов на системном диске C:.

3. **Связка сообщений в Telegram и разметка треда:**
   - Часть 0 загружается как заглавное сообщение в канале с обложкой/видео-превью и подписью:
     `🟢 /Путь/Файл [Часть 1 из N, total=...Bytes] #latest`.
   - Части 1..N загружаются как прямые ответы (`reply_to_msg_id = masterMessageId`), формируя аккуратный изолированный тред внутри канала, с подписью:
     `/Путь/Файл [Часть K из N, total=...Bytes]`.
   - Имена документов нумеруются по стандарту составных архивов: `${fileName}` (часть 0), `${fileName}.002`, `${fileName}.003` и т.д.
   - Автоматический расчет лимита части: 2000 МБ для обычных пользователей, 4000 МБ для Premium (или `CustomMaxUploadPartSizeBytes` из настроек).

4. **Прозрачный стриминг и произвольный Seek (`DownloadMultiPartFileAsync`):**
   - При запросе на чтение диапазона `[offset, length]` диспетчер `TelegramService.DownloadFileAsync` проверяет наличие сегментов в `node_parts`.
   - При наличии нескольких частей запрос передается в `DownloadMultiPartFileAsync`, где глобальное смещение мгновенно сопоставляется с диапазонами частей:
     - Одиночный запрос попадает ровно в нужную часть (например, перемотка на 15-й ГБ адресует сразу Часть 7 без трогания частей 0–6).
     - Запрос на стыке частей прозрачно разделяется на два подзапроса (хвост части K и голова части K+1), которые последовательно отдаются в непрерывный выходной поток `destination`.
     - Плееры (VLC, MPC-HC, AIMP) и Проводник получают цельный непрерывный поток данных.

5. **Гарантированная очистка всех частей (`EnqueuePermanentDeletion`):**
   - Метод `NodeRepository.EnqueuePermanentDeletion` при удалении узлов автоматически опрашивает `node_parts` для всех удаляемых `dbNodeIds` и помещает ID сообщений всех частей в очередь гарантированного удаления `pending_deletions`.
   - Исключена любая утечка сообщений или потерянных частей в Telegram.

## 51. Защита от накопления объектов в ОЗУ при непрерывной работе и гибернации (LRU + TTL самоочистка словарей аудита и контекстов чтения)

### Контекст и проблематика:
При непрерывной работе операционной системы Windows без перезагрузок (с частым использованием режима гибернации/сна) и активном воспроизведении или скачивании сотен файлов в памяти накапливались записи служебных словарей `TelegramService`:
1. `_networkAudits` (`ConcurrentDictionary<int, NetworkTransferAudit>`): хранит объекты сетевого аудита. Внутри каждого объекта для каждого 1 МБ чанка создаются записи в двух вложенных словарях (`_receivedChunkIndexes` и `_chunkBytesAccumulator`). Для больших файлов (2–4 ГБ) это до 4 000 элементов на файл, которые никогда не удалялись.
2. `_fileReadSequences`: история последовательного чтения и кэш прочитанных диапазонов `ChunkBytesRead`.
3. `_fileDownloadLocks`: объекты `SemaphoreSlim` для сериализации скачивания.
4. `_documentCache`: кэшированные дескрипторы `TL.Document`.

Кроме того, пожизненное сохранение `NetworkTransferAudit` приводило к тому, что при повторном просмотре фильма спустя время или после паузы счетчик `NetworkBytes` суммировал скачанный трафик за обе сессии (`2 * FileSize`), выдавая ложное предупреждение `2.00x (ВНИМАНИЕ — обнаружено избыточное дублирование сетевых запросов!)`.

### Архитектурное решение (Root Cause First):
1. **Отслеживание активности (`LastActivityTime`):**
   - В класс `NetworkTransferAudit` добавлено поле `public DateTime LastActivityTime { get; set; } = DateTime.UtcNow;` и метод `TouchActivity()`, вызываемый при любой передаче данных (`AddNetworkBytes`, `AddRamBytes`, `MarkRangeReceived`).
2. **LRU + TTL метод очистки `EnsureAuditCacheCapacity()`:**
   - Вызывается при каждом входе в `DownloadFileAsync`.
   - **TTL-очистка:** проверяет `_networkAudits` и удаляет записи, где неактивность превысила `ChunkMemoryCacheTtlMinutes` (по умолчанию от 15 до 30 минут). При удалении аудита синхронно освобождаются парные записи в `_fileReadSequences` и `_fileDownloadLocks`.
   - **LRU-вытеснение:** емкость `_networkAudits` жестко ограничена лимитом 100 наиболее активных файлов. При превышении лимита самые старые записи вытесняются.
   - **Очистка DocumentCache:** устаревшие дескрипторы документов с истекшим `expiresAt` удаляются из `_documentCache`.
3. **Бесшовный сброс для повторных сеансов:**
   - При старте `DownloadFileAsync`, если существующий аудит файла не проявлял активности дольше `cacheTtlMinutes`, он безопасно удаляется из `_networkAudits`, гарантируя, что повторный просмотр фильма или скачивание после паузы начнется с чистого листа и покажет эталонную эффективность `1.00x`.

## 53. Реализация автозапуска сервиса при входе в Windows через пользовательский реестр HKCU (`AutoStartHelper`)

### Контекст и проблема:
На первой вкладке «Сервер и Диск» в рамке «Интеграция с Windows и проводником» присутствовал чекбокс «Автозапуск сервиса при входе в Windows», привязанный к параметру `_settings.Server.AutoStartWithWindows`. Однако фактической регистрации приложения в операционной системе Windows не происходило: параметр сохранялся в `config.json`, но в реестр автозапуска Windows запись не вносилась и оттуда не удалялась.

### Архитектурное решение (Root Cause First):
1. **Утилита `AutoStartHelper` (`TelegramWebDAV/Utils/AutoStartHelper.cs`):**
   - Использует стандартную пользовательскую ветку реестра Windows `HKEY_CURRENT_USER\Software\Microsoft\Windows\CurrentVersion\Run`.
   - Работает под учетной записью текущего пользователя без необходимости повышения прав администратора (UAC).
   - Метод `IsAutoStartEnabled()` проверяет наличие и валидность строкового параметра `TelegramWebDAV`.
   - Метод `SetAutoStart(bool enable)`:
     - При `enable = true`: получает актуальный путь к текущему исполняемому файлу (`Environment.ProcessPath ?? Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "TelegramWebDAV.exe")`), экранирует кавычками и записывает в `Run`.
     - При `enable = false`: безопасно удаляет параметр `TelegramWebDAV` из реестра.
2. **Интеграция в окно настроек (`AuthSettingsForm.cs`):**
   - При инициализации формы статус чекбокса синхронизируется с реальным состоянием реестра Windows (`AutoStartHelper.IsAutoStartEnabled() || _settings.Server.AutoStartWithWindows`).
   - В обработчике `BtnSave_Click` вызывается `AutoStartHelper.SetAutoStart(_chkAutoStart.Checked)`, мгновенно применяя настройку в реестре Windows.
3. **Самовосстановление при запуске (`TrayContext.cs`):**
   - При старте трея, если в настройках включен автозапуск, вызывается `AutoStartHelper.SetAutoStart(true)`, автоматически обновляя путь к исполняемому файлу в реестре (например, при перемещении папки с программой на другой диск или путь).

## 54. Защита от шквала повторных запросов (FLOOD_WAIT) и автоматическая обработка утраченных файлов в Telegram (Root Cause First)

### Контекст и проблема:
1. При обращении сторонних медиаплееров (например, AIMP при сканировании фонотеки или воспроизведении) или Проводника к файлу, сообщение которого было удалено из Telegram (при очистке корзины или из старого бэкапа базы), `TelegramService` не находил документ (`document == null`) и выбрасывал `FileNotFoundException`.
2. В `WinFspServer.Read` ошибка перехватывалась общим блоком `catch (Exception ex)` и возвращала Windows статус `NT_STATUS_UNSUCCESSFUL` (`0xC0000001`), транслируемый в Win32-код `ERROR_GEN_FAILURE` (код 31: «Устройство не функционирует»). Плеер расценивал это как временный сбой контроллера диска и запускал серию мгновенных повторных попыток чтения (`retry`) каждые 40-50 мс.
3. В `TelegramService._documentCache` сохранялись исключительно найденные дескрипторы `TL.Document`. При отсутствии документа в кэш ничего не записывалось (отсутствовало негативное кэширование). В результате каждая повторная попытка чтения приводила к реальному сетевому MTProto RPC-запросу `GetMessages` к Telegram, что через 3-4 запроса за 140 мс приводило к `RpcError 420 FLOOD_WAIT_8` и временной блокировке всех сетевых операций сервиса.

### Архитектурное решение (Root Cause First):
1. **Негативное кэширование в `TelegramService._documentCache`:**
   - Коллекция переведена на тип `ConcurrentDictionary<int, (TL.Document? document, DateTime expiresAt)>`.
   - Если сервер Telegram подтвердил отсутствие сообщения или медиа (`TL.MessageEmpty` или отсутствие документа), факт отсутствия документа кэшируется со сроком жизни 10 минут (`_documentCache[messageId] = (null, now + 10 min)`).
   - Все последующие повторные обращения плеера или ОС мгновенно получают ответ `null` из оперативной памяти за 0.001 мс без отправки сетевых запросов в Telegram, полностью исключая `FLOOD_WAIT`.
2. **Точный код ошибки Windows NT (`NT_STATUS_OBJECT_NAME_NOT_FOUND`):**
   - В `TelegramWinFspFileSystem.Read` добавлен специализированный перехват `FileNotFoundException`: метод возвращает `NT_STATUS_OBJECT_NAME_NOT_FOUND` (`0xC0000034`).
   - Ядро Windows транслирует статус в Win32 `ERROR_FILE_NOT_FOUND` (код 2). Плеер сразу понимает, что файл отсутствует, прекращает серию повторных запросов и помечает трек недоступным.
3. **Автоматическое перемещение в корзину `.Trash` и текстовый журнал `logs/lost_files.txt` (Вариант Б):**
   - В `AppLogger` добавлен метод `LogLostFile`, записывающий понятную текстовую строку в файл `logs/lost_files.txt` (дата, путь, размер, Telegram MsgId, NodeId, причина).
   - В `NodeRepository` внедрен метод `HandleLostFile` / `HandleLostFileByMessageId`: при обнаружении удаленного из Telegram файла узел перемещается в системную корзину `.Trash` через `SoftDeleteNode(nodeId)` с полным сохранением исходной иерархии подпапок.
   - В результате файл немедленно исчезает из рабочей папки (плееры больше не спотыкаются о него), но не удаляется безвозвратно: пользователь может зайти в `.Trash` на диске и увидеть структуру утраченных файлов либо открыть `logs/lost_files.txt` в Блокноте.

## 55. Плавная бегущая строка (Marquee Ping-Pong) и адаптивная верстка всплывающего оверлея передачи (`TrayProgressOverlay`)

### Контекст и проблема:

   - Базовая ширина увеличена с `325 px` до `370 px` (современный стандарт Toast-уведомлений Windows 10/11).

2. **Плавная бегущая строка (Marquee / Ping-Pong):**
   - Убрано грубое усечение `Substring(0, 30)`.
   - Добавлен точный замер физической ширины строки в пикселях через `g.MeasureString(..., StringFormat.GenericTypographic)`.
   - Если ширина текста превышает доступные `availableWidth`:
     - Текст прокручивается по алгоритму Ping-Pong:
       - **1.8 сек** пауза на старте (пользователь спокойно читает начало названия);
       - плавный скролл влево со скоростью 32 px/сек до правого края;
       - **1.8 сек** пауза в конце (пользователь видит расширение и маркер части `[Часть 1/2]`);
       - плавный возврат на исходную позицию со скоростью 48 px/сек.
     - Отрисовка ограничена строгим клип-регионом `g.SetClip`, исключая вылезание текста за границы карточки.
   - Если текст полностью помещается или передача завершена (`_isCompleted`), он отрисовывается статично без скролла.
3. **Плавная анимация без нагрузки на CPU:**
   - Интервал таймера перерисовки `_updateTimer` оптимизирован до `35 мс` (~28.5 FPS) для плавности восприятия человеческим глазом.
   - Таймер работает исключительно во время видимости активного оверлея; при скрытии окна таймер полностью останавливается (0% CPU).

## 56. Устранение бага игнорирования настройки отображения оверлея прогресса (Root Cause First)

### Контекст и проблема:
1. В окне настроек сервиса присутствовал чекбокс «Автоматически открывать карточку прогресса при отправке файлов», привязанный к `_settings.Server.AutoShowUploadPopup`.
2. При снятии галочки и сохранении настроек всплывающее окно оверлея всё равно продолжало открываться поверх всех окон при любой передаче файлов.
3. Кроме того, название опции не отражало того, что оверлей всплывал также при скачивании файлов и чтении метаданных, а формулировка «карточка» была неудачной.

### Первопричина (Root Cause):
1. **Мёртвое свойство в коде:** В `TrayProgressOverlay.cs` было объявлено свойство `public bool AutoShowOnUpload { get; set; } = true;`, в которое `TrayContext.cs` честно передавал значение из `AppSettings`.
2. Однако внутри самого класса `TrayProgressOverlay.cs` это свойство **ни разу не читалось и не проверялось**. В методах `UpdateProgress` и `CompleteMetadata` при `!Visible` безоговорочно вызывался метод `TryShowOverlay()`, игнорируя выставленный флаг.

### Архитектурное решение (Root Cause First):
1. **Прямой контроль показа в `TrayProgressOverlay.cs`:**
   - Свойство переименовано в `AutoShowOverlay`.
   - В метод `UpdateProgress` добавлен строгий guard-clause: если окно скрыто (`!Visible`), оно открывается только если `AutoShowOverlay == true` (`if (!AutoShowOverlay || !TryShowOverlay()) return;`).
   - В метод `CompleteMetadata` добавлена аналогичная проверка `AutoShowOverlay`.
   - При выключенной опции всплывающий индикатор полностью отключается для всех операций (отправка, скачивание, чтение метаданных). При этом внутреннее отслеживание прогресса в памяти сохраняется для обновления тултипа и контекста трея.
2. **Чистое переименование без легаси-багажа:**
   - В `AppSettings.cs` параметр переименован в `AutoShowProgressOverlay`.
   - В `TrayContext.cs` свойство синхронизируется при старте и при сохранении настроек (`SettingsSaved`).
3. **Понятное название в интерфейсе (`AuthSettingsForm.cs`):**
   - Чекбокс переименован в:  
     `«Отображать индикатор прогресса операций с файлами»`.

## 57. Официальный ребрендинг проекта в TGramFS (Telegram Virtual File System)

### Контекст и предпосылки:
1. Изначально проект создавался как легковесный WebDAV-сервер для утилит бэкапа и плагина Total Commander (`TelegramWebDAV`).
2. В процессе эволюции проект перерос из простого HTTP-прокси в полноценную файловую систему Windows уровня ядра (драйвер WinFsp), обеспечивающую:
   - Прямой RAM-стриминг аудио и видео без временных файлов на диске C:.
   - Редактирование файлов «на лету» прямо на диске с атомарным версионированием и сохранением.
   - Поддержку сегментированных файлов произвольного размера свыше 2 ГБ / 4 ГБ.
3. Использование старого имени `TelegramWebDAV` вводило пользователей в заблуждение: встроенная служба Windows WebClient имеет архитектурное ограничение (скачивает файл целиком в `%TEMP%` перед открытием и имеет лимит 4 ГБ), в то время как наш основной нативный движок WinFsp работает молниеносно в ОЗУ.
4. Популярные имена вроде `tgdisk`, `tgdrive`, `teledisk`, а также `TGramDrive` уже заняты другими проектами на GitHub.

### Принятое решение:
1. Выбрано имя **`TGramFS`** (**T**ele**Gram** **F**ile **S**ystem):
   - **100% уникальность:** 0 аналогов в мире и на GitHub.
   - Честное и авторитетное отражение архитектуры: настоящая файловая система поверх Telegram.
2. **Обновление кодовой базы:**
   - В `TelegramWebDAV.csproj` выходное имя сборки переведено на `<AssemblyName>TGramFS</AssemblyName>` (бинарник компилируется как `TGramFS.exe`).
   - В `AppSettings.cs` имя тома по умолчанию обновлено до `TGramFS Drive`.
   - В `AutoStartHelper.cs` регистрация в автозапуске реестра Windows переведена на `TGramFS`.
   - В `ShellContextMenuHelper.cs` пункт меню обновлён до «Открыть корзину TGramFS».
   - В `AuthSettingsForm.cs`, `TrayContext.cs`, `TrayProgressOverlay.cs` обновлены заголовки окон, всплывающие подсказки трея и диалоговые окна.
   - В `index.html` и `README.md` обновлена официальная спецификация проекта.

   - Из метода `UnregisterTrashContextMenu()` удалены все хардкодные обращения к старым ключам `TelegramWebDAV`. Метод оперирует исключительно собственными зарегистрированными константами (`TrashMenuKeyName`, `BindChannelMenuKeyName`, `OpenInTgMenuKeyName`).

## 59. Расширение диапазона выбора букв виртуального диска (буквы от Z: до D: и AUTO)

2. **Защита сохраненной конфигурации:**
   - Значение `_settings.Server.DriveLetter` нормализуется (верхний регистр, завершающее двоеточие).
   - Если в конфигурации указана нестандартная буква (например, редкие сценарии), она гарантированно добавляется в список `Items` без сброса на дефолт.
3. **Информирование пользователя при сохранении:**
   - В методе `SaveAllSettings()` добавлено отслеживание изменения буквы диска (`oldDriveLetter != _settings.Server.DriveLetter`). При смене буквы или драйвера окно подтверждения сообщает о необходимости переподключить диск через трей или перезапустить сервис.

## 60. Фильтрация и защита от выбора занятых системных букв дисков Windows в окне настроек

### Контекст и первопричина проблемы:
1. В решении 59 в список `_cmbDriveLetter` были добавлены все буквы от `Z:` до `D:`, однако отсутствовала проверка реальной занятости букв в системе Windows.
2. В результате, если на компьютере пользователя уже существовали локальные разделы (например, `C:`, `D:`, `E:`), оптические приводы или внешние накопители, эти буквы всё равно присутствовали в списке, и их можно было выбрать и сохранить без предупреждения со стороны интерфейса.

### Принятое решение (Root Cause First):
1. **Динамическая фильтрация занятых дисков при открытии формы (`AuthSettingsForm.cs`):**
   - Вызывается опрос логических дисков Windows через `Environment.GetLogicalDrives()`.
   - Буквы, уже занятые другими физическими или сетевыми дисками ОС, исключаются из списка доступных вариантов.
   - Свой текущий смонтированный диск (`WinFspServer.ActiveMountPoint`) и текущая сохраненная настройка диска не отфильтровываются, гарантируя их доступность в списке при открытии формы.
2. **Двухуровневая валидация при сохранении (`SaveAllSettings`):**
   - Перед записью настроек выполняется повторная проверка выбранной буквы на конфликт с существующими дисками Windows.
   - Если буква занята другим устройством, сохранение блокируется с выводом понятного предупреждения в `MessageBox`.

## 61. Автоматический фоллбек на свободную букву диска при конфликте с внешними устройствами (флешки / накопители)

### Контекст и первопричина проблемы:
1. Если пользователь настроил диск на определенную букву (например, `E:`), затем закрыл программу, а позже подключил флешку или внешний накопитель, Windows назначает флешке именно букву `E:`.
2. При последующем запуске TGramFS попытка смонтировать диск на занятую букву `E:` завершалась неудачей (`ERROR_ALREADY_ASSIGNED` / 85).
3. В результате виртуальный диск вообще не появлялся в Проводнике, а пользователь оставался без доступа к файлам и без понятного уведомления о причине отсутствия диска.

### Принятое решение (Root Cause First):
1. **Интеллектуальный временный фоллбек (`VirtualDriveManager.cs`):**
   - Перед вызовом драйверов монтирования проверяется занятость целевой буквы физическими устройствами Windows через `Environment.GetLogicalDrives()`.
   - Если целевая буква занята внешним устройством, сервис автоматически находит первую доступную букву в системе (через `NetworkDriveMounter.GetFirstAvailableDriveLetter()`, например, `Z:`) и монтирует диск на неё.
   - Свойства `RequestedLetter` и `IsFallbackActive` фиксируют состояние временного переназначения.
   - **Сохраненные настройки не затираются:** в `appsettings.json` остается исходная буква (например, `E:`). После отключения конфликтующей флешки и перезапуска или переподключения диск автоматически возвращается на родную букву.
2. **Прозрачное информирование пользователя в трее (`TrayContext.cs`):**
   - При старте сервиса и при переподключении, если активирован фоллбек, выводится Toast/Balloon уведомление:
     `Буква E: занята другим устройством (флешкой/диском). Диск временно смонтирован как Z:`.
   - Пункты контекстного меню («Открыть диск (Z:)», «Открыть корзину (Z:\.Trash)») и методы открытия каталогов динамически используют реально смонтированную букву `MountedLetter`.

## 65. Устранение ложных логов синхронизации базы при выходе из сна Windows (Root Cause First)

### Контекст и симптомы:
Пользователь отключил в настройках флаг «Проверять наличие свежей базы в Telegram» (`CheckForRemoteOnStartup = false`). Однако при выходе Windows из режима сна в журнале `app.log` всё равно появлялись записи уровня `INFO`:
```
[DatabaseBackup] [Синхронизация] Зафиксирован выход Windows из сна/гибернации (временной скачок: 4923 сек). Ожидание подключения к Telegram...
[DatabaseBackup] [Синхронизация] Получен сигнал подключения к Telegram (Connected to DC). Запуск проверки свежей базы...
```
Это создавало ложное впечатление, что сервис игнорирует отключение настройки и выполняет проверку базы.

### Первопричина (Root Cause Analysis):
1. В `DatabaseBackupService.StartHeartbeatTimer` сторожевой таймер отслеживания скачков времени логировал системное событие пробуждения ОС под категорией `DatabaseBackup` с тегом `[Синхронизация]`, хотя его реальная цель — пинг и выявление разорванного сокета MTProto для общего коннекта Telegram (`_telegramService.PingOrReconnectAsync()`).
2. В `DatabaseBackupService.HandleTelegramConnectionRestored` информационный лог `[Синхронизация] Получен сигнал подключения к Telegram... Запуск проверки свежей базы...` выводился до проверки настройки `settings.CheckForRemoteOnStartup`. Затем в фоновой задаче вызывался `CheckAndSyncFromTelegramAsync`, который сразу прерывался по условию `!settings.CheckForRemoteOnStartup` с выводом в уровень `Debug`, но пользователь в консоли/файле видел только предшествующий лог `INFO`.

### Принятое решение (Root Cause First):
1. В `HandleTelegramConnectionRestored` добавлена строгая предварительная проверка: если `settings.CheckForRemoteOnStartup` выключен (`false` или `null`), обработчик мгновенно выходит (`return`) без записи логов уровня `INFO` и без запуска фоновых задач.
2. В `StartHeartbeatTimer` категория лога изменена на системную `TelegramService` без вводящего в заблуждение префикса `[Синхронизация]`:
   `[TelegramService] Зафиксирован выход Windows из сна/гибернации (временной скачок: N сек). Проверка связи с Telegram...`
3. Логи стали на 100% честными и прозрачными: при отключенной проверке базы никаких записей о запуске проверки больше не формируется.

## 66. Внедрение полноценной многослойной иконки приложения и устранение бага отсутствия иконки в трее (Root Cause First)

### Контекст и симптомы:
1. В Проводнике Windows исполняемый файл `TGramFS.exe`, а также пункты контекстного меню («Привязать папку к отдельному каналу Telegram») и значок окна на панели задач отображались сплошным синим квадратом.
2. В системном трее Windows (область уведомлений рядом с часами) иконка приложения отсутствовала либо отображалась некорректно.

### Первопричина (Root Cause Analysis):
1. **Сплошной синий квадрат:** Исходный файл `TelegramWebDAV/icon.ico` представлял собой тестовую 16x16 растровую заглушку размером всего 1118 байт, где абсолютно все пиксели имели сплошной цвет `(34, 149, 237)` (`#2295ed`) без прозрачности, альфа-канала и рисунка. Windows растягивала этот 16x16 синий блок на крупные значки проводника, контекстное меню и панель задач.
2. **Отсутствие иконки в трее:** В `TrayContext.cs` инициализация компонента `NotifyIcon` содержала явный вызов устаревшей системной заглушки:
   `Icon = SystemIcons.Application`
   Приложение вообще не пыталось использовать собственную иконку. В современных версиях Windows 10/11 старый значок `SystemIcons.Application` из эпохи Windows 95 на темной панели задач либо сливался, либо вытеснялся системой в скрытую область трея под стрелку `^`.
3. **Панель задач:** Окно настроек `AuthSettingsForm.cs` не назначало свойство `this.Icon`, наследуя системное поведение.

### Принятое решение (Root Cause First):
1. **Многослойная иконка:** Заменен файл `TelegramWebDAV/icon.ico` на полноценный системный пакет иконок высокого качества со слоями: `16x16`, `32x32`, `48x48`, `64x64`, `128x128` и `256x256` (32 bpp с альфа-прозрачностью).
2. **Копирование иконки в билд:** В `TelegramWebDAV.csproj` файл `icon.ico` включен в `<None Update="icon.ico"><CopyToOutputDirectory>PreserveNewest</CopyToOutputDirectory></None>`, обеспечивая доступность как в ресурсах `.exe`, так и в рабочей директории.
3. **Загрузка иконки в системный трей:** В `TrayContext.cs` реализовано автоматическое извлечение ассоциированной иконки приложения через `Icon.ExtractAssociatedIcon(Environment.ProcessPath ?? Application.ExecutablePath)` с безопасным откатом на `Path.Combine(AppDomain.CurrentDomain.BaseDirectory, "icon.ico")` и лишь затем на `SystemIcons.Application`.
4. **Загрузка иконки формы настроек:** В `AuthSettingsForm.InitializeComponents()` свойству `this.Icon` явно присваивается извлеченная иконка приложения, гарантируя отображение правильного логотипа в заголовке окна и на панели задач Windows.

   После чего лог замирал на несколько минут без повторных попыток переподключения.

### Первопричина (Root Cause Analysis):
1. **Гонка готовности Wi-Fi адаптера:** `DatabaseBackupService.StartHeartbeatTimer` при обнаружении скачка времени (`elapsed >= 30s`) немедленно вызывал `PingOrReconnectAsync()` на 0-й миллисекунде, когда сетевой адаптер Windows еще восстанавливал связь с точкой доступа и не получил локальный IP-адрес по DHCP. Это приводило к гарантированному падению основного адреса DC2 (`149.154.167.41`) с ошибкой `SocketException 10065 HostUnreachable`.
2. **Отсутствие таймаута на сокетах в WTelegramClient:** Стандартный `TcpHandler` библиотеки вызывает `new TcpClient().ConnectAsync(host, port)` без таймаута, полностью полагаясь на таймаут ядра ОС. Когда библиотека перебирала альтернативные адреса DC и доходила до IPv6 `[2001:67c:4e8:f002::a]:443`, отсутствие IPv6-шлюза приводило к безответным TCP SYN запросам. Windows запускала экспоненциальный повтор пакетов (`TcpMaxConnectRetransmissions`), удерживая вызов сокета заблокированным от 21 до 75+ секунд. При этом ошибки сокета во внутреннем цикле `DcOptions` перехватывались библиотекой молча (`catch (SocketException) { continue; }`), создавая иллюзию «зависания» без логов.
3. **Холостой прожиг процессора на 100% (Tight Loop при `ReactorError`):** В декомпилированном коде `WTelegramClient.Client.Invoke` метод крутится в бесконечном цикле `do { ... } while (true)`. При сбое реактора все ожидающие RPC-задачи получают результат `ReactorError`. Так как `ReactorError` не является ни результатом `T`, ни `RpcError`, метод `Invoke` немедленно уходил на `continue;` и без единой паузы непрерывно спамил попытками отправки по упавшему сокету, разогревая процессор до 100%.
4. **Синхронная блокировка потоков WinFsp:** При попытке открыть документ Проводник вызывал `WinFspServer.Read()`, который синхронно через `.GetAwaiter().GetResult()` ждал чанк от зависшего воркера Telegram, вешая весь системный Проводник.

### Принятое решение (Root Cause First):
1. **Асинхронная проверка готовности сети при выходе из сна (`WaitForNetworkAvailableAsync`):**
   В `DatabaseBackupService.StartHeartbeatTimer` перед отправкой сетевого пинга добавлен вызов `WaitForNetworkAvailableAsync(TimeSpan.FromSeconds(7))`, опрашивающий `NetworkInterface.GetIsNetworkAvailable()` каждые 500 мс. Пинг и восстановление сокета запускаются только тогда, когда Wi-Fi адаптер физически поднялся и стабилизировался. Если сеть недоступна, проверка откладывается до следующего тика таймера.
2. **Контролируемый таймаут на сокетах (`SafeTcpHandlerAsync`):**
   В `TelegramService.InitClient` переопределен фабричный делегат `_client.TcpHandler = SafeTcpHandlerAsync`. При вызове `tcpClient.ConnectAsync(host, port, cts.Token)` задан жесткий таймаут в 5 секунд. При его превышении сокет немедленно освобождается, а наверх выбрасывается `SocketException(SocketError.TimedOut)`, благодаря чему WTelegramClient мгновенно переходит к следующему адресу без многоминутных системных зависаний.
3. **Подписка на сбои реактора (`_client.OnOther`):**
   В `TelegramService` реализован обработчик `HandleClientOtherAsync`, перехватывающий `TL.ReactorError` и предотвращающий бесконечный цикл за счет плавного отложенного восстановления сессии через `Task.Delay(3000)`.
4. **Защита потоков файловой системы (`WinFspServer.Read Timeout`):**
   В методе `WinFspServer.Read` ожидание скачивания чанка защищено таймаутом `downloadTask.Wait(TimeSpan.FromSeconds(25))`. При отсутствии ответа возвращается статус ядра `NT_STATUS_IO_TIMEOUT` (`0xC00000B5`), что предотвращает зависание Проводника Windows.

## 68. Автоматическое самовосстановление сессии Telegram при ручном отключении/включении сети Windows (Root Cause First)

### Контекст и симптомы:
При ручном отключении Wi-Fi или сетевого кабеля во время работы системы (без ухода компьютера в сон) на время более 30–40 секунд:
1. `WTelegramClient` отправлял `PingDelayDisconnect`, не получал ответа по таймауту сокета (`10060`), делал 5 попыток переподключения по адресам DC и падал с ошибкой `SocketException 10065 HostUnreachable`.
2. После исчерпания 5 попыток внутренний поток реактора WTelegram окончательно умирал, генерируя событие `TL.ReactorError`.
3. Одиночный пинг через 3 секунды запускался, пока Wi-Fi ещё был выключен, и завершался неудачей.
4. Когда пользователь через 20–30 секунд включал Wi-Fi обратно, связь с Telegram автоматически не восстанавливалась, так как:
   - Сторожевой таймер сна не срабатывал (система не уходила в гибернацию/сон, `elapsed` был в пределах нормы ~10 сек).
   - В приложении отсутствовала подписка на системные сетевые события операционной системы Windows.
   - Старый экземпляр `_client` с упавшим реактором не утилизировался и не пересоздавался заново.

### Первопричина (Root Cause Analysis):
1. **Однократность попытки самовосстановления:** При падении реактора запускалась единичная проверка сокета с фиксированной задержкой в 3 секунды. Если в этот момент интернет отсутствовал, сервис прекращал дальнейшие попытки.
2. **Отсутствие реакции на события ядра Windows:** Приложение не отслеживало системные нотификации `System.Net.NetworkInformation.NetworkChange.NetworkAvailabilityChanged`, из-за чего момент физического включения Wi-Fi адаптера игнорировался.
3. **Требование WTelegram к полному перезапуску клиента:** В соответствии с архитектурой `WTelegramClient` (пример `Program_ReactorError.cs`), если реактор умер, вызовы методов на старом экземпляре бессмысленны. Необходимо полностью вызвать `Dispose()` старого клиента, обнулить ссылку и выполнить новый `ConnectAsync()` с созданием чистого экземпляра `WTelegram.Client`.

### Принятое решение (Root Cause First):
1. **Системная подписка на сетевые события Windows (`NetworkChange.NetworkAvailabilityChanged`):**
   В конструкторе `TelegramService` оформлена подписка на событие `NetworkChange.NetworkAvailabilityChanged`. При включении Wi-Fi или подключении Ethernet Windows немедленно передает сигнал в сервис, который мгновенно инициирует `TriggerReactorReconnect("восстановление сетевого интерфейса Windows")`. При штатной утилизации сервиса подписка корректно снимается в `Dispose()`.
2. **Потокобезопасный цикл самовосстановления (`TriggerReactorReconnect`):**
   Внедрен надежный фоновый процесс с защитой от одновременных запусков (`Interlocked.CompareExchange`):
   - Если клиент жив, делает быстрый проверочный пинг `Help_GetNearestDc`.
   - Если сокет мертв, запускается цикл ожидания сети с шагом 5 секунд.
   - Как только `NetworkInterface.GetIsNetworkAvailable() == true`, выполняется полный `Dispose()` старого клиента, сброс `_client = null` и `_storagePeer = null`, и вызов `ConnectAsync()`.
   - Цикл завершается только при успешной авторизации `IsAuthorized == true`.
3. **Безопасная обработка в `ConnectAsync`:**
   Из блока `catch` метода `ConnectAsync` удален принудительный сброс авторизации в `NeedsPhone` при сетевых ошибках (`SocketException`, `IOException`). Ошибка пробрасывается наверх в цикл восстановления, сохраняя сессию пользователя.

## 69. Восстановление внедрения зависимости NodeRepository в TelegramService и защита проверочных пингов после сна (Root Cause Fix)

### Контекст и симптомы:
1. При старте службы и первой попытке чтения файлов пользователь получал ошибку ядра:
   `[ERROR] [WinFsp] Ошибка прямого чтения: One or more errors occurred. (Клиент Telegram не подключен или не авторизован.)`
2. При отключении и повторном включении интернета или после выхода ПК из гибернации/сна (временной скачок 8072 сек) в логе фиксировалось:
   `[INFO ] [TelegramService] [Network] Зафиксировано появление активного сетевого подключения Windows.`
   Однако самовосстановление соединения с Telegram не запускалось, и файлы оставались недоступны с той же ошибкой неавторизованного клиента.

### Первопричина (Root Cause Analysis):
1. **Потеря ссылки на `NodeRepository` в точке композиции корня приложения (`Program.cs`):**
   При инициализации сервисов `TelegramService` создавался через `new TelegramService(configManager)` вместо `new TelegramService(configManager, repository)`.
   Внутри сервиса поле `_repository` оставалось `null`.
2. **Блокировка авторизации и циклов самовосстановления из-за `_repository == null`:**
   - В `ConnectAsync()` вызов `_repository?.GetActiveTelegramAccount()` возвращал `null`, из-за чего сервис мгновенно сбрасывал флаг `IsAuthorized = false` и выходил, даже не пытаясь загрузить сессию с диска.
   - В `TriggerReactorReconnect()` проверка `var account = _repository?.GetActiveTelegramAccount(); if (account == null) return;` приводила к мгновенному холостому выходу при любых сетевых событиях операционной системы Windows.
3. **Отсутствие таймаута на проверочный пинг в `TriggerReactorReconnect` и пассивный `PingOrReconnectAsync`:**
   - При проверке полумертвого TCP-сокета вызов `_client.Help_GetNearestDc()` мог зависать в ожидании ответа до системного таймаута ядра.
   - Метод `PingOrReconnectAsync()` при выходе из сна в случае исключения сокета лишь логировал отладочное сообщение `DEBUG`, но не вызывал активное самовосстановление сессии. Если же клиент был не авторизован, метод сразу выходил (`return`).

### Принятое решение (Root Cause First):
1. **Передача `NodeRepository` в конструктор (`Program.cs`):**
   Вызов обновлен до `new TelegramService(configManager, repository)`. `_repository` гарантированно доступен с момента старта процесса, сессия `user.session` корректно подгружается, и авторизация проходит успешно.
2. **Прозрачность и контроль аккаунта в `TriggerReactorReconnect` (`TelegramService.cs`):**
   Если аккаунт не найден в БД, в лог записывается явное предупреждение `AppLogger.Warn`, исключая скрытые выходы.
   Проверочный пинг `_client.Help_GetNearestDc()` защищен жестким 5-секундным таймаутом через `Task.WhenAny`: если сокет подвис и не ответил за 5 секунд, сессия немедленно отправляется на пересоздание без зависаний.
3. **Активное самовосстановление после сна в `PingOrReconnectAsync` (`TelegramService.cs`):**
   - Если при выходе из сна клиент оказался не подключен или не авторизован, метод немедленно запускает `TriggerReactorReconnect("пробуждение системы при неактивном клиенте")`.
   - Пинг после сна защищен таймаутом 5 секунд: при таймауте или сетевой ошибке сразу вызывается `TriggerReactorReconnect`, гарантируя поднятие соединения.

## 70. Гибридное самовосстановление: легкий TCP-зонд (Socket Probe), прерывание сна через `NetworkAddressChanged` и адаптивный бэкофф (Root Cause First)

### Контекст и симптомы:
1. При отключении интернета (или при физическом выключении Wi-Fi на ПК с включенными виртуальными сетевыми картами WSL, Hyper-V, VMware) в лог непрерывно спамились сообщения каждые 5 секунд:
   `[INFO ] [TelegramService] [Reactor] Попытка #N: Сеть Windows доступна. Пересоздание клиента WTelegram и переподключение...`
   `[ERROR] [WTelegram] SocketException HostUnreachable (10065): Сделана попытка выполнить операцию на сокете для недоступного хоста.`
2. За несколько минут отсутствия интернета в лог записывались сотни однотипных ошибок (попытки #1–#20+).
3. Каждые 5 секунд сервис впустую читал с SSD файл `user.session`, создавал новый экземпляр `WTelegram.Client` и утилизировал его при неизбежной ошибке сокета.

### Первопричина (Root Cause Analysis):
1. **Ложноположительный статус сети:** Системный метод `NetworkInterface.GetIsNetworkAvailable()` проверяет лишь наличие интерфейсов со статусом `Up`. При наличии виртуальных адаптеров или активной связи с роутером (даже без внешнего интернета) метод всегда возвращает `true`.
2. **Тяжелые холостые итерации (Brute-Force Retry):** Вместо легкой проверки маршрутизации сервис на каждом тике выполнял полное пересоздание клиента, чтение диска и инициализацию сессии WTelegram.
3. **Фиксированный интервал без бэкоффа:** Жесткая 5-секундная задержка не давала системе успокоиться при длительном отсутствии интернета.

### Принятое решение (Root Cause First):
1. **Сверхлегкий сокет-зонд (`ProbeTelegramConnectivityAsync`):**
   Перед тем как трогать файл сессии и создавать `WTelegram.Client`, сервис выполняет мгновенный проверочный TCP-запрос к дата-центру Telegram (`149.154.167.50:443`, при необходимости `149.154.167.41:443`) с таймаутом 2.5 сек.
   Если маршрут отсутствует (`HostUnreachable`) или сокет не отвечает, диск не трогается, `WTelegram.Client` не создается, а ресурсы CPU/I/O остаются на 0%.
2. **Мгновенное прерывание ожидания через системные события Windows (`NetworkAddressChanged` + `NetworkAvailabilityChanged`):**
   Оформлена подписка на `NetworkChange.NetworkAddressChanged` (реагирует на включение адаптера, смену шлюза и перестроение маршрутов даже при статическом IP). При возвращении адаптера Windows посылает сигнал, мгновенно сбрасывающий текущую паузу через `_reconnectWaitCts?.Cancel()`, и подключение поднимается за 1 секунду.
3. **Адаптивный бэкофф и тихий режим:**
   Интервал ожидания плавно масштабируется: 1-я попытка — 5 с, 2-я — 10 с, последующие — 25 с. 
   Повторяющиеся сообщения о недоступности маршрута скрыты из основного лога (выводятся не чаще одного раза в минуту), избавляя журнал от спама.

## 71. Полный отказ от жестко зашитых IP-адресов серверов Telegram и делегирование перебора дата-центров WTelegramClient (Root Cause First)

### Контекст и симптомы:
1. В решении 70 в метод сокет-зонда были временно зашиты IP-адреса DC2 (`149.154.167.50` и `149.154.167.41`).
2. При выполнении системного DNS-запроса `nslookup api.telegram.org` пользователь обнаружил другой IP (`149.154.166.110`), а пользователи из других географических регионов регистрируются на иных дата-центрах (DC1 Майами, DC3, DC4, DC5 Сингапур).
3. Жесткая привязка к статическим IP в коде создавала риски несовместимости при смене дата-центров или изменении сетевой топологии Telegram.

### Принятое решение (Root Cause First):
1. **Полное удаление хардкодных IP-адресов из кодовой базы:**
   Методы `ProbeTelegramConnectivityAsync` и `QuickTcpConnectAsync` со статическими адресами полностью удалены.
2. **Делегирование перебора адресов библиотеке `WTelegramClient`:**
   В цикле самовосстановления вызывается `await ConnectAsync(isSilentRetry: ...)`. Библиотека WTelegram сама динамически извлекает актуальный список IP-адресов и портов своего целевого дата-центра из файла сессии `user.session` (`DcOptions`, IPv4 и IPv6).
3. **Режим тихого переподключения (`isSilentRetry`):**
   В `ConnectAsync` добавлен флаг `isSilentRetry`:
   - При штатном запуске приложения выводятся полные информационные логи и конфигурация стриминга.
   - В цикле фонового ожидания сети при отключенном интернете отладочные ошибки сокета подавляются (лог уровня DEBUG), а сводный статус ожидания выводится в лог не чаще одного раза в минуту, предотвращая разрастание файла лога.
4. **Сохранение адаптивного бэкоффа и мгновенного прерывания Windows:**
   Сохранен адаптивный интервал (5 с -> 10 с -> 25 с) с мгновенным сбросом паузы по системным событиям ядра Windows `NetworkAddressChanged` и `NetworkAvailabilityChanged`.

## 72. Легковесный TCP-зонд к `api.telegram.org:443` перед инициализацией WTelegram и троттлинг сетевых событий ядра Windows (Root Cause First)

### Контекст и симптомы:
1. При пробуждении ноутбука после сна (14 часов офлайна) Wi-Fi адаптер находился в процессе подключения к роутеру (согласование DHCP, IPv4, IPv6, шлюза).
2. За 2.5 секунды ядро Windows сгенерировало несколько последовательных событий `NetworkAddressChanged` и `NetworkAvailabilityChanged`, каждый раз мгновенно сбрасывая таймер бэкоффа. Это приводило к быстрым попыткам создания `WTelegramClient` с ошибками `HostUnreachable (10065)` до завершения настройки сетевого стека.
3. После успешного подключения сессии на 5-й попытке (спустя 6.5 сек после выхода из сна) Windows еще в течение 6 секунд рассылала события настройки DNS и маршрутов. На каждое событие сервис отправлял избыточный проверочный RPC-запрос `Help_GetNearestDc` («Соединение живо, реактор успешно ответил») 4 раза подряд, хотя сокет уже был активен.

### Принятое решение (Root Cause First):
1. **Динамический DNS/TCP-зонд к `api.telegram.org:443` (`CheckTelegramReachabilityAsync`):**
   - Перед созданием экземпляра `WTelegramClient`, чтением сессии и перебором ДЦ сервис выполняет быстрый зонд (таймаут 2.5 сек) к официальному домену Telegram `api.telegram.org:443` по протоколу TCP HTTPS.
   - Использование доменного имени вместо фиксированных IP гарантирует автоматическое разрешение через системный DNS и независимость от географического расположения пользователя.
   - Если `api.telegram.org:443` не отвечает (Wi-Fi еще не согласовал шлюз/DHCP), `WTelegramClient` вообще не создается, сокетные ошибки `HostUnreachable` не генерируются, а процесс ожидает появления связи.
   - Как только `api.telegram.org:443` отвечает, подключение WTelegram выполняется с первой попытки.
2. **Троттлинг сетевых событий при живом соединении (`_lastSuccessfulTrafficTime`):**
   - Отслеживается время последнего успешного сетевого взаимодействия с Telegram (`Pong`, `RpcResult`, `Connected to DC`, `Receiving Updates` или `Help_GetNearestDc`).
   - Если сессия уже авторизована и активный трафик был менее 15 секунд назад, входящие сигналы `NetworkAddressChanged` и `NetworkAvailabilityChanged` от ядра Windows игнорируются, исключая серию холостых запросов `Help_GetNearestDc`.
3. **Интеграция с `DatabaseBackupService`:**
   - Метод `WaitForNetworkAvailableAsync` при выходе из сна ожидает не только абстрактного флага `GetIsNetworkAvailable()`, но и реального ответа `CheckTelegramReachabilityAsync(1500)`, исключая преждевременные сбои сокетов.

## 73. Восстановление индикации прогресса при повторном скачивании и перемотке видео (Root Cause First)

### Контекст и симптомы:
1. При повторном скачивании файла или повторном открытии видео в медиаплеере плашка прогресса `TrayProgressOverlay` не отображалась вовсе.
2. Проблема наблюдалась даже на файлах большого размера (1–4 ГБ), которые заведомо не помещаются целиком в кэш ОЗУ и повторно запрашиваются из сети Telegram через воркеры MTProto.
3. При просмотре видео с перемотками назад шкала прогресса плашки залипала на максимальной когда-либо достигнутой позиции, а расчет мгновенной скорости и расчет оставшегося времени (ETA) искажались.

### Первопричина (Root Cause Analysis):
1. **Паразитное глушение сетевого прогресса флагом `audit.IsAllChunksReceived()`:**
   В `TelegramService.cs` перед вызовом события `OnDownloadProgress` стояло условие `if (!audit.IsAllChunksReceived())`. Объект `NetworkTransferAudit` кэшируется по `messageId` на 30 минут. После первого успешного завершения скачивания все чанки отмечались как полученные (`IsAllChunksReceived() == true`), из-за чего при любом последующем сетевом скачивании того же файла в течение 30 минут условие `!audit.IsAllChunksReceived()` возвращало `false`, наглухо блокируя отправку событий `OnDownloadProgress` в UI.
2. **Залипание состояния завершения в скрытом оверлее:**
   В `TrayProgressOverlay.cs` метод `CompleteTransfer` при `Visible == false` (например, скачивание завершилось до всплытия плашки) выставлял флаг `_isCompleted = true`, но не запускал таймер `_completionTimer`, из-за чего `_isCompleted` не сбрасывался в `false` и отсекал последующие вызовы для этого файла.
3. **Монотонный фильтр `Math.Max` при перемотке (Seek):**
   В `TrayProgressOverlay.UpdateProgress` вычислялось `_currentBytes = Math.Max(_currentBytes, current)` для защиты от джиттера параллельных воркеров при линейной загрузке. При перемотке видео назад (Seek) позиция `current` уменьшалась, но `_currentBytes` удерживал максимальное смещение хвоста файла.

### Принятое решение (Root Cause First):
1. **Разделение сетевой аналитики и событий UI (`TelegramService.cs`):**
   - Убрано паразитное условие `!audit.IsAllChunksReceived()` из обработчиков прогресса в `DownloadSingleDocumentSliceAsync` и `TriggerContinuousPrefetch`. Если воркер MTProto физически скачивает байты из сети Telegram, событие `OnDownloadProgress` гарантированно передается в UI.
   - В `NetworkTransferAudit` добавлен метод `ResetCompletion()`, который сбрасывает флаг завершения `_completionLogged` при новом старте скачивания с `offset == 0` (`!isMetadataProbe`). Структура аудита и подсчет сетевых байтов/ОЗУ остались полностью неизменными и целостными.
2. **Интеллектуальная обработка перемоток и джиттера (`TrayProgressOverlay.cs`):**
   - В `UpdateProgress` при откате смещения назад более чем на 2 МБ (`current < _currentBytes - 2 МБ` или `_currentBytes >= total`) фиксируется перемотка назад: `_currentBytes` актуализируется на текущее значение `current`, а таймер скорости сбрасывается для чистого расчета текущей скорости и ETA.
   - Фильтр игнорирования повторных обновлений завершенного файла активен только пока реально тикает таймер показа статуса завершения (`_completionTimer.Enabled`). По истечении таймаута плашка готова к новым сессиям передачи.
   - В `CompleteTransfer` при вызове для скрытого оверлея (`!Visible`) состояние завершения сбрасывается немедленно.

## 74. Единый режим тихого фонового опроса сети (Silent Reachability Polling) при потере интернета и выходе из сна/гибернации (Root Cause First)

### Контекст и симптомы:
1. При отключении интернета (разрыв соединения, отсутствие Wi-Fi, долгий офлайн) или выходе ноутбука из сна/гибернации в лог выводилось множество предупреждений и промежуточных сообщений о недоступности сети.
2. Даже при подавлении ошибок WTelegram адаптивный бэкофф с периодичностью в 1 минуту продолжал выводить строки `Серверы Telegram пока недоступны. Ожидание появления сети...`, засоряя `app.log`.
3. Системные события сетевых адаптеров Windows (`NetworkAddressChanged`, `NetworkAvailabilityChanged`) при согласовании DHCP или смене IPv6-маршрутов выводили в лог технические записи и повторные запросы проверки сессии.
4. В `DatabaseBackupService.StartHeartbeatTimer` при выходе из сна сетевой стек опрашивался в течение 7 секунд, после чего выводилось предупреждение `Сетевой интерфейс не готов... Проверка связи отложена до следующего тика`, и управление зависало до спонтанных внешних событий.

### Первопричина (Root Cause Analysis):
Разрозненная реакция нескольких служб на разрыв сети и отсутствие строгого правила «однократное предупреждение при обрыве -> полная тишина во время офлайна -> однократное уведомление при восстановлении». Попытки периодического логирования статуса в цикле ожидания создавали шум без какой-либо практической пользы для пользователя.

### Принятое решение (Root Cause First):
1. **Строго однократное логирование обрыва связи (`hasLoggedOffline`):**
   - При сбое сокета, разрыве соединения или выходе из сна без интернета в лог выводится **ровно одна информативная строка**:
     `[WARN ] [TelegramService] [Reactor] Сеть недоступна ({reason}). Ожидание подключения к интернету...`
   - Переменная `hasLoggedOffline = true` блокирует любые последующие записи в лог на все время нахождения устройства в офлайне (даже если ноутбук без сети находится часами).
2. **Абсолютно тихий фоновый TCP-зонд (`CheckTelegramReachabilityAsync`):**
   - В фоновом потоке каждые 3 секунды выполняется легковесный TCP HTTPS-зонд к `api.telegram.org:443`.
   - Во время офлайна в лог пишется **0 строк**: никаких сообщений раз в минуту, никаких `HostUnreachable`, никаких созданий `WTelegramClient` и чтения файлов сессии.
3. **Бесшумное ускорение по событиям ядра Windows:**
   - Обработчики `OnNetworkAvailabilityChanged` и `OnNetworkAddressChanged` переведены в полностью бесшумный режим (удален весь лог-шум). При получении системного сигнала о поднятии интерфейса они лишь сбрасывают текущую 3-секундную паузу `_reconnectWaitCts?.Cancel()`, позволяя мгновенно проверить `api.telegram.org:443` без ожидания истечения таймера.
4. **Бесшовная передача управления из `DatabaseBackupService`:**
   - При фиксации временного скачка (выход из сна/гибернации) таймер делает прямой зонд `CheckTelegramReachabilityAsync(2000)`.
   - Если сеть недоступна, служба не выводит предупреждений и не запускает холостых циклов ожидания, а сразу передает задачу в `TriggerReactorReconnect("выход из сна без подключения к сети")`.
5. **Чистый старт сессии при появлении связи:**
   - Как только зонд `api.telegram.org:443` успешно соединяется, выводится сообщение:
     `[INFO ] [TelegramService] [Reactor] Подключение к интернету подтверждено (api.telegram.org доступен). Запуск сессии Telegram...`
   - Инициируется `ConnectAsync()`, и после авторизации выводится:
     `[INFO ] [TelegramService] [Reactor] Сессия Telegram успешно восстановлена!`

## 75. Устранение дублирующего лога запуска WebDAV-сервера (Root Cause First)

### Симптом:
При старте приложения в `app.log` фиксировались два одинаковых сообщения об успешном запуске WebDAV в одну и ту же миллисекунду:
```
[2026-10-27 01:02:40.178] [INFO ] [WebDAV] WebDAV Сервер запущен на http://localhost:37000/
[2026-10-27 01:02:40.178] [INFO ] [Program] Встроенный WebDAV сервер запущен: http://localhost:37000/
```

### Первопричина (Root Cause Analysis):

3. В случае сбоя запуска (например, занят порт `37000`) `WebDavServer` перехватывал исключение и писал ошибку, а `Program.cs` ошибочно сообщал об успешном запуске.

### Принятое решение:
* Удалена дублирующая строка логирования из `Program.cs`. Логирование успешного запуска сохранено исключительно внутри `WebDavServer.Start()`, что гарантирует его вывод строго при действительно поднятом `HttpListener`.

## 76. Устранение задвоения лога источника копирования и надежное извлечение длительности/разрешения MKV (Root Cause First)

### Контекст и симптомы:
1. При перетаскивании (Drag-and-Drop) или вставке файлов на диск в логе дважды подряд выводилось идентичное сообщение:
   `[WinFsp] [Источник] НАЙДЕНО СОВПАДЕНИЕ! Оригинальный файл '...' существует и доступен для чтения (размер: ... байт).`
2. Для видеофайлов формата MKV (`.mkv`) библиотека `z440.atl.core` завершалась сбоем `NullReferenceException` (`Object reference not set to an instance of an object`). Последующий вызов генерации эскиза Windows Shell (`IThumbnailProvider`) возвращал превью размером `320x180`, однако длительность видео оставалась равной `0 сек`, а исходное разрешение подменялось размером превью (`320x180`), передаваясь в Telegram атрибутами `TL.DocumentAttributeVideo(duration = 0, w = 320, h = 180)`.

### Первопричина (Root Cause Analysis):
1. **Задвоение лога:** Метод физической проверки `VerifyReadable(filePath)` уже выводил сообщение об успешном совпадении и доступности файла для чтения. Сразу после возврата из поиска метод `ResolveSourceCopySession` повторно выводил такое же сообщение на уровне активной и новой сессии.
2. **Отсутствие извлечения метаданных MKV:**
   - Парсер `ParseMp4Full` обрабатывал только контейнеры MP4/MOV.
   - ATL.NET 6.1.0 падал на MKV файлах без стандартных глав/тегов (например, созданных программами захвата экрана).
   - Shell `IThumbnailProvider` принципиально возвращает только графический HBITMAP, не считывая тайминги контейнера.

### Принятое решение (Root Cause First):
1. **Удаление дублирования лога (`WinFspServer.cs`):**
   - Убран повторный вызов `AppLogger.Info("WinFsp", "[Источник] НАЙДЕНО СОВПАДЕНИЕ!...")` в ветках активной и новой сессий `ResolveSourceCopySession`. Логирование выполняется строго в `VerifyReadable`, что гарантирует однократный и достоверный вывод.
2. **Прямой бинарный парсер Matroska / WebM (`ParseMkvFull` в `VideoMetadataExtractor.cs`):**
   - Реализован чистый автономный C# парсер EBML:
     * Чтение `EBML Header` (`0x1A45DFA3`) и `Segment` (`0x18538067`).
     * Извлечение `TimecodeScale` (`0x2AD7B1`) и `Duration` (`0x4489`) из `Info` (`0x1549A966`).
     * Извлечение `PixelWidth` (`0xB0`) и `PixelHeight` (`0xBA`) из `Tracks -> Video` (`0x1654AE6B`).
     * Парсинг тегов `Tags -> Tag -> SimpleTag -> DURATION` (`0x45A3` / `0x4487`) для файлов, где длительность записана в метатегах FFmpeg/Lavf.
     * Поддержка смещений `SeekHead` (`0x114D9B74`) для файлов с индексами метаданных.
3. **Резервный опрос Windows Shell Property System (`IPropertyStore`):**
   - Через `SHGetPropertyStoreFromParsingName` запрашиваются системные свойства `PKEY_Media_Duration`, `PKEY_Video_FrameWidth`, `PKEY_Video_FrameHeight` (откуда Проводник Windows берет данные о продолжительности и размерах кадра).
4. **Защита от подмены разрешения видео размером эскиза:**
   - Если истинное разрешение видео уже определено парсером или Shell Property Store, размер стоп-кадра (`320x180`) больше не перезаписывает реальные габариты видеопотока.

## 78. Миллисекундная точность временных меток и сквозное сохранение PID вызывающего процесса при перезаписи (Root Cause First)

### Контекст и симптомы:
1. При резервном копировании и синхронизации папок утилитами бэкапа (Create Synchronicity, SyncBack и др.) с диска `D:` на диск `Y:` файлы загружались успешно при первом запуске, однако при повторной синхронизации программа предлагала перезаписать (`Update: Слева -> Направо`) уже существующие неизмененные файлы (например, `Nina - Counting Stars.mp3` и `[FDM] Ben Delay feat. Alexandra Prince...`).
2. При выполнении повторной перезаписи виртуальная файловая система WinFsp не могла обнаружить исходный файл на диске `D:` и писала в журнал:
   `[Write] Исходный путь для '...' НЕ найден в буфере обмена Windows.`
   В результате выполнялся аварийный откат на чтение первых 256 КБ входного потока (`ExtractFromStream`), из-за чего длительность аудио определялась как `0 сек`, а обложка отсутствовала.

### Первопричина (Root Cause Analysis):
1. **Усечение миллисекунд в базе данных (`NodeRepository.cs`):**
   - Метод `UpdateNodeTimestamps` и запись в базу SQLite форматировали даты модификации и создания как `yyyy-MM-dd HH:mm:ss`, полностью отсекая доли секунды.
   - Файловая система NTFS на диске `D:` хранит время с точностью 100 наносекунд.
   - В свойствах Windows отображаются только секунды (`23:30:36`), создавая иллюзию идентичности дат. Однако утилиты синхронизации сравнивают таймстемпы на уровне Win32 API `FILETIME`: время исходного файла на `D:` (`23:30:36.427`) оказывалось больше времени виртуального файла на `Y:` (`23:30:36.000`) на 427 миллисекунд. Утилита считала исходный файл более новым и ставила его на повторную перезапись при каждом цикле бэкапа.
2. **Потеря идентификатора процесса в жизненном цикле WinFsp (`Open -> Overwrite -> Write`):**
   - Метод `WinFspServer.Open` создавал контекст `FspNodeContext` без заполнения `CreatorProcessId` (оставался равен `0`).
   - Согласно спецификации WinFsp, функция `FileSystemBase.GetOperationProcessId()` возвращает корректный PID вызывающего процесса во время операций `Create`, `Open` и `Rename`, но возвращает `0` во время вызовов `Overwrite` и `Write`.
   - В методе `Overwrite` значение `ctx.CreatorProcessId = overwritePid` безусловно перезаписывалось нулем.
   - При поиске открытых файловых дескрипторов ядра (`CollectOpenFileHandles`) процесс утилиты синхронизации (например, `Create Synchronicity.exe` PID 21740) отсутствовал в списке целевых PID, опрашивались только процессы `explorer.exe`, и исходный файл на `D:` не определялся.
3. **Сброс открытых дескрипторов каталогов в `CollectOpenFileHandles`:**
   - В ветке проверки открытых файлов проверка имени выполнялась как `Path.GetFileName(path) == targetFileName`.
   - Для открытых папок источника (`D:\TGtest\...\big`) имя папки (`big`) не совпадало с именем целевого файла (`Nina...mp3`), из-за чего открытая директория отбрасывалась без проверки вложенного файла и добавления папки в корни сессии копирования (`SourceRoots`).

### Принятое решение (Root Cause First):
1. **Сохранение и чтение полной миллисекундной точности дат (`NodeRepository.cs`):**
   - Введен единый стандарт сериализации дат SQLite: `yyyy-MM-dd HH:mm:ss.fff` (`FormatDateTime`).
   - Внедрен универсальный парсер `ParseDateTime`, безопасно считывающий даты как старого секундного формата, так и нового миллисекундного формата без потери совместимости.
   - Драйвер WinFsp передает в Win32 структуру `FileInfo` точное время `FILETIME`, синхронизированное с NTFS с точностью до миллисекунды. Повторные ложные предложения об обновлении в утилитах синхронизации полностью устранены.
2. **Сквозное сохранение `CreatorProcessId` в WinFsp (`WinFspServer.cs`):**
   - В `Open` фиксируется `CreatorProcessId = FileSystemBase.GetOperationProcessId()`.
   - В `Overwrite` сохраняется существующий `CreatorProcessId`, если `overwritePid <= 0`.
   - Идентификатор процесса бэкапера гарантированно доходит до `ResolveFileSource` и `Write`.
3. **Интеллектуальная проверка открытых каталогов в `CollectOpenFileHandles`:**
   - Разделена проверка `File.Exists(path)` и `Directory.Exists(path)`.
   - Если процесс держит открытым дескриптор папки (стандартное поведение утилит синхронизации при обходе дерева), сканер мгновенно проверяет существование целевого файла внутри открытой папки (`Path.Combine(path, targetFileName)`).
   - При обнаружении файл немедленно возвращается (Fast-Break), а путь к папке добавляется в `SourceRoots` сессии, позволяя фоновому бэкапу безошибочно находить оригинал и считывать полные метаданные (теги, длительность, обложки) даже без открытых окон Проводника.

## 79. Атомарное создание файлов в SQLite строго после завершения выгрузки (Zero-Stub) и устранение 0-байтовых файлов в корзине (Root Cause First)

### Контекст и симптомы:
1. При синхронизации файлов некоторыми утилитами (например, SyncBackFree) создаются временные файлы вида `SBSE____.***`, куда пишется контент, после чего файл закрывается (`Cleanup`) и переименовывается в целевое имя. Либо при отмене копирования файла пользователем в процессе выгрузки, в папке `.Trash` появлялись пустые 0-байтовые файлы без привязки к Telegram (`tg_message_id = null`).
2. Запись файла в базу SQLite выполнялась в два этапа: сначала в методе `Create` создавалась пустая заглушка с `size = 0` и `tg_message_id = null`, а затем в `Cleanup` происходило ее обновление данными из Telegram.
3. При отмене операции до завершения передачи WinFsp вызывал `Cleanup` с флагом `CleanupDelete` (`flags & CleanupDelete != 0`), из-за чего недогруженная заглушка с `size = 0` перемещалась в корзину `.Trash` через `SoftDeleteNode`.

### Первопричина (Root Cause Analysis):
Преждевременное сохранение сущности в постоянное хранилище (БД SQLite) до того, как операция передачи файла фактически завершилась. Запись промежуточных заглушек 0 байт нарушала атомарность и захламляла базу и корзину фантомными записями при любой отмене или обрыве загрузки.

### Принятое решение (Root Cause First):
1. **Чистая модель в памяти на этапе `Create` (In-Memory Node):**
   - В `WinFspServer.Create` для новых файлов (как обычных, так и VirtualCopy) объект `Node` создается исключительно в оперативной памяти с временным отрицательным ID (`Interlocked.Decrement(ref _nextTempNodeId)`).
   - В базу данных SQLite пустая заглушка больше НЕ записывается.
   - Активный загружаемый узел регистрируется в потокобезопасной коллекции `_activeUploadNodes` по нормализованному пути.
2. **Абсолютная чистота при отмене (`Cleanup` с флагом удаления):**
   - Если при вызове `Cleanup` передан флаг удаления или `DeleteOnClose`, и `node.Id <= 0`, операция прерывается: отменяется токен отмены потоковой загрузки (`UploadCts`), поток закрывается, узел удаляется из `_activeUploadNodes`.
   - Никаких записей в SQLite не создается, `SoftDeleteNode` не вызывается. 0-байтовые файлы-призраки в корзине исключены на корню.
3. **Единая атомарная фиксация после завершения передачи (`Cleanup` с `IsModified`):**
   - Только после того, как все байты переданы и получен `uploadResult.MessageId` (или сохранен inline_data), вызывается `_repository.CreateOrUpdateFile(...)`.
   - В единой транзакции SQLite создается полноценная запись со всеми реальными метаданными (`size`, `tg_message_id`, `updated_at`, `created_at`, `node_parts`).
   - Полученный реальный `nodeId > 0` присваивается `node.Id`, а путь удаляется из `_activeUploadNodes`. Последующие вызовы `Rename` от программ синхронизации работают уже с готовым реальным ID узла в БД.
4. **Защита от конфликтов доступа (`Open`, `SetBasicInfo`, `CanDelete`, `Rename`):**
   - В `Open` при попытке стороннего процесса открыть еще недогруженный файл, находящийся в `_activeUploadNodes`, возвращается статус `NT_STATUS_SHARING_VIOLATION`.
   - В `CanDelete` для узлов с `node.Id <= 0` возвращается мгновенный успех `STATUS_SUCCESS`.
   - В `SetBasicInfo` системные даты обновляются в памяти, а запрос `UpdateNodeTimestamps` в БД выполняется только если `node.Id > 0`.
   - В `Rename` при переименовании активного узла с `node.Id <= 0` перерегистрируется ключ в `_activeUploadNodes` без холостых запросов к БД.

## 80. Синхронизация выгрузки больших файлов (Multi-Part Chunks > 2 ГБ / 4 ГБ) с архитектурой Zero-Stub, исправление подписей и поддержка составных файлов в Virtual Copy (Root Cause First)

### Контекст и симптомы:
1. Выгрузка файлов размером более 2 ГБ (для базовых аккаунтов) и более 4 ГБ (для Premium) выполняется в Telegram путем разбиения файла на последовательные независимые бинарные части (`part1`, `part2`, ...) через `UploadMultiPartFileAsync`.
2. При анализе кода выгрузки больших файлов после вчерашнего перехода на Zero-Stub были выявлены следующие расхождения и скрытые дефекты:
   - В `BoundedStream` был сохранен собственный внутренний callback подсчета байт, что в сочетании с переданным callback `_client.UploadFileAsync` приводило к задвоению учета переданного объема в общем прогрессе выгрузки.
   - Подпись первой (мастер) части формировалась без использования канонического `NodeRepository.FormatTelegramCaption`: маркер части пристыковывался после хэштега `#latest`, ломая структуру хэштега, а строка `ID: {masterMessageId}` отсутствовала.
   - Подписи дочерних частей (2..N) не содержали системный идентификатор `ID: {message.ID}`, в отличие от одиночных файлов.
   - Метод мгновенного серверного копирования `ForwardFileAsync` (задействованный в WinFsp и WebDAV при Virtual Copy) принимал и форвардил только один `sourceMessageId` мастер-части. Все связанные записи из таблицы `node_parts` игнорировались, а в целевой узел передавался `parts = null`. В результате скопированные файлы более 2 ГБ становились нечитаемыми/поврежденными в SQLite после первой части.

### Первопричина (Root Cause Analysis):
1. **Изолированность реализации `UploadMultiPartFileAsync`:**
   При оптимизациях одиночных файлов логика канонического форматирования подписей и единого источника учета прогресса не была синхронизирована с методом многосоставной загрузки.
2. **Отсутствие поддержки коллекций `node_parts` в виртуальном копировании (`ForwardFileAsync`):**
   `ForwardFileAsync` проектировался под одиночные сообщения и возвращал кортеж `(int MessageId, int? PreviewMessageId)?`, не имея возможности вернуть обновленный список дочерних частей для новой копии файла.

### Принятое решение (Root Cause First):
1. **Синхронизация учета прогресса выгрузки (`UploadMultiPartFileAsync`):**
   - Удален избыточный внутренний вызов `progressCallback` из `BoundedStream`.
   - Прогресс выгрузки каждой части учитывается строго один раз через стандартный делегат `_client.UploadFileAsync(..., progress: (sent, total) => ...)`.
2. **Каноническое форматирование подписей составных частей (`TelegramService.cs`):**
   - Для мастер-части (Часть 1) путь формируется с наглядным указанием размера в гигабайтах `[Часть 1 из {partCount}, total={totalGb:F2} ГБ]`, форматируется через `NodeRepository.FormatTelegramCaption` и после отправки финализируется реальным `masterMessageId` и `#latest`.
   - Для дочерних частей (2..N) подпись сделана лаконичной: `↳ {rawCaptionPath} [Часть {partDisplayNum} из {partCount}]` без дублирования общего размера, с финализацией строкой `ID: {message.ID}` после отправки.
3. **Полноценная поддержка составных файлов в виртуальном копировании (`ForwardFileAsync`):**
   - Сигнатура `ForwardFileAsync` переведена на возврат `Task<FileUploadResult?>`.
   - Метод автоматически извлекает составные части оригинала через `NodeRepository.GetNodePartsByMessageId(sourceMessageId)`.
   - Если файл является составным (`parts.Count > 1`), метод последовательно форвардит все дочерние части на серверной стороне Telegram, формирует новый список `newParts` с актуальными `tg_message_id` в целевом канале и возвращает его в составе `FileUploadResult`.
   - В подписи мастер-части обновленной копии автоматически сохраняется корректный заголовок `[Часть 1 из N, total={totalGb:F2} ГБ]`.
4. **Сквозная передача частей в WinFsp и WebDAV:**
   - В `WinFspServer.Cleanup` результат `fwdResult.Parts` передается в `_repository.CreateOrUpdateFile(..., parts: fwdResult.Parts)`, гарантируя полную сохранность таблицы `node_parts` при копировании файлов любого размера.
   - В `WebDavMiddleware.HandleCopyAsync` аналогично передается `parts: fwdResult.Parts`.
